# 公開前検査の組織固有設定

`policy.json` は機械が読む設定、この文書はその**理由**を書く。値を変えるときは両方を更新する。

**この文書はルールの正本ではない。** 正本は共通運用ルールを定める索引リポジトリの `CONVENTIONS.md` である。
そこに定義の無い許容をここへ足さない。

## 4つの設定項目

### 1. `organization_accounts` — 許可する組織アカウント識別子

台帳・remote・所有者の表記は、組織アカウント識別子を名指ししないと成立しない。一方、検査は
リポジトリの著者名を辞書化して本文と照合するため、組織アカウント名が個人名として検出されうる。

**そこで、許可する識別子を1件ずつ、理由を添えて列挙する。**

- **一般的な著者名の一括除外はしない。** 「よくある名前だから除外する」形の辞書を置かない。
- 各エントリは `identifier` / `kind` / `reason` を持つ。**`reason` が10文字未満なら検査は起動しない**
  （`policy.json` の読み込み時に検証し、終了コード 2 で止まる）。
- 許容するのは**組織・サービスの識別子**だけである。個人名・個人アカウント名・個人のメールアドレスは
  対象外で、引き続き検出する。

### 2. `anonymized_path_placeholders` — 匿名化されたパスの形

端末の配線を説明するには、パスの**形**を示す必要がある。利用者名の位置を伏せた表記は許容し、
**実在の利用者名を含む絶対パスは引き続き検出する。**

- 許容するのは、利用者名の位置が `<...>` `＜...＞` `{{...}}` `%VAR%` `$VAR` `...` `…` のいずれかに
  一致する場合だけである。
- 実在の利用者名はどの形にも一致しないため検出される。境界は `tests/test_preflight.py` の
  `test_anonymized_placeholder_path_passes` と `test_real_looking_absolute_path_blocks` が確認する。

### 3. `conversational_rule_exempt_paths` — 空にする

**会話文脈の規則に例外パスを設けない。** 設定は空のまま置き、値を足さない。

以前は、設計側とのやり取りを記録した実装ブリーフを原文のまま追跡するために、この一覧へ
そのパスを入れていた。**そのパスは追跡しないことに決めたため、例外の根拠が無くなった。**
追跡しない場所に「検査を外す」宣言を残すと、後から別の用途で追跡され始めたときに、
誰も気づかないまま検査が外れる。

- 調整記録・実行履歴は成果物ではない。`.gitignore` で公開対象から外し、端末に残す。
- 原文保持が要る記録を将来追跡する必要が出たら、**例外を復活させる前に**「なぜ公開物として
  必要か」を上の4列で埋める。
- 境界は `test_conversational_wording_blocks_under_every_path` と
  `test_policy_declares_no_conversational_exemption` が確認する。

### 4. `operational_log_paths` — 追跡を認める運用ログ

共通運用ルールは「バックアップの複製本体は追跡しない。ただし**復旧領域ごとに1つの運用記録**は
追跡する」と定める。

- 許容するのは `backups/BACKUP_LOG.md` と `backups/<復旧領域>/BACKUP_LOG.md` だけである。
- **バックアップ本体・生データは引き続き検出する。** 境界は `test_operational_log_passes` と
  `test_backup_body_blocks` が確認する。
- サブディレクトリのログを追跡するには、対象リポジトリ側の `.gitignore` で
  「親ディレクトリを再包含 → 中身を除外 → ログだけ再包含」の順に書く必要がある。設定を足すだけでは
  追跡候補にならない。

## 変更するときの順序

1. 索引リポジトリの `CONVENTIONS.md` を更新する（PR）。
2. `policy.json` とこの文書を更新する。
3. 必要なら `preflight.py` を更新し、**先に `tests/` へ境界のテストを足してから**反映する。

**検査だけを書き換えない。** 検査が正本に追随していない状態は実装側の未完了であり、
文書を歪めて回避しない。恒久的に発生する検出を `--force` や抑制マーカーで通し続けない。

## 例外を増やすときに埋める4列

新しい許容を足すときは、次の4つを書けることを確認する。書けないものは例外ではなく未解決の課題である。

| 列 | 内容 |
| --- | --- |
| 対象 | 何を許容するのか（範囲を絞って書く） |
| 理由 | なぜ許容しないと文書が成立しないのか |
| 許容しない範囲 | 引き続き検出するもの。ここが空なら例外の設計が誤っている |
| 実装方針 | 検査側でどう表現するか。そして回帰テストをどこに置くか |

## receipt_root

検査レシートの置き場所。**検査する側（`preflight.py` の既定）と読む側（PreToolUse ゲートを置く場合）が
この1つの宣言を読む。**

- 場所を2箇所に書くと、書いた先と読む先が食い違う。実際にそれが起きていた: ゲートは
  エージェント home の cache を読み、`preflight.py` はエージェント home への書き込みを拒否する
  実装だったため、レシートは永久に見つからず、フックを登録すれば全リポジトリで commit と push が
  拒否される状態だった（2026-09-03 に実測して修正）。
- エージェント home（`~/.claude` / `~/.codex`）の外に置く。設定リポジトリが端末のホームを
  汚さないという原則を保つため。
- 一時ディレクトリに置かない。検査した直後に掃除で消えると、ゲートが誤って拒否する。
- 値は移植可能な形で書く（`~` 展開）。実在の利用者名を含む絶対パスは書かない。
