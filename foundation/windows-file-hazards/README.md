# Windows でエージェントにファイルを触らせるとき、どこで黙って壊れるか

**この手引きは未検証です。** 下の確認手順はこの環境で実行していません。実行ファイルとしては置いて
いないので、使うなら自分のところへ写し、1 つずつ確かめてから使います。状態は `experiment` で、
特定の設定の導入を勧めるものではありません。

## 何の問題を扱うか

ここで扱うのは、モデルの出力が誤っている場合ではなく、**出力は正しいのに、ファイルに着くまでの
間に中身が変わる**場合です。起動条件は「Windows でエージェントにファイルを読み書きさせている」こと。
三つの層があり、いずれも**失敗が画面に出ません**。

| 層 | 何が変わるか | 気づけるか |
| --- | --- | --- |
| 文字の符号化 | 日本語が化ける、角括弧が構文として誤解される | 開けば見える |
| 改行 | ファイル全体が差分になる、シェルの処理系が行を読み違える | 差分で見える |
| クラウド同期のプレースホルダー | 中身が**途中までしか読めず**、その状態で書き戻される | **見えない** |

三つ目だけが性質が違います。ファイルの大きさは正しいまま、中身が切り詰められます。

## 1. 符号化：版によって既定が違う

提供元の仕様（`REF-154`）では、既定の符号化は版で分かれます。

- **Windows PowerShell 5.1**: BOM の無いファイルを読むとき、実行系は系の ANSI コードページとして
  解釈します。日本語環境ではこれが日本語用のコードページになるため、BOM 無し UTF-8 で保存した
  スクリプトの非 ASCII 文字が壊れます。提供元自身が「非 ASCII を使うなら BOM 付き UTF-8 で保存せよ」と
  書いています。
- **PowerShell 6 以降**: 出力は一律で BOM 無し UTF-8、読み取りも同じ前提です。この罠は起きません。

**入口の記事（`ART-046`）が扱っているのは読み取り側だけですが、書き出し側にも同じ段差があります。**
5.1 では `Out-File` と `>` / `>>` が **UTF-16LE** を作り、`Set-Content` / `Add-Content` は対象が空か
存在しないとき ANSI を使い、`Export-Csv` は ASCII を作ります。同じ会話の中で「ファイルに書き出す」と
言っても、どのコマンドを選ばせたかで出てくる符号化が三通りに分かれます。エージェントに書き出させる
場合はここが先に効きます。

### この環境特有の衝突

同じ公式ページが、**BOM 付き UTF-8 は Unix 系の道具で問題になる**と書いています（`cat`、`sed`、`awk`
などが BOM を解さない）。Windows 上で PowerShell と Git Bash を**両方**使う構成では、入口の記事の
対処（BOM を付ける）は片方を直して片方を壊します。先に決めるのは対処ではなく**どちらの処理系が
そのファイルを読むか**です。

| そのファイルを読むのは | 妥当な既定 |
| --- | --- |
| Windows PowerShell 5.1 だけ | BOM 付き UTF-8 |
| Unix 系の道具・Git Bash・他のエージェントも読む | BOM 無し UTF-8。PowerShell 側を 7 以降にする、または非 ASCII をスクリプト本体へ書かない |
| 判断がつかない | 非 ASCII を**ファイルの外**（データファイル・引数）へ出し、スクリプト本体を ASCII に保つ |

### 系全体を UTF-8 にする選択肢

提供元には、プロセスまたは系の有効コードページを UTF-8 にする道があります（`REF-155`）。アプリの
manifest で指定する方法と、言語設定の「ベータ: ワールドワイド言語サポートで Unicode UTF-8 を使用」で
系全体を切り替える方法です。同じページが条件も書いています。manifest の指定は**描画系には効かず**
そちらは系の設定を見ること、系の設定は**再起動が要り、全アカウントに及ぶ**こと、そして
プログラムの側はこの設定がされていることを前提にできないこと。

つまりこれは「一度入れれば済む」設定ではなく、**自分の機械の全体の前提を変える**操作です。
この環境では入れていません。入れる場合は、既存の処理が ANSI を前提にしていないかを先に確かめます。

### 出力側の既定を 1 行で揃える

5.1 では、符号化を持つコマンドの既定をまとめて変えられます（`REF-154`）。

```powershell
# 現在のセッションに対して。恒久的にするならプロファイルへ置く
$PSDefaultParameterValues['*:Encoding'] = 'utf8'
```

ただし 5.1 の `utf8` は **BOM 付き**です。BOM 無しが要るなら、この指定では足りません。
また `$OutputEncoding` は外部プログラムとのやり取りに効く別の変数で、ファイルへの保存には効きません。

## 2. 改行：道具ごとに直さず、版管理の層で決める

入口の記事は、その場で編集する道具がファイル全体の改行を変えてしまう例を挙げ、別の道具を使う対処を
示しています。これは**その道具の数だけ対処が要る**形で、エージェントが選ぶ道具を事前に数え上げる
ことはできません。

改行の決定は版管理の層に持てます（`REF-156`）。`.gitattributes` に書けば、利用者ごとの設定より強く、
機械が変わっても同じ結果になります。

```gitattributes
* text=auto          # 既定。取り込む側は LF に正規化する
*.sh   text eol=lf   # Git Bash / WSL が読む。CR が混じると行を読み違える
*.ps1  text eol=crlf # Windows の処理系が読む
*.png  binary        # 触らせない
```

既にあるリポジトリに入れる場合は、設定を入れてから `git add --renormalize .` を通し、その結果だけを
別の変更として記録します（`REF-156`）。そうしないと、以後の変更が常に「全行が差分」になります。

**その場で編集する道具について、確かめられた性質を 1 つだけ書いておきます。** 入口の記事が指摘する
改行の変換自体は、ここでは一次情報で裏付けられませんでした。裏付けられたのは別の性質で、
**`-i` のような「その場で編集」は、たいてい上書きではなく置換**（別のファイルを作って名前を入れ替える）
だということです。これが次の節の問題に直結します。

## 3. クラウド同期：ここだけは、黙ってデータが消える

### 何が置かれているのか

同期フォルダのファイルは、必ずしも中身を持ちません。オンライン専用の状態では、大きさだけを持つ
置き札が置かれています。状態は三つあり、属性として問い合わせられます（`REF-157`）。

```text
attrib <パス>        # P = 常に保持 / U = オンライン専用
attrib +p <パス>     # 中身を落としてから触る
```

属性を読むだけなら中身は落ちません。**書き込みの前にこれを確かめられる**、というのがこの節で一番
使える事実です。

### 報告されている壊れ方（三つ、いずれも対応予定なしで閉じている）

この環境で使っているのと同じ製品の課題管理に、三つの別々の壊れ方が報告されています。

1. **置き札を完全なファイルと誤認して、切り詰めて書き戻す**（`REF-159`、2026-05-25 報告）。
   報告では、十数万バイトのファイルが途中で切れた状態で読まれ、その状態のまま書き戻されています。
   エラーも警告も差分の確認も出ません。報告者が挙げている検出方法が有用です。
   **大きさが 0 でないのにディスク上のブロックが 0 なら、中身はそこに無い**、という判定です。
   後続の報告では、完全に落としてあるファイルでも、外側で編集した後に別経路から読むと切り詰められる
   ことと、クラウドの層が無い普通のディスクでも同じことが起きることが報告されており、
   原因は同期そのものよりも**経路をまたいだときの整合性**の側にあります。

2. **置換書き込みが、同期の側から「削除」と見なされる**（`REF-158`、2026-06-04 報告）。
   編集の道具が「一時ファイルを作る → 元を削除する → 名前を入れ替える」の順で置換すると、
   同期の処理系がこの削除を権威あるものとして先にクラウドへ伝え、後続の名前の入れ替えが無視される、
   という報告です。報告の再現条件が重要で、**最近触っていないファイルほど壊れます**（報告では
   数時間では壊れず、十日放置したものは確実に壊れた）。ファイルの大きさは引き金ではありません。
   対象として Edit / Write / NotebookEdit が挙がっています。

3. **広い走査が、無関係なクラウド専用ファイルを大量に落とす**（`REF-160`、2026-03-17 報告）。
   下位エージェントを使った探索で、対象のリポジトリと無関係な画像や文書まで落ち始めた、というもの。
   原因の説明（範囲の指定が無い検索が利用者ディレクトリ全体を走査する）は報告者の推定です。

**三つとも「対応予定なし」として閉じています。** つまり上流で直るのを待つ設計にはできません。
対処は利用者の側の環境に置くことになります。

### 入口の記事との食い違いを、そのまま残す

入口の記事（`ART-046`）は、オンライン専用のファイルは検索で**ヒットしない**と書いています。
上の 3 は**逆向き**（検索が全部落としてしまう）です。どちらも「置き札の状態が結果を決め、ファイルの
大きさからは分からない」という同じ性質の表れですが、**どちらに転ぶかは道具による**ので、
片方だけを前提にした対処は外れます。ここでは片方に決めず、先に状態を見る側に寄せています。

### 対処の順序

1. **作業ツリーを同期の外へ置く。** これが一番確実で、ほかのどの対処よりも先に検討します。
   同期は成果物の配布のためのもので、版管理と役割が重なっています。
2. 置けない場合は、**触る前に状態を確かめる**（`attrib`、またはブロック数）。オンライン専用のまま
   編集させない。
3. **編集の後に読み返して確かめる。** 大きさと更新時刻とハッシュを編集の前後で比べます。
   これは `REF-158` の報告者が実際に使っている回避策で、**黙って壊れる種類の故障には、黙って
   成功したように見える出力ではなく、独立した読み返しだけが効きます**。
4. 重要なファイルは、エージェントに直接編集させず、別の場所で作らせてから自分で移す。

```powershell
# 編集の前後で比べる。値が縮んでいたら、そこで止める
Get-Item <パス> | Select-Object Name, Length, LastWriteTime, Attributes
(Get-FileHash <パス>).Hash
```

## どのシェルの道具になるか

Windows でこの製品をそのまま動かす場合、**サンドボックスは利用できません**（`REF-161`）。また、
Git for Windows が入っていれば Bash の道具が使われ、入っていなければ PowerShell の道具が使われます。
両方入っている構成では両方が並びます。上の 1 と 2 は、どちらの道具が選ばれたかで答えが変わるので、
自分の環境がどちらなのかを先に確かめます。配置と設定の詳細は [../claude-code/README.md](../claude-code/README.md) にあります。

## 他の領域との関係

- 広い走査の費用はトークンだけではありません。同期の下では帯域とディスクも使います。
  委譲の判断は [../heavy-read-delegation/](../heavy-read-delegation/) にあります。
- 「黙って切り詰められる」はこの領域に固有ではありません。手元で動かす実行系が入力を黙って切る話は
  [../local-model-boundary/](../local-model-boundary/)、変換先の形式で中身が落ちる話は
  [../presentations/](../presentations/) にあります。見えているものが全部だと仮定しない、という
  同じ形がこれで三例目です。
- 指示では確実にできないことを hook に置く判断は [../claude-code/README.md](../claude-code/README.md)
  にありますが、**この領域の対処を hook に寄せるのは順序が逆です。** 止める閾値の根拠（自分の機械が
  同期の下にあるのか、どの道具が選ばれているのか）を先に確かめます。

## 限界

- `ART-046` は実務者の記録で、対照も測定もありません。採ったのは入口の四つと、著者が実測した
  一つの観察（同期の完了より先に道具が起動する）だけで、数値は移していません。
- `REF-158`・`REF-159`・`REF-160` は利用者からの報告で、提供元による確認ではありません。
  三件とも対応予定なしとして閉じています。採ったのは機構と検出方法であって、再現率ではありません。
  報告された所要日数やファイルの大きさは移していません。
- `ART-046` の「その場で編集する道具が改行を変える」という主張は、一次情報で裏付けられませんでした。
  未確認として扱い、代わりに確かめられた性質（置換であること）を書いています。
- 符号化の既定は版に強く依存します（`REF-154`）。使う版を確かめてから適用します。
- この環境では、作業ツリーが同期の下にあるかどうかを確かめていません。上の確認手順は未実行です。
