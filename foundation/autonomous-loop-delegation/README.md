# 自律ループにどこまで任せるか

**この手順はこの環境で実行していません。** 根拠は提供元の公開資料と公開された研究で、ここに書いたのは
判断の型です。状態は `experiment` です。

起動条件は「**作業を1つずつ指示するのをやめて、まとめて回させたくなったとき**」です。
[../model-tier-selection/](../model-tier-selection/) は作業を始める段階でどのモデルを選ぶか、
[../heavy-read-delegation/](../heavy-read-delegation/) は1回ごとの大きい読み取りを逃がすかどうかを扱います。
ここはその手前にある別の問い、**そもそも何周分を人の確認なしで回させてよいか**を扱います。

## 先に決めるのは「何を証拠にするか」

任せられる範囲は、エージェントの賢さではなく**その作業に機械判定できる検証があるか**で決まります。
提供元はループを「文脈を集める → 手を動かす → 出来を確かめる → 繰り返す」と定義したうえで、
確かめ方を信頼度の順に並べています（`REF-049`）。

| 確かめ方 | 信頼度 | 向く対象 |
| --- | --- | --- |
| 規則で判定する（テスト、型、リント、スキーマ） | 高い。どの規則がなぜ落ちたかまで返る | 任せてよい範囲の上限を決める基準そのもの |
| 画面や描画を見る | 中くらい。1つの視点しか写らない | 見た目・配置 |
| 別のモデルに判定させる | **低い。**提供元自身が、一般に頑健な方法ではないと断っている | ほかに手が無く、多少の改善でも割に合う場合だけ |

**この順序がそのまま、任せてよい範囲の順序になります。** 規則で判定できるところまでは回させ、
判定が画面の目視や別モデルの意見に落ちた時点が、人が受け取る境目です。
別モデルの判定を唯一の根拠にして完了と扱わない、というのがこの表の読み方です。

同じ理由で、**エージェントの完了報告は検証ではありません**。報告は、その作業をした当人による自己申告です。
提供元は、確かめるものが無ければ「できたように見える」が唯一の信号になり、**人が検証ループそのものになる**と
書いています（`REF-055`）。成功したと主張させるのではなく、**証拠を出させます**。実行したコマンドとその返り値、
テストの出力、結果の画面です。あとから証拠を読む方が、自分で検証をやり直すより速く、見ていなかった回にも効きます。

## 指示に書くだけでは効かない

常時の指示ファイルに原則を書けば守られる、とは扱いません。提供元は、**指示ファイルの記述は助言であり、
hook は確定である**と明記しています（`REF-055`）。必ず起きてほしいことは、文章ではなく仕組みに置きます。

同じ資料は、指示ファイルに**書かないもの**として「自明の良い習慣（きれいなコードを書く、等）」を挙げています。
また、ルールがあるのに守られないなら原因はたいていファイルが長すぎることで、**指示が無くても正しくできている
項目は削るか hook へ変換する**としています。見直しの判定も、文面の良し悪しではなく**挙動が実際に変わったか**です。

読み替えると、自律で回すときに効くのは文章の立派さではなく、**止め方の強度**です。

| 強度 | 形 | 効く範囲 |
| --- | --- | --- |
| 弱 | 同じ指示文の中で「確かめてから直せ」と頼む | その場限り。どの作業でも今日から使える |
| 中 | セッションの達成条件として置き、毎ターン別の評価器が再判定する | 1 セッション。達成するまで続き、行き詰まれば止まる |
| 強 | 終了時に走る hook で検査を実行し、**合格するまで終了させない** | 無人の実行。連続して阻める回数には上限がある |
| 別軸 | 別の文脈の下位エージェントに、結果を否定できるか試させる | 作った当人が採点しない状態を作る |

弱いものほど設定が要らず、強いものほど**見ていない間に正しく終わる**確率が上がります（`REF-055`）。
無人で回す前に、どの強度まで用意したかを確かめます。

ただし否定役には副作用があります。欠点を探せと頼まれた確認役は、**健全な成果にも何かしら指摘を返します**。
指摘をすべて潰すと、要らない抽象化・防御的なコード・起こり得ない場合の試験が積み上がります。
確認役には「正しさか、決めた要件に関わるものだけを挙げる」と範囲を与え、残りは任意として扱います（`REF-055`）。

## 周回数そのものが危険量

ループは定義上、何度も往復します。往復そのものが品質を下げることが測られています。6 つの生成課題・
20 万を超える模擬会話で、**多ターンは単発より平均 39% 低い**という報告があります（`REF-056`）。
内訳が重要で、落ちているのは能力よりも**信頼性**です。早い段階で仮定を置いて解に飛びつき、それに依存し、
**いったん誤った方向へ進むと戻ってこない**。

これは「自律で回せば人の確認を減らせる」という見込みに正面から当たります。**周回を増やすこと自体が
失敗率を押し上げる**ので、周回数は節約の手段ではなく管理すべき量として扱います。実務的には、
区切りで文脈を切り直す、誤った前提に乗ったまま進ませない、2 回直しても直らなければ回し直すより
やり直す、という向きになります。

原因については見方が割れています。別の研究は、これはモデルの能力不足ではなく**利用者とモデルの間の
意図のずれ**であり、規模を大きくしても学習を改善しても解けないとして、曖昧な入力を明示的な指示へ
変換する仲介役を置く構成を提案しています（`REF-057`）。どちらも査読前なので、採るのは
**現象の向き（多ターンでは落ちる）**だけで、原因の説明も数値も移しません。ただし原因が意図のずれ側に
あるなら、対策は「賢いモデルに替える」ではなく「**回す前に要件を書き切る**」になります。

## 求める成功率を下げると、任せられる長さが縮む

「どれくらい長く任せられるか」は、**どれくらいの失敗率を許すか**と一組で決まります。
査読を通った測定（`REF-053`）が使っている指標は「50% の成功率で完了できる作業の、人の所要時間」です。
指標の定義自体が、**成功率を固定しないと長さを語れない**ことを示しています。許す失敗率を下げれば、
同じモデルで任せられる長さは短くなります。

送信記事（`ART-013`）が見出しに置いている「最強 AI でも成功率25%」も同じ向きの話です。
記事の本文は会員限定で確認できず、その数字の出所も追えませんでしたが、**完全自動化の成功率に限界がある**
という方向だけは、この測定と提供元の注意（誤りが累積する、`REF-051`）の両方が独立に支持しています。

実務上の読み替えはこうなります。

- 失敗しても安く戻せる作業 → 長く任せてよい。復旧の経路を用意する方が、成功率を上げるより効く
- 失敗が高くつく作業（本番反映、外部への公開、削除、資格情報） → **1周ごとに人が受け取る**
- 判定が機械でできない作業 → 長さにかかわらず、成果物を人が見るまで完了にしない

## 止まらないループは実在する

停止条件を書かないと何が起きるかは、測られています。6,549 のエージェント実装を静的解析した報告では、
47 プロジェクトで 68 件の「終われないループ」が手で確認されました（`REF-054`、精度 91.9%、査読前）。
費用の増加とサービス停止につながる、としています。

提供元の原典も、制御の手段として**反復回数の上限**と**チェックポイントで人に戻すこと**を挙げています
（`REF-051`）。回す前に書くのは、次の4つです。

1. 完了を示す証拠（どのコマンドが何を返したら完了か）
2. 反復回数または時間の上限
3. 安全に止める条件（上限に達した、同じ失敗が続いた、想定外の権限を要求した）
4. 人が引き取る判断点

## 1回の文脈に収まらないとき

長く回す場合は、**文脈が切れても続けられる形**が要ります。提供元の実装例（`REF-050`）は次の組み立てです。

- 進捗を**ファイルに書き出し**、作業の区切りで commit する
- 次のセッションは、履歴と進捗ファイルを読んでから始める
- **やることの一覧を外に持ち**、エージェントには完了欄だけを更新させる。一覧やテストを書き換えることは
  禁じる。これが早すぎる「終わりました」を防ぐ仕組みになっている
- 壊れたら履歴から戻せるようにしておく
- セッションの頭で、まず動く状態かを確かめる試験を1本通す

**自己申告できる場所を狭めるのが要点です。** 完了欄だけを触らせ、判定の規則そのものには触らせません。

## ループの組み立て方

同じ指示を何度も流し続ける形には、提唱された技法があります。最小の形は、同じプロンプトを無限に流す
シェルのループです（`REF-058`）。提唱者が挙げる不変条件は 3 つです。

- **1 周に 1 仕事。** まとめて片付けさせない
- **仕様と修正計画を、毎周あらためて積み直す。** 前の周の記憶に頼らせない
- **テストとビルドを背圧にする。** 進み具合ではなく、落ちた検査が次の仕事を決める

提唱者自身が、この技法は完成を保証しないと書いています。状態は「焼けていない」「焼けた」
「仕様化していない潜在挙動」の 3 つしかなく、**上級者が設計と判断に関わり続けることが前提**です。
失敗の例として、探索結果が安定しない、仮実装に流れる、同じ実装が重複する、文脈が尽きると崩れる、を
挙げています（`REF-058`）。

### 外に置く 4 点

公開された実践報告は、約 40 画面の作り直しにこの形を使い、外に次の 4 つを置いています（`ART-031`）。

| 置くもの | 役割 |
| --- | --- |
| 進捗表 | 対象 × 工程（仕様／実装／テスト）の表。**1 周 1 ステップ**の対象をここから選ばせる |
| 手順書 | 毎周読ませる作業の決まり。検証を別の担当へ回すことなどを書く |
| 判断待ちの置き場 | 進められないものを積む先。人はここをまとめて見る |
| 仕様の雛形 | 対象ごとの仕様を同じ形で書かせる |

**これは [上の節](#1回の文脈に収まらないとき)で提供元が示した構成と同型です**（`REF-050`）。
提供元とは別の組織が、独立に同じ形へ到達している点が、この構成の確からしさを支えます。

完了の扱いも同じ考え方です。報告では、進捗表の全行が済みか対象外か保留になるまで、
**完了を示す合図を出すこと自体を禁じています**（`ART-031`）。「だいたい終わった」を言わせない形です。

### 観測された壊れ方

同じ報告が、実際に起きた失敗を記録しています（`ART-031`）。

- **要約で初期の指示が薄れ、途中で人に判断を仰いで止まった。** 長い往復では会話の履歴が要約され、
  履歴として入っているものは一緒に消えます。入口の指示ファイルや条件なしのルールは読み直されますが、
  会話として渡した指示は戻ってきません（`REF-017`）。**毎周積み直す**という不変条件は、ここに効きます
- **完了扱いなのに検証されていない対象が残った。** 進捗表の欄を自分で埋められる限り起こります
- **検証役が、実行中に次の依頼を受けて溢れた。** 解決側では、依頼を出す周と結果を取り込む周を分け、
  検証を独立した担当へ並列に出す形にしています

### 向く仕事と向かない仕事

報告の著者は、相性を次のように書いています（`ART-031`）。

| 向く | 向かない |
| --- | --- |
| 旧画面を元に新画面を作るなど、**要件が明確で作業量が多い**仕事 | 荒い要件を渡して、よしなに判断させることが許されない仕事 |

同じ著者が、**動かす時間が延びるほど、機械が判断する部分も増える**と注記しています。
これは前の節（周回数そのものが危険量）と同じ向きで、`REF-058` が上級者の関与を前提に置くのとも一致します。
つまりこの形は、**判断の量を減らす仕事にだけ向きます**。判断を増やす仕事に使うと、増えた判断は
人の目を通らずに通過します。

報告されている「約 1 日で一巡」という結果は、1 組織の自己申告で、対照も品質の測定もありません。
採れるのは構成と失敗様式であって、所要時間ではありません。

## 足場が前提にしていることは古くなる

提供元は、ループの足場について「**モデルが自分ではできないことについての仮定を符号化したもの**であり、
その仮定はモデルが良くなると陳腐化するので、繰り返し疑う必要がある」と書いています（`REF-052`）。
実例として、ある世代では文脈の上限が近づくと作業を早く切り上げる挙動があり、足場の側で文脈を
入れ替える対処を入れていたが、**次の世代ではその挙動自体が消えていた**ことを挙げています。

ここから採れるのは、**足場を足したときは理由と前提を書き残し、版が上がったら外せるかを見直す**という運用です。
対処を入れた理由が書かれていないと、要らなくなった制約だけが残ります。

## 限界

- 数値はすべて提供元または研究側のもので、ここで再現していません。採ったのは順序と失敗様式です。
- `REF-051` はページ自身が「2024-12 以降、周辺は変わった」と断っており、原典として引いています。
  現況の根拠には `REF-049`・`REF-050`・`REF-052` を使います。
- `REF-054` は査読前で、提案されたツールの評価も著者ら自身によるものです。採ったのは
  「停止条件の欠如は実在し、珍しくない」という向きだけで、件数は移していません。
- `REF-056`・`REF-057` はどちらも査読前で、原因の説明が食い違っています。測られているのも会話の課題で、
  コーディングの自律ループそのものではありません。採ったのは「多ターンでは落ちる」という向きだけです。
- 止め方の強度の表は `REF-055` の記述を並べ替えたもので、ここで動かしていません。特に終了時の hook は、
  連続して阻める回数に上限があるため、**合格しないまま終われる場合がある**前提で使います。
- `ART-031` は 1 組織の実践報告で、対照も品質の測定もありません。所要時間と規模の数字は移さず、
  採ったのは外に置く構成と、観測された壊れ方と、著者自身が書いた適用範囲だけです。
- `REF-058` は個人のブログで、測定値はありません。採ったのは不変条件と、提唱者自身が挙げる限界です。
  費用についての主張は採っていません。
- 入口にした記事（`ART-013`、2 ページ目を含む）は本文が会員限定で、2026-10-06 の再確認では全体を
  読めませんでした。内容の判断は一次情報と研究だけで行っています。
