# 層のあるコードを書かせるとき、境界をどう決め、どう守らせるか

**この手引きはこの環境で実行していません。** 根拠は一次情報と公開された測定で、ここに書いたのは
判断の型です。状態は `experiment` です。

起動条件は「**層（ドメイン / ユースケース / データアクセス）を分けたコードベースに、
エージェントにコードを書かせる・足させると決めたとき**」です。

近い領域とは起動条件が違います。確かめる側の組み方は
[../review-design/](../review-design/)、どのモデルで始めるかは
[../model-tier-selection/](../model-tier-selection/)、言語や版に機械判定の土台が在るかは
[../low-resource-language-codegen/](../low-resource-language-codegen/) にあります。
ここは「**規則そのものが機械で判定できる形をしているか**」だけを扱います。

ここに書くのは製品にも言語にも依存しない設計です。

## 規則は 2 つに割れる。割らずに書くと、守れたかが分からなくなる

層の規則は 1 つの文に見えて、確かめ方の違う 2 つが混ざっています。

| 規則の種類 | 例 | 確かめ方 |
| --- | --- | --- |
| **依存の向き** | ドメイン層がデータアクセスの実装を参照しない。層をまたぐ循環が無い | 機械で判定できる |
| **責務の中身** | データアクセス層に業務上の判断が埋まっていない | 機械では判定できない |

この区別が実務で効くのは、**後者が前者に一切現れない**からです。保存する前に条件分岐で値を
組み立てる、という処理は、`import` を 1 つも増やさずにデータアクセス層へ書けます。
依存の検査は緑のままです。

したがって「層の規則を検査に入れた」と言えるのは向きの側だけで、中身の側は
レビューの観点として残ります。ここを一緒くたにすると、
**検査が緑であることを「層が守られた」と読む**誤りが入ります。これは
[../review-design/](../review-design/) が別の経路で到達している結論と同じ形です。

## 境界そのものは、一次情報の言い方を使う

データアクセス層の責務は、パターンの一次情報では「ドメインとデータマッピングの仲介」であり、
得られる性質として**きれいな分離と一方向の依存**が挙げられています（`REF-187`）。

この言い方を採る理由は、思想が立派だからではありません。**一方向の依存だけが、そのまま
検査規則に翻訳できる形をしている**からです。「責務を守る」は検査になりませんが、
「この方向の参照を禁止する」は検査になります。境界を宣言するときは、後者の語彙で書きます。

## 「出す」は正しい。「ユースケース層へ入れる」は行き先として危うい

データアクセス層から業務ロジックを出す、という方向自体は一次情報と一致します（`REF-187`）。
危ういのは**行き先の指定**です。

出したものをすべてユースケース層（アプリケーション層）へ置くと、`REF-187` を収めた書籍の著者が
同じ 2003 年にアンチパターンとして名付けた形になります（`REF-188`。カタログの当該項目自体は
別の執筆者の手による）。ドメインオブジェクトが
getter と setter の入れ物になり、サービス層がトランザクションスクリプトに戻り、
**ドメインモデルの費用を払って利益を受け取らない**状態です。同じ出典は分け方も示しています。
検証・計算・業務ルールはドメインのオブジェクトへ、永続化と表示の都合はその外へ。
サービス層を否定してはおらず、**薄く保つ層**として位置づけています。

エージェントに書かせる文脈でここが重要なのは、「ユースケース層へ移せ」が**1 手で実行できる
命令**だからです。文字どおり実行され、肥えたユースケースと空のドメインが残ります。
指示として書くなら 2 段階にします。

1. データアクセス層から出す
2. 検証・計算・業務ルールはドメインへ。**どのドメインオブジェクトにも属さない調整だけ**が
   ユースケースに残る

## 文章で書いた境界は、規模が上がるほど守られない

「層の責務」を指示ファイルに書けば済む、とは言えません。要求されたアーキテクチャ様式を
モデルがどこまで適用できるかを統制条件下で測った査読済みの研究は、**単純なパターンは
正しく適用できる一方、アーキテクチャの複雑さと問題の規模が上がるにつれて適合が落ちる**と
報告しています。検索で資料を足す構成（RAG）の効果はまちまちで、一方向に効くとは言えない、
というのが同じ研究の結論です（`REF-190`）。

ここから採るのは向きだけですが、その向きが設計を決めます。**守られなくなるのは、規模が
大きくて人が全部は読まない場面**です。つまり文章の規則は、最も効いてほしいところで弱くなります。
数値は移していません（後述の限界を参照）。

反対の結果も記録します。単著・査読前の測定は、同じ課題で最前線のモデルが違反率 0%、
公開重みの小さいモデルが大きく崩れる、と報告しています（`REF-191`）。これを読むと
「良いモデルを使えば検査は要らない」とも取れます。採用していないのは、1 課題・1 著者・
査読前で、かつ規模を上げた条件が含まれていないためです。`REF-190` が落ちると言っているのは
まさにその規模の側です。ただし同じ報告が、AST を解析して違反を数えるという**測り方**を
採っている点は、この手引きの前提と一致します。

## 向きの側を、落ちる検査にする

依存の向きは、設定ファイル 1 つで宣言して非ゼロ終了にできます。TypeScript / JavaScript の
系統では、公式の規則文書が次を定めています（`REF-189`）。

- `forbidden` は禁止する依存、`allowed` は許可する依存の明示、`required` は必ず持つべき依存
- `from` と `to` は正規表現で指定し、`pathNot` で除外する。`to` に `circular: true` を置くと
  循環依存にあたる
- 捕捉したグループを `to` 側で参照して「**自分の層の外を参照したら違反**」を 1 行で書ける
- `severity: "error"` のとき、対応するレポータが**非ゼロの終了コード**を返すのでビルドを落とせる

この形は未検証です。参考として、同じ文書が挙げている書き方を示します。

```json
{
  "forbidden": [
    {
      "name": "no-cross-layer",
      "severity": "error",
      "from": { "path": "^src/([^/]+)/.+" },
      "to":   { "path": "^src/([^/]+)/.+", "pathNot": "^src/$1/.+" }
    },
    {
      "name": "no-circular",
      "severity": "error",
      "from": {},
      "to": { "circular": true }
    }
  ]
}
```

同種の仕組みは他の言語系統にもありますが、ここで確かめたのは上の 1 つだけです。
名前を挙げての推奨はしていません。

### 入れる順序

1. **既存の違反を先に片付ける。** ビルドを落とす層へ規則を上げるのは、現状が通ってから。
   順序を逆にすると最初に壊れるのは自分のビルドです（[../review-design/](../review-design/) の
   移し先ごとの条件と同じ）。
2. **設定ファイルを正本にし、指示ファイルには場所と実行コマンドだけを 1 行で書く。**
   層の定義そのものを散文で書き足すと、正本が 2 つになって必ずずれます。
3. **機械で判定できない「中身」だけを、レビューの観点として残す。** 観点が短くなるので、
   人も意味的レビュー層も実際に見られるようになります。

### 検査を無効化する経路を、同じ層で塞ぐ

規則を黙らせる注釈や、設定ファイル自体の書き換えが対象側からできるなら、その検査は
合格条件になりません。例外が要る場合の正規の手続きを先に決めます。
これも [../review-design/](../review-design/) と同じ要求です。

## 限界

- この手引きはこの環境で実行していません。検査を回しておらず、上の設定例も動かしていません。
- `REF-189` は 1 つの道具の規則文書です。採ったのは規則の表現力と終了コードの扱いだけで、
  導入は勧めていません。版によって書式が変わりうるので、入れる前に当時の文書で確かめます。
- `REF-190` は本文を取得できず、書誌と要旨だけを確認しています。対象モデル・課題数・
  判定方法が読めていないため、適合率などの数値は移していません。
- `REF-191` は単著の査読前で、課題は 1 つです。違反率も、業務ロジックが省かれた量も
  移していません。反対方向の根拠として登録しています。
- `REF-187` と `REF-188` は 2003 年の文章です。採ったのは責務の分け方と、ロジックを
  サービス層へ集めたときに何が失われるかという指摘で、当時の実装技術は関係しません。
- `ART-014` は実測も対照もない設計論です。採ったのは問題設定と、データアクセス層から
  出すという向きだけです。
- 言語によっては、依存の向きを宣言する手段が無いか、検査器がこの環境で動かない場合があります。
  その場合は向きの側も機械判定できないので、前提から見直します
  （[../low-resource-language-codegen/](../low-resource-language-codegen/)）。
