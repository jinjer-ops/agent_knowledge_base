# どの段階のモデルで始めるか

**この手引きはこの環境で実測していません。** 価格と既定値は公式の一覧で確認した時点の値で、
採否は自分の環境で計算し直します。状態は `experiment` です。特定の段階へ下げることを勧めるもの
ではありません。

[../token-drain-review/](../token-drain-review/) は原因探し、
[../heavy-read-delegation/](../heavy-read-delegation/) は重い読み取りの逃がし先、
[../cost-change-evaluation/](../cost-change-evaluation/) は入れた変更の判定です。ここはその前、
**作業を始める段階で、どの段階のモデルを選ぶか**を扱います。

## よくある勧め方と、その前提

「まず安いモデルで試し、進まなければ上げる」という段取りはよく見かけます（`ART-028`）。
その記事の実測では、1 つの作業あたりの費用が最も安い段階で約 $0.07、中間で約 $0.72、
上位で約 $7.60 でした。**上下で 100 倍近い開き**があり、この比なら安い方から試す価値は大きい。

ただしこの前提は提供元によって変わります。別の提供元の公式の一覧では、同じ時点で
100 万トークンあたりの単価が最上位 $10 / $50、中位 $4 / $20、最小 $1 / $5 で、
**上下の差は 4〜10 倍**です（`REF-032`）。桁が 1 つ違えば、同じ段取りの損得も変わります。

## 損得は、価格比と一発成功率で決まる

上位モデルの単価を 1、安い段階をその **1/r**、安い段階で一発で終わる割合を **p** とすると、
失敗したときは上げ直して払い直すので、1 作業あたりの期待費用はおよそ次になります。

```
1/r + (1 - p) × 1      （上位でそのままやれば 1）
```

得になる条件は **p > 1/r**。つまり:

| 価格比 r | 安い段階で必要な一発成功率 |
| --- | --- |
| 100 倍 | 1% を超えれば得 |
| 10 倍 | 10% を超えれば得 |
| 4 倍 | 25% を超えれば得 |

**r が小さいほど、安い段階の成功率が効く。** 粗い見積もりですが、方向を間違えないためには十分です。
やり直しには文脈の作り直しと人の時間も乗るので、実際の損益分岐は表より厳しくなります。削ったのに
総額が増える形は、別のテーマでも測られています（[../cost-change-evaluation/](../cost-change-evaluation/)）。

## 下げる前に、下げ方は 1 つではない

公式が挙げている手段のうち、モデルの段階を下げるのは一部です（`REF-027`）。

| 手段 | 効く場面 |
| --- | --- |
| 作業に合わせて段階を選ぶ | 難しい設計判断と、定型の作業を同じ段階でやらない |
| **下位エージェントだけ小さいモデルにする** | 冗長な出力を別の文脈へ出す作業。宣言でモデルを個別に指定できる（`REF-026`） |
| 思考の深さ（effort）を下げる | 深い推論が要らない作業。**既定の値はモデルごとに違う**（`REF-032`、`REF-013`） |
| 作業の切れ目で履歴を切る | 長い文脈の再送が効いている場合 |
| 同じことが CLI でできるなら CLI | 常時の占有を無くす |

**本体の段階を下げるのは、このうち最も影響が大きい選択です。** ほかの手段で足りるなら先にそちらを
試し、下げるかどうかは[判定の手順](../cost-change-evaluation/)で費用と品質を同時に見てから決めます。

## 1 つ選ぶ代わりに、役割で分ける

段階を 1 つ選ぶのではなく、**上位と安い側を同時に走らせて役割を分ける**構成も報告されています
（`REF-034`、`ART-029`）。上位は計画・解釈・見直しを持ち、安い側が探索・実装・試験の実行を担当し、
上位は制約と成功基準を書いた短い指示を渡して監督します。

この構成の肝は、2 つが**それぞれ別の文脈と道具を持ち、指示・結果・指摘だけを交換する**ところに
あります。1 つの会話の途中でモデルを切り替えるとキャッシュが壊れますが、別の文脈で走らせれば
壊れません。同じ形は製品に内蔵の下位エージェントでも取れます（`REF-026`）。

提供元の報告では、公開されている指標で**品質はほぼ同等のまま費用が 36〜39% 下がった**とされ、
個別の内訳も出ています（ある課題で 64.3 → 63.1、費用 $14.63 → $7.88）。読むときの注意が 3 つ。

- **すべて提供元の自己申告です。** 独立した再現は見当たりませんでした。広く出回っている解説記事は
  発表の言い換えで、独立した根拠には数えません。
- **指標側の費用はトークン分だけです。** 採用している指標は、公開される 1 行が「ハーネスとモデルと
  推論の設定の組み合わせ」を表し、費用は提供元のトークン単価から計算されます。**基盤・運用・監督の
  費用は対象外**と明記されています（`REF-035`）。2 体を動かす構成は、まさにその対象外の側を増やします。
- **効果の桁が違う理由を見ます。** 出力を削って整える種類の改善は実測で 1 桁パーセントでした
  （`REF-030`）。役割を分ける構成が数十パーセントを主張できるのはレバーが違うからですが、
  根拠の強さも違います（前者は二段の検証、後者は自己申告）。

線引きの作り方は同じです。提供元も**弱い側に計画のための探索は渡さず、上位が常に監督する**設計に
しており、サイドキックの能力で届かない複雑な作業は対象外、どこまで委譲するかは研究中だと書いて
います。最初の指示だけでは作業の難易度は判定できず、コードを調べて初めて分かる、という前提も
同じ記事にあります（`REF-034`）。

## 自分で確かめられる作業かどうかで分ける

入口の記事が出している基準は、価格より使えます。**結果を自分で確かめられる作業**（差分が読める、
テストが通るかで判定できる、出力が短い）なら、安い段階の失敗は安く済み、気づける。確かめられない
作業（調査の結論、設計の判断、安全性に関わる修正）では、安い段階の失敗は気づかれないまま下流へ
流れます。段階を分ける線は、費用ではなく**検証のしやすさ**に引きます。

これは委譲の線引きとも一致します。要約だけを受け取る構成で推論を委譲できないのは、戻ってきた
要約の正しさを確かめられないからでした（[../heavy-read-delegation/](../heavy-read-delegation/)）。

## 手元で動かす場合は、段ではなくビット数で選ぶ

ここまでは外の提供元に送る前提でした。**置き場所が制約で先に決まっている場合**（資料を外へ
出せない、など）は、選ぶ軸が変わります。その判断自体は
[../local-model-boundary/](../local-model-boundary/) にあります。手元に置くと決めた後の選び方は
ここに置きます。

手元では単価ではなく**容量**が効きます。選択肢は「小さいモデルをそのまま動かす」か「大きい
モデルを圧縮して収める」かの 2 つで、0.5B〜14B の範囲と 7 種類の量子化方式を一般的な機材で
測った評価が、この分岐に直接答えています（`REF-100`）。

- **強く圧縮した大きいモデルのほうが、小さいモデルを無圧縮で動かすより一貫して良い結果でした。**
  同じ容量に収めるなら、規模を落とすより精度のビット数を落とすほうが有利、という向きです。
- ただし**重みあたり約 3.5 ビット付近で頭打ち**になります。それ以上削ると見返りが無くなるので、
  「限界まで圧縮して最大のモデルを」という方向には進めません。
- 資源の消費は重みあたりのビット数に比例しますが、**電力とメモリの振る舞いは量子化の方式で
  変わります。** 同じビット数なら同じ、とは扱えません。
- モデルが小さくなるほど、速度の律速が通信から計算へ移ります。

**採るのは向き（規模より精度を落とす、ただし下限がある）だけです。** 自分の機材と自分の作業で
測り直す必要があるのは、外に送る場合と同じです。上の表の「自分で確かめられる作業かどうか」で
分ける基準は、手元のモデルにもそのまま当てはまります。

## 段を下げる以外に、「生成しない」という選択肢がある

ここまでの段は、どれも文章を生成するモデルの中での選択でした。作業の一部が
**有限の選択肢に対する判定**（どの処理へ回すか、この文書は条件に当てはまるか）である場合、
文章を生成せず、選んだ選択肢と確率だけを返す種類のモデルが別にあります。独立した評価では、
**応答時間と費用は大きく下がり、正答率は最良の汎用モデルより下がる**という向きで揃っています
（`REF-110`）。

この選択肢は、上の「自分で確かめられる作業かどうか」の基準の内側に収まります。選択肢が
事前に書けて、正解を自分で用意できる判定だけが対象です。ただし**返ってくる確率を閾値として
使えるかどうかは別の問題**で、提供元の一次情報も「自分のデータで試して調整せよ」と書いています
（`REF-108`）。置き換えの判断手順と、その確かめ方は
[../typed-decision-gating/](../typed-decision-gating/) に置きました。

## 名前・価格・既定値は引き直す

- **モデルの一覧と価格は公式の現在の表を正本にします**（`REF-032`）。記事の表も、手元に置いた
  控えも、書かれた時点のものです。段階の名前自体が入れ替わることもあります。
- **課金の単位も提供元で違います。** ある提供元は要求の件数で数え、モデルごとの倍率と月の割り当てが
  あり、超過は 1 件いくらで課金されます（`REF-033`）。トークン単価で書かれた記事の数字を、
  件数で課金される環境へそのまま持ち込むことはできません。**まず自分の請求の単位を確かめます。**
- **既定の effort はモデルごとに違う**ので、段階を変えると思考の深さも一緒に動きます（`REF-032`）。
  段階と effort を同時に変えると、どちらが効いたのか分からなくなります。

## 限界

- 上の式は、失敗が 1 回で済み、やり直しの費用が上位モデル 1 回ぶんに等しいという粗い仮定です。
  `p` は自分の作業の種類ごとに測らないと分かりません。
- **ここに書いた価格・既定値・段階の構成は、確認した時点のものです。** 比の桁を示すために載せており、
  判断に使うときは公式の一覧を引き直してください。
- 入口の記事（`ART-028`）は 1 人の環境での実測で、対象の製品もプランも限定されています。採ったのは
  段取りと「自分で確かめられるか」という基準で、数値は自分の環境のものに置き換えます。
- 役割分けの数値（`REF-034`、`ART-029`）は提供元の自己申告で、ここでは再現していません。採ったのは
  構成（別の文脈を持たせて指示と結果だけを交換する、弱い側に計画を渡さない）と、その数値の読み方です。
- 生成しないモデルの話（`REF-110`、`REF-108`）も、この環境では測っていません。採ったのは向きと、
  確率を閾値に使う前に自分で測るという条件だけです。数値は移していません。
- `REF-100` は一般的な機材での評価で、著者ら自身が専用の機器へは一般化できないと断っています。
  対象は学習後に行う量子化だけで、ほかの圧縮手法は含みません。採ったのは向きと頭打ちの位置で、
  個別のモデルや方式の優劣は移していません。
