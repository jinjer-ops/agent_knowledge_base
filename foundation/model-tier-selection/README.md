# どの段階のモデルで始めるか

**この手引きはこの環境で実測していません。** 価格と既定値は公式の一覧で確認した時点の値で、
採否は自分の環境で計算し直します。状態は `experiment` です。特定の段階へ下げることを勧めるもの
ではありません。

[../token-drain-review/](../token-drain-review/) は原因探し、
[../heavy-read-delegation/](../heavy-read-delegation/) は重い読み取りの逃がし先、
[../cost-change-evaluation/](../cost-change-evaluation/) は入れた変更の判定です。ここはその前、
**作業を始める段階で、どの段階のモデルを選ぶか**を扱います。

## よくある勧め方と、その前提

「まず安いモデルで試し、進まなければ上げる」という段取りはよく見かけます（`ART-028`）。
その記事の実測では、1 つの作業あたりの費用が最も安い段階で約 $0.07、中間で約 $0.72、
上位で約 $7.60 でした。**上下で 100 倍近い開き**があり、この比なら安い方から試す価値は大きい。

ただしこの前提は提供元によって変わります。別の提供元の公式の一覧では、同じ時点で
100 万トークンあたりの単価が最上位 $10 / $50、中位 $4 / $20、最小 $1 / $5 で、
**上下の差は 4〜10 倍**です（`REF-032`）。桁が 1 つ違えば、同じ段取りの損得も変わります。

## 損得は、価格比と一発成功率で決まる

上位モデルの単価を 1、安い段階をその **1/r**、安い段階で一発で終わる割合を **p** とすると、
失敗したときは上げ直して払い直すので、1 作業あたりの期待費用はおよそ次になります。

```
1/r + (1 - p) × 1      （上位でそのままやれば 1）
```

得になる条件は **p > 1/r**。つまり:

| 価格比 r | 安い段階で必要な一発成功率 |
| --- | --- |
| 100 倍 | 1% を超えれば得 |
| 10 倍 | 10% を超えれば得 |
| 4 倍 | 25% を超えれば得 |

**r が小さいほど、安い段階の成功率が効く。** 粗い見積もりですが、方向を間違えないためには十分です。
やり直しには文脈の作り直しと人の時間も乗るので、実際の損益分岐は表より厳しくなります。削ったのに
総額が増える形は、別のテーマでも測られています（[../cost-change-evaluation/](../cost-change-evaluation/)）。

## 下げる前に、下げ方は 1 つではない

公式が挙げている手段のうち、モデルの段階を下げるのは一部です（`REF-027`）。

| 手段 | 効く場面 |
| --- | --- |
| 作業に合わせて段階を選ぶ | 難しい設計判断と、定型の作業を同じ段階でやらない |
| **下位エージェントだけ小さいモデルにする** | 冗長な出力を別の文脈へ出す作業。宣言でモデルを個別に指定できる（`REF-026`） |
| 思考の深さ（effort）を下げる | 深い推論が要らない作業。**既定の値はモデルごとに違う**（`REF-032`、`REF-013`） |
| 作業の切れ目で履歴を切る | 長い文脈の再送が効いている場合 |
| 同じことが CLI でできるなら CLI | 常時の占有を無くす |

**本体の段階を下げるのは、このうち最も影響が大きい選択です。** ほかの手段で足りるなら先にそちらを
試し、下げるかどうかは[判定の手順](../cost-change-evaluation/)で費用と品質を同時に見てから決めます。

## 自分で確かめられる作業かどうかで分ける

入口の記事が出している基準は、価格より使えます。**結果を自分で確かめられる作業**（差分が読める、
テストが通るかで判定できる、出力が短い）なら、安い段階の失敗は安く済み、気づける。確かめられない
作業（調査の結論、設計の判断、安全性に関わる修正）では、安い段階の失敗は気づかれないまま下流へ
流れます。段階を分ける線は、費用ではなく**検証のしやすさ**に引きます。

これは委譲の線引きとも一致します。要約だけを受け取る構成で推論を委譲できないのは、戻ってきた
要約の正しさを確かめられないからでした（[../heavy-read-delegation/](../heavy-read-delegation/)）。

## 名前・価格・既定値は引き直す

- **モデルの一覧と価格は公式の現在の表を正本にします**（`REF-032`）。記事の表も、手元に置いた
  控えも、書かれた時点のものです。段階の名前自体が入れ替わることもあります。
- **課金の単位も提供元で違います。** ある提供元は要求の件数で数え、モデルごとの倍率と月の割り当てが
  あり、超過は 1 件いくらで課金されます（`REF-033`）。トークン単価で書かれた記事の数字を、
  件数で課金される環境へそのまま持ち込むことはできません。**まず自分の請求の単位を確かめます。**
- **既定の effort はモデルごとに違う**ので、段階を変えると思考の深さも一緒に動きます（`REF-032`）。
  段階と effort を同時に変えると、どちらが効いたのか分からなくなります。

## 限界

- 上の式は、失敗が 1 回で済み、やり直しの費用が上位モデル 1 回ぶんに等しいという粗い仮定です。
  `p` は自分の作業の種類ごとに測らないと分かりません。
- **ここに書いた価格・既定値・段階の構成は、確認した時点のものです。** 比の桁を示すために載せており、
  判断に使うときは公式の一覧を引き直してください。
- 入口の記事（`ART-028`）は 1 人の環境での実測で、対象の製品もプランも限定されています。採ったのは
  段取りと「自分で確かめられるか」という基準で、数値は自分の環境のものに置き換えます。
