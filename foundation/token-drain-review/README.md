# 自分の入力以外で枠が減る分を点検する

**この手順はこの環境で実行していません。** 使うコマンドは対話の中で動くもので、ここでは公式資料に
書かれた内容と版の要件を確認しただけです。状態は `experiment` で、出てくる数字は自分の環境で
見てから判断します。

扱うのは「作業量の感覚より早く枠が尽きる」ときの原因探しです。指示ファイルを短くする作業は
[../instruction-upkeep/](../instruction-upkeep/)、1 回ごとの大きい読み取りは
[../heavy-read-delegation/](../heavy-read-delegation/) にあります。ここはその手前、**どこに原因が
あるかを先に当てる**ための順序です。

## 順序を間違えない

1. **割り当てを見る。** 購読の計画では、直近の使用が skill・下位エージェント・プラグイン・MCP
   サーバーごとに割り当てられ、それぞれの割合が出ます。全体の 10% 以上を占める振る舞い（長い文脈、
   キャッシュミスなど）には印が付きます。定期実行は重い順に行が出て、発火の間隔、実行回数、合計と
   1 回あたりのトークン、最後に走った時刻まで分かります（`REF-027`）。
2. **いま載っているものを見る。** セッション内の内訳表示で、何が context を埋めているかを見ます
   （`REF-017`）。
3. **そのうえで個別の設定を触る。**

逆からやると、効かない設定をいじって終わります。削る対象の分母を確かめずに手を付けても減らない、
というのは別のテーマでも同じ結論でした（[../heavy-read-delegation/](../heavy-read-delegation/)）。

数字は手元のセッション履歴から計算した概算で、ほかの端末や別の入口からの利用は入りません
（`REF-027`）。

## 触っていない間に減るもの

公式が挙げている、セッションを操作していなくても枠を使うものです（`REF-027`）。心当たりが
「設定の重さ」だけに向きがちな部分で、実際にはこちらの方が大きいことがあります。

| 原因 | 何が起きるか |
| --- | --- |
| 長い文脈 | 毎回の要求が会話全体を運ぶ。道具を使うたびに、その結果を載せた要求がもう一度出る |
| キャッシュミス | キャッシュの寿命を超えた最初の 1 通で全文脈を再処理する。寿命は購読で 1 時間、利用枠を超えた支払いや API では既定 5 分 |
| 定期実行 | 待機中でも間隔ごとに発火し、**そのたびに全文脈を送る** |
| セッション間の伝言 | 別のセッションからの伝言が、待機中に新しいターンとして届き全文脈を送る。保留にする設定がある |
| 目標の確認 | 背景の作業を待っている間、確認のターンが入る。回数の上限があり、環境変数で止められる |
| 背景処理 | 再開用の要約、状態確認、次の入力候補の生成など。概ね 1 セッションあたり少額 |

**止める前に、どれが効いているかを上の割り当てで見ます。** どれも既定のまま動くので、意識して
見に行かない限り気づけません。

## よくある 4 つの心当たりを、現行の仕様で検算する

公開記事でよく挙がる 4 項目（`ART-025`、`ART-026`）を、公式資料で確かめた結果です。**2 つは
そのまま正しく、1 つは現行版では前提が弱く、1 つはコマンド名が違います。**

| 心当たり | 現行の仕様 | すること |
| --- | --- | --- |
| 指示ファイルが毎回載る | 正しい。入口の指示ファイルは起動時に読み込まれ、関係のない作業中も載る。公式は 200 行未満を目安とし、作業ごとの手順は呼び出し式の skill へ移すよう勧める（`REF-027`） | 詳細は [../instruction-upkeep/](../instruction-upkeep/) |
| MCP を繋いでいるだけで食う | **現行では弱い。** ツール定義は**既定で遅延**され、実際に使うまでは**ツール名とサーバーの指示だけ**が載る（`REF-027`）。接続も、以前のセッションで取得した一覧が残っていれば初回利用まで先送りされる（`REF-028`） | まず内訳で実測する。使っていないサーバーは無効化し、同じことが CLI でできるなら CLI の方が常時の占有は無い（`REF-027`） |
| 定期実行が走り続ける | 正しい。しかも待機中でも全文脈を送る（`REF-027`） | 割り当ての行で頻度と 1 回あたりを見てから止める。この行には最低版の要件がある |
| skill の一覧が毎回載る | 正しい。ただし載るのは名前と説明だけ。**使用頻度と占有を出すのは設定診断のコマンドではなく、skill 専用の診断コマンド**で、最低版と機能フラグの取得が要る（`REF-029`） | 専用コマンドで使っていない skill を特定してから外す |

4 項目のうち 2 つが**そのままでは当たらない**という結果は、この種の記事の読み方そのものを示して
います。項目の着眼は妥当でも、製品の既定と手順の名前は版とともに動きます。

## 名前と版は動く

紹介されていたコマンドを打って何も出ないとき、まず疑うのは自分の設定ではなく、**名前が変わったか、
最低版に届いていないか**です。機能に最低版が付くこと、版が動くと設定が誤りにならないまま効かなく
なることは、別の点検でも確認されています（`ART-022`、`REF-029`）。記事に出てくるコマンド名は、
公式の一覧で引き直してから使います。

## 限界

- ここに書いたコマンドは実行していません。確認したのは公式資料の記述と版の要件だけです。
- 割り当ての数字は概算で、他端末の利用は含みません（`REF-027`）。
- 入口にした記事（`ART-025`、`ART-026`）は個人の点検記録で、測定値は示されていません。採ったのは
  「自分の入力以外にも消費元がある」という着眼と、点検する項目の並びだけです。
- 版の要件が付く機能は、ここに書いた番号ではなく公式資料の現在の記述を正本にします。
