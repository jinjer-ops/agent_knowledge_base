# 承認を外したとき、実際に残る境界はどれか

**この領域を開くとき**: 1 操作ごとの確認を出させるのをやめると決めたとき。自動承認のモードへ移す、
無人で（script や定期実行から）回す、あるいはその実行に**外から来る本文**（Web ページ、issue、ログ、
受け取った文書）を読ませるときです。

**この環境では運用検証していません。** 下に並べる層は、提供元の公開仕様と外部の実証から読み取った
内容です。設定も隔離も、ここで動かして確かめていません。道具の導入も勧めていません。

隣の領域との分かれ目は次のとおりです。[../autonomous-loop-delegation/](../autonomous-loop-delegation/) は
**何周分を人の確認なしで回させるか**、[../change-recovery-layers/](../change-recovery-layers/) は
**止まらなかったものをどこから取り戻すか**、[../secret-exposure-layers/](../secret-exposure-layers/) は
**秘密が外へ出る経路**です。ここはその手前にある別の問いで、**確認を外した後に、強制として残るのは
どの層か**を扱います。

## 強制される層と、最善努力の層を分ける

同じ「安全対策」として並ぶものの中に、**性質の違う 2 種類**が混ざっています。
分けずに数えると、層を 5 つ重ねたつもりで強制は 1 つも無い、という状態になります。

| 層 | 性質 | 何で決まるか |
| --- | --- | --- |
| 指示ファイル（正本の `AGENTS.md`、製品の入口ファイル） | **最善努力**。提供元自身が「規則を強制するのは製品であってモデルではない。プロンプトや指示ファイルの記述は、何を**試みるか**を変えるが、何が**許されるか**は変えない」と明記している（`REF-145`） | モデルの従い方 |
| `deny` の権限ルール | **強制**。どのモードでも効き、最も緩いモードでも効く（`REF-164`）。`allow` から例外を切り出せない（`REF-145`） | コマンド文字列・パスの照合 |
| `ask` の権限ルール | **強制**（確認を出す側）。判定モデルより先に評価され、自動承認でも必ず尋ねる（`REF-230`） | 同上 |
| 自動承認の判定モデル（分類器） | **最善努力**。提供元自身が「安全を保証しない」と書いている（`REF-164`） | 判定モデルの出力 |
| hook | 自前の論理で入力の全文を見られる。ただし**サンドボックスの外**で、利用者の権限のまま動く（`REF-231`）。どのイベントなら止められるかはイベントごとに違う（`REF-020`） | 自分で書いた処理 |
| サンドボックス（OS の隔離） | **強制**。**コマンドの文字列に依存しない唯一の層**で、提供元自身が「文字列に依存しない強制が要るならこちら」と書いている（`REF-145`、`REF-231`） | OS の機構 |
| コンテナ・VM・egress 制限 | **強制**。製品の外側 | 実行環境 |

**文字列の照合には共通の穴があります。** 規則が見ているのは、モデルが書いたコマンドの文面です。
同じプログラムを別の書き方で呼べば当たりません。提供元自身が例を挙げており、`git push` を止める規則は
`git -C <dir> push` や `git -c <key>=<value> push` に当たらず、プログラムをパスで指定した場合や
`sh -c` の中に入れた場合も同じです（`REF-145`、`REF-230`）。だから提供元は、止める必要が本当にあるなら
**サンドボックス側と組にせよ**と書いています。

ここから、この領域の最初の結論が出ます。**自作の正規表現で危険なコマンドを弾く hook は、
サンドボックスの代わりにはなりません。** 書く価値が無いという意味ではなく、**同じ層ではない**という
意味です。hook は「自分がうっかり踏む経路」を減らしますが、書き方を変えられる相手には足りません。

## 自動の安全判定は、門ではない

自動承認のモードには、確認の代わりに**判定モデル**が立ちます。このモデルは、依頼の範囲を超える操作、
知らない宛先への送信、読み込んだ敵対的な内容に駆動された操作を止める、と説明されています（`REF-164`）。
構成は入念で、提供元の設定資料（`REF-230`）によれば、無条件の禁止・利用者の意図で解除できる禁止・
その例外・利用者の明示の意図、という 4 段の優先順位を持ちます。

それでも、**これを門として数えることはできません。** 根拠は 3 つあり、方向が揃っています。

1. **提供元自身がそう書いています。** 設定資料は「利用者の意図や分類器の設定にかかわらず決して
   実行させてはならない操作は、分類器が相談される前に止まる `deny` を管理設定に置け」と書き、
   モードの資料は「自動承認は確認を減らすが、安全を保証しない」と書いています（`REF-230`、`REF-164`）。
   つまり提供元の設計自体が、**強制の層と最善努力の層を分けています**。
2. **破られた実証があります。** 外部の研究者が、**「このページを要約して」という依頼 1 つ**から
   遠隔コード実行まで到達する連鎖を公開しました（`REF-232`、2026-08-26）。成功率は条件により
   60〜80%（各 5 回、著者自身が小標本と明記）。提供元はこれを仕様どおりと判定しています。
3. **自動の権限審査を持つ実装を横断した測定も、同じ向きです。** 6 つのエージェント実行基盤を対象に
   13 の攻撃目標を試した査読前の報告は、**自動の権限審査を備えた 3 つを含め、すべてで目標が達成された**
   としています（`REF-233`、要旨の範囲で確認）。

**提供元の評価値と、この実証は矛盾していません。** 公表されている「固定のシナリオ集合で成功率 0.00%」は、
その集合に対する結果です。研究者の連鎖はその集合に入っていないので、**0% と動く攻撃は同時に成立します**
（`REF-232`）。評価値の読み方として一般化できます。**ベンチマークの 0% は「破れない」ではなく、
「測った範囲では出なかった」です。**

もう 1 つ、設計に直接効く観測があります。同じ実証で、判定モデルは**マルウェアの起動を通したあと、
それを停止しようとしたコマンドを止めました**（`REF-232`）。止める側が常に安全な向きへ倒れる、という
仮定は置けません。

## 外から来た本文を読む実行では、読む経路と実行する経路が同じ

無人の実行に外部の本文を読ませる構成では、上の表に**入力の側**が加わります。実証された連鎖の形
（`REF-232`）から、製品に依存しない注意が 3 つ出ます。

- **道具を 1 つ塞いでも、別の道具へ移ります。** 連鎖は、Web 取得の道具が拒否された時点で
  シェルの取得コマンドへ移りました。取得の道具にドメイン許可を掛けることは、**経路を 1 本閉じた**だけで、
  同じ機械にある別の経路は開いたままです。提供元の資料も同じ注意を、`curl` や `wget` を `deny` で止めて
  から取得の道具へ許可ドメインを置き、**さらにサンドボックスの許可ドメインと組にせよ**という形で
  書いています（`REF-145`）。
- **取ってきたものの隣で、何かを実行しない。** 連鎖の核は、文字としての指示ではなく
  **言語の探索順序**でした。展開した先で自分が書いたスクリプトを走らせると、標準ライブラリと同じ名前の
  ファイルがその場にあれば、そちらが読まれます。取得物の置き場と実行の作業ディレクトリは分けます。
- **「自分で書いたコードだから安全」は成り立ちません。** 連鎖の中でエージェントは、渡された実行ファイルを
  正しく拒否し、**自分で復号器を書きました**。拒否は機能しており、それでも実行に至っています。

査読前の報告（`REF-233`）が、**実行基盤が備える持続的な目標と定期実行で再現した**と書いている点も
同じ向きです。定期実行は、攻撃者から見れば**こちらが毎回必ず読みに来る約束**です。

## 設定そのものを守る層

自動承認では、**設定ファイル自身が標的になりうる**という問いが出ます。ここは層が既にあります。

- 製品側に**保護パス**があり、設定ディレクトリ、シェルの起動ファイル、版管理の設定・hook などへの
  書き込みは、サンドボックスでは `allowWrite` に入れても開きません（`REF-231`）。
- ただし**最も緩いモードでは、保護パスへの書き込みの確認も飛びます**（`REF-145`）。
  保護は「確認が出る」形で実装されているので、確認を全部外すモードでは一緒に外れます。
- 判定モデルの設定には、**リポジトリの中に置かれた設定を読まない**という規則があります。理由が明示されて
  いて、取り込んだリポジトリやビルドの段が、自分で自分への許可を注入できてしまうからです（`REF-230`）。

最後の 1 行は、自分で門を作るときにそのまま使える一般形です。**判定する側は、判定される側が書き換え
られる場所から設定を読まない。** 作業対象のリポジトリに置いた設定で自分の門を緩められるなら、
その門は門ではありません。

**既定の集合を置き換える操作にも注意が要ります。** 判定モデルの規則一覧は、既定を引き継ぐ指定を
書かずに配列を置くと、**組み込みの規則が丸ごと消えます**（`REF-230`）。追記のつもりの設定が置換である、
という形は設定ファイル一般にあります。書いた後に、効いている規則を出力させて確かめます。

## 確かめる項目

この環境で未確認のものを含みます。順に見ます。

1. **今どのモードで動いているか。** 既定の開始モードは版で変わります（`REF-164`）。
   「自分は確認する設定のはず」を前提にしない。
2. **強制の層が 1 つでもあるか。** 指示ファイルと判定モデルしか無いなら、強制は 0 です。
   最低限、`deny` と `ask` は文字列の照合であっても強制側に入ります。
3. **OS の隔離がこの機械で使えるか。** Windows でそのまま動かす構成では**サンドボックスが使えません**。
   WSL2 では使えます（`REF-231`、`REF-161`）。使えないなら、**この表の「文字列に依存しない層」は
   空**だという前提で残りを組みます。
4. **無人の実行が外部の本文を読むか。** 読むなら、取得物の置き場・実行の作業ディレクトリ・
   egress・資格情報の見え方を先に決めます。研究者の助言も同じ 4 点です
   （隔離した環境で動かす、egress を絞る、監視する、home や鍵や資格情報を見せない。`REF-232`）。
5. **hook をどこで数えているか。** hook はサンドボックスの外で動きます（`REF-231`）。
   隔離の内側にあると数えていたなら、その数え方が誤りです。
6. **効いている規則を出力して確かめたか。** 設定を書いたことと、効いていることは別です。

## この入力で採らなかったもの

入口の記事（`ART-058`）は、個人・チーム・組織の 3 層に分けて 10 個の設定・hook・テストを並べています。
構成と問題設定は採りましたが、**代表にはしていません**。検証が 1 環境・1 版・対照なしであることに加え、
採否を決める 3 点——モードごとに何が強制で何が最善努力か、判定モデルを門に数えてよいか、
この OS に隔離の層が在るか——の根拠が、すべて一次情報と外部の実証の側にあるためです。

記事が置く**自前の正規表現 hook** も、上の表のとおり層が違います。同じ記事が挙げる
**設定の書き換え防止**は、保護パスという形で製品側に既にあります（`REF-231`）。
ただし最も緩いモードでは外れるので、記事の対処が無意味になるわけではありません。

## 限界

- ここで動かした設定は 1 つもありません。モード、`deny`、サンドボックス、隔離のいずれも未検証です。
- `REF-232` は個人の研究ブログで、成功率は各 5 回の小標本です。著者自身が普遍的な値ではないと
  書いています。採ったのは**連鎖の形**と、**判定モデルを境界に数えない**という結論だけで、
  数値は移していません。
- `REF-233` は査読前で、要旨の範囲でしか確認していません。対象の実行基盤名も採っていません。
  採ったのは「自動の権限審査があっても達成された」という向きだけです。
- モードの識別子、設定の項目名、保護パスの一覧、版の条件は製品に依存するので、ここには置かず
  [../claude-code/README.md](../claude-code/README.md) にあります。版で動くので、使う版の一次情報から
  引き直します。
