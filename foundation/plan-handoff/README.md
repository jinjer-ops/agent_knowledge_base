# 計画を立てる側と、実装する側を分ける

**読むとき**: 片方のエージェントに計画を書かせ、別のエージェント（別製品・別モデル・別セッション）に
その計画を実装させる構成を考え始めたとき。どの製品を選ぶかではなく、**何を受け渡し、どこで黙ってずれるか**を
扱います。ここに書いたことは公開資料から読み取った内容で、この環境では動かしていません。

同じ作業を 1 本のセッションで通すか分けるかは別の判断です。段階ごとにモデルの等級を選ぶ話は
[../model-tier-selection/](../model-tier-selection/)、何周分を人の確認なしで回させるかは
[../autonomous-loop-delegation/](../autonomous-loop-delegation/) にあります。

## 先に分けておく 2 つの問い

この構成には、混ざりやすい 2 つの主張が入っています。

| 主張 | いま言えること |
| --- | --- |
| **計画を先に作らせると良くなる** | 測られている。向きは正。ただし条件付き（下記） |
| **計画と実装を別の道具に割ると良くなる** | 測った資料を見つけられなかった。体験談の範囲 |

分けた構成を採る理由として使えるのは、いまのところ前者だけです。後者は、道具ごとの得手不得手が
あるという観察であって、比較ではありません。**前者の根拠で後者を正当化しない**ようにします。

## 計画が効く条件と、逆効果になる条件

計画の遵守そのものを体系的に測った資料があります（`REF-165`、2026-04、査読の記載なし）。
コーディングのエージェントを 4 つのモデル、2 つのベンチマーク、8 通りの計画条件で走らせたものです。
採れるのは次の 3 点で、数値は移していません（軌跡の件数は取得経路によって食い違ったため使いません）。

- **計画が無いと、訓練で身についた手順に戻る。** その手順はしばしば不完全か、特定の型に過剰適合している。
  つまり「計画を渡さない」は中立ではなく、見えない既定の計画を使わせることです
- **質の悪い計画は、計画が無いときよりも悪い。** 特に、モデル自身の解き方と噛み合わない段階を
  前半に差し込むと落ちる。ここが実務で効く一点です。計画を外から与える構成は、**上振れと同時に
  下振れも作ります**
- **時間が経つと計画から外れる。定期的に計画を示し直すと、違反が減って成功率が戻る。**
  渡して終わりにせず、再提示の契機を手順に含めます

ここから出る設計は、「良い計画を 1 回渡す」ではなく、**計画が噛み合っていないと分かったときに
捨てられる経路を、渡す側と実行側の両方に用意する**ことです。実行側が「この計画では解けない」と
言える停止条件は、決定が足りないときの停止とは別物として用意します。

## 受け渡す器を、製品機能の外に置く

計画を別の道具へ渡すなら、**その計画がファイルとして存在するか**を先に確かめます。公開資料で
確かめた範囲では、製品の計画機能はどちらも自分の中で閉じています（確認日 2026-10-13）。

| 事項 | Claude Code の plan mode (`REF-164`) | Antigravity の artifact (`REF-163`) |
| --- | --- | --- |
| 計画の作られ方 | 調査して計画を提示し、編集はしない | planning mode で Markdown の計画などを作る |
| 人の関わり方 | 承認／却下を選ぶ。`Ctrl+G` で既定のエディタに開いて直接直せる | 節目で確認し、文面へのコメントで誘導する |
| ディスクのファイルになるか | **記載なし** | **記載なし** |
| 承認した後 | **同じセッションがそのまま編集側へ移る** | 記載なし |

つまり、**「計画を Markdown ファイルで受け渡す」は、製品の計画機能が自動で与えてくれるものでは
ありません。** 分ける構成を採るなら、計画をリポジトリ内の普通のファイルとして書かせる手順を
自分で足します。器の置き場が決まれば、版管理・レビュー・再提示の経路がそのまま使えます。

### 計画の段階に、編集されない保証はない

`REF-164` は、対話端末で bypass permissions が使える構成では **plan mode のブロックが効かない**と
明記しています。モデルは計画するよう指示されたままですが、その間に試みた編集やコマンドは
確認なしで実行されます。「計画の間はディスクが変わらない」を前提に置くなら、**どの許可構成で
走らせるか**まで込みで決めます。前提にできないなら、止める側は指示ではなく仕組みに置きます
（`REF-001`）。

## 大きい文脈窓は、計画の代わりにならない

分ける構成の理由として「実装側は窓が大きいのでリポジトリ全体を見られる」が挙がることがあります。
この読み替えは測定と合いません。

- 入力の長さだけを増やし、課題の難しさを一定に保った測定で、**調べた全モデルが長さとともに落ちます**
  （`REF-166`）。紛らわしい情報は 1 つ入るだけで落ち、増えると加速します。探している物と問いの
  意味的な近さが低いほど、落ち方が早くなります
- より新しい測定は、長い文脈で動くエージェントに **早期終了** という別の故障を見ています
  （`REF-167`、2026-06、査読の記載なし）。窓を使い切る前に諦める、または自信の無い誤答を返す割合が、
  文脈長と正の相関を持つ、というものです。**出力は「見つかりませんでした」の形で返るため、
  見落としとして気づきにくい**のが厄介な点です

どちらも限界があります。`REF-166` は課題を意図的に単純化しており、対象モデルの世代が古く、
いま 100 万トークン級をうたう製品を含みません。`REF-167` は対象モデル名を明示していません。
したがって採るのは**向きだけ**です。それでも設計に効く結論は変わりません。**窓の大きさは
「入れてよい量」であって「見える量」ではない**ので、実装側に渡す文脈は、窓に入るかではなく
**その作業に要る分か**で絞ります。計画は、その絞り込みそのものです。

## 道具をまたぐなら、常時の指示の正本も合わせる

計画だけを渡しても、作業の約束（守ってほしい規約、触ってよい範囲、禁止する操作）が実行側に
無ければ意味がありません。この層はツール非依存の `AGENTS.md` へ寄せます。置き方と各製品が読む条件は
[../agents-md/](../agents-md/) にまとめました。分ける構成で追加になるのは次の 2 点です。

- **受け渡しの約束そのものを正本へ書く。** 「実行を始める前に有効な計画を読む」「許可された範囲の外を
  触らない」「計画で決まっていないことを推測しない」は、どの道具で実行しても同じです。
  実行側の入口ファイルに書くと、道具を増やすたびに写すことになります
- **ただし、指示は強制ではありません**（`REF-001`）。禁止操作のうち必ず止めたいものは、
  実行側の仕組み（hook など）に置きます。正本に残すのは、判断や例外を伴う側です

## 導入前に確かめること

1. 計画が**ファイルとして残る**手順になっているか。製品の計画画面の中だけで完結していないか
2. 実行側が、計画が噛み合わないときに**止まれる**か。決定不足で止まる条件とは別に用意したか
3. 長い作業で、計画を**示し直す契機**があるか（`REF-165`）
4. 計画の段階で編集が走らない構成か。走りうるなら、止める側を仕組みに置いたか（`REF-164`）
5. 実行側に渡す文脈を、窓の大きさではなく作業に要る分で絞ったか（`REF-166`、`REF-167`）
6. 作業の約束が正本側にあり、実行側の道具を増やしてもそのまま効くか（[../agents-md/](../agents-md/)）
7. 各製品の常時の指示に**上限と切り詰め**があるか。正本が途中で切れていないか
   （[../agents-md/](../agents-md/) の上限の節）

## この構成の出どころ

入口になった記事（`ART-047`）は、計画を書かせる道具と実装させる道具を割り、受け渡し物を
Markdown の計画にするという構成を示しています。採ったのはその構成と着眼だけです。記事は
個人の使用経験で、対照も測定もありません。記事が挙げる文脈窓のトークン数と同時に動かせる
エージェントの本数は、当該製品の公開資料で確認できなかったため、ここには持ち込んでいません。
