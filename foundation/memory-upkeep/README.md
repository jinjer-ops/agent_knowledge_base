# 自動の記憶の棚卸し

人が書いた指示ファイルを軽くする話は [../instruction-upkeep/README.md](../instruction-upkeep/README.md) にあります。ここは別の対象、**エージェント自身が書いた記憶**を扱います。長さではなく**正しさ**が問題になる点が違います。

## 何が違うのか

自動の記憶はリポジトリ単位で保存され、索引になるファイルと話題別のファイルに分かれます。毎 session 読まれるのは索引の先頭一定量だけです（`REF-001`）。指示ファイルから個人の観察や経緯を追い出す先がここなので（`REF-012`）、指示ファイルを軽くするほど、この層に中身が溜まります。

溜まった中身は古くなります。**古い記憶は、無いより悪い**というのが要点です（`ART-012`）。空なら調べ直しますが、古い記述が残っていると、それを前提にして自信を持って動きます。

## 気づけない、という前提から始める

「おかしくなったら気づくだろう」は成り立ちません。独立したベンチマークでは、記憶が無効になった場面を扱わせたとき、全体の正答率は最良のモデルでも 55.2%、多くは 25% 未満でした（`REF-019`）。内訳が示すのは次の3つです。

| 観測 | 運用への意味 |
| --- | --- |
| 直接「これはまだ有効か」と問えば高い確率で気づくのに、**問いが古い前提を含んでいるとそのまま乗る**（同じモデルで 92% → 30%） | 通常の作業の中で気づくことは期待できない。棚卸しは**別の活動として明示的に**行う |
| 古いと**認識できても、後続の判断に反映できるとは限らない**（76% → 39%） | 「これは古い」と注記して残すのは対策にならない。保管へ移すか消す |
| 1つの事実を更新しても、**それに依存する記述は古いまま残る** | 1件直したら、その前提に依存している記述も併せて見る |

## 手順

`ART-012` の順序をそのまま使えます。

1. **退避する。** 先に丸ごと控えを取る。
2. **測る。** 索引の行数とバイト数（読み込みの上限に対する割合）、ファイル数、1件あたりの長さ、種類の分布、更新日の無いもの。
3. **外の事実と突き合わせる。** ここが中核です。参照している課題や変更要求の状態を実際に引き、参照先ファイルの実在を確かめます。**製品に組み込まれた整理機能はここを見ません**（`ART-012`）。内部の重複や長さは直せても、「外の世界が変わったこと」は外を見ないと分かりません。前の節の「古い前提に乗る」が、そのまま機械側にも当てはまります。
4. **分類する。** 下の表で分ける。
5. **小分けで承認を取る。** 「まとめて全部やっていいか」と聞かない。まとめて聞くと、判断を1つずつ見ないまま通ります。
6. **反映して報告する。** 消さずに保管用の場所へ移し、前後の数を残す。

## 残すか、移すか

| 中身 | 扱い |
| --- | --- |
| 済んだ作業、条件が満たされた注意書き | 保管へ。**前提が偽になった記述が一番危ない** |
| 重複・ほぼ同じ内容 | 1つにまとめる |
| 参照先の無いリンク | 索引から外す |
| git・コード・課題管理から引き直せる情報 | 維持費の方が高い。消す候補 |
| **引き直せない知識**（好み、その判断に至った理由、落とし穴の場所） | **残す。ここが本体** |
| 全員に効く規則・歯止め | 個人の記憶ではなく共有の規則の層へ移す |
| 索引の1行が長いもの | 話題別ファイルへ畳み、索引は呼び出しの手がかりだけにする |

削除ではなく移動を既定にします。消すと、なぜ消したかが次の人に残りません。

## やりすぎない

- 頻度は設計対象です。目安は月1回程度で、**上げすぎると圧縮のたびに詳細が落ちます**（`ART-012`）。
- 未確認の推測を確定事項として書き戻さない。確かめていないものは確かめていないと書きます。
- 管理の手間が効果を上回るなら、記憶の仕組みを使わない選択もあります。`ART-012` の筆者自身が最後にその可能性に触れています。棚卸しが続かないまま古い記憶を抱えるより、切ったほうが安全です。
