# 自動の記憶の棚卸し

人が書いた指示ファイルを軽くする話は [../instruction-upkeep/README.md](../instruction-upkeep/README.md) にあります。ここは別の対象、**エージェント自身が書いた記憶**を扱います。長さではなく**正しさ**が問題になる点が違います。

## 何が違うのか

自動の記憶はリポジトリ単位で保存され、索引になるファイルと話題別のファイルに分かれます。毎 session 読まれるのは索引の先頭一定量だけです（`REF-001`）。指示ファイルから個人の観察や経緯を追い出す先がここなので（`REF-012`）、指示ファイルを軽くするほど、この層に中身が溜まります。

**この層には、放っておいても減る経路がありません。** 会話の記録には保存期間があって自動で消えますが、
記憶のファイルはその掃除の**対象外**で、人かエージェントが書き換えるか消すまで残ります（`REF-001`、
確認日 2026-10-28）。古い記述が自然に落ちることはない、というのがこの作業を別途やる理由です。

範囲も先に確かめます。記憶は**リポジトリ単位**で、同じリポジトリの worktree は同じものを共有します。
一方で**機械の外には出ません**。別の機械やクラウド側の実行環境は、同じリポジトリでも別の記憶を持ちます。
下位エージェントも既定では親の記憶を読まず、自分の記憶を持たせた場合はそれが**別の棚卸し対象**になります
（`REF-001`）。棚卸しを「1 回やれば終わり」と数えないのは、このためです。

索引と話題別ファイルの役割分担も、ここから決まります。話題別ファイルは起動時には読まれず、
必要になったときに読まれます（`REF-001`）。だから索引の 1 行は**要約ではなく、呼び出しの手がかり**です。
そこに内容を詰めると、上限に当たって後ろが載らなくなるうえ、詰めた分を毎回払います。
上限の形と、黙って欠ける 3 通りの経路は [../claude-code/README.md](../claude-code/README.md) にまとめてあります。

溜まった中身は古くなります。**古い記憶は、無いより悪い**というのが要点です（`ART-012`）。空なら調べ直しますが、古い記述が残っていると、それを前提にして自信を持って動きます。

## 気づけない、という前提から始める

「おかしくなったら気づくだろう」は成り立ちません。独立したベンチマークでは、記憶が無効になった場面を扱わせたとき、全体の正答率は最良のモデルでも 55.2%、多くは 25% 未満でした（`REF-019`）。内訳が示すのは次の3つです。

| 観測 | 運用への意味 |
| --- | --- |
| 直接「これはまだ有効か」と問えば高い確率で気づくのに、**問いが古い前提を含んでいるとそのまま乗る**（同じモデルで 92% → 30%） | 通常の作業の中で気づくことは期待できない。棚卸しは**別の活動として明示的に**行う |
| 古いと**認識できても、後続の判断に反映できるとは限らない**（76% → 39%） | 「これは古い」と注記して残すのは対策にならない。保管へ移すか消す |
| 1つの事実を更新しても、**それに依存する記述は古いまま残る** | 1件直したら、その前提に依存している記述も併せて見る |

## 手順

`ART-012` の順序をそのまま使えます。

1. **退避する。** 先に丸ごと控えを取る。
2. **測る。** 索引の行数とバイト数（読み込みの上限に対する割合）、ファイル数、1件あたりの長さ、種類の分布、更新日の無いもの。
3. **外の事実と突き合わせる。** ここが中核です。参照している課題や変更要求の状態を実際に引き、参照先ファイルの実在を確かめます。**製品に組み込まれた整理機能はここを見ません**（`ART-012`）。内部の重複や長さは直せても、「外の世界が変わったこと」は外を見ないと分かりません。前の節の「古い前提に乗る」が、そのまま機械側にも当てはまります。
4. **分類する。** 下の表で分ける。
5. **小分けで承認を取る。** 「まとめて全部やっていいか」と聞かない。まとめて聞くと、判断を1つずつ見ないまま通ります。
6. **反映して報告する。** 消さずに保管用の場所へ移し、前後の数を残す。

## 残すか、移すか

| 中身 | 扱い |
| --- | --- |
| 済んだ作業、条件が満たされた注意書き | 保管へ。**前提が偽になった記述が一番危ない** |
| 重複・ほぼ同じ内容 | 1つにまとめる |
| 参照先の無いリンク | 索引から外す |
| git・コード・課題管理から引き直せる情報 | 維持費の方が高い。消す候補 |
| **引き直せない知識**（好み、その判断に至った理由、落とし穴の場所） | **残す。ここが本体** |
| 全員に効く規則・歯止め | 個人の記憶ではなく共有の規則の層へ移す |
| 索引の1行が長いもの | 話題別ファイルへ畳み、索引は呼び出しの手がかりだけにする |

削除ではなく移動を既定にします。消すと、なぜ消したかが次の人に残りません。

## 棚卸しのしやすさは、書き方の段階で決まっている

上の表は、**1 件を見れば分類できる**ことを前提にしています。その前提が成り立つかどうかは、
棚卸しの時点ではなく**書いた時点**で決まります。

記憶を項目として持つ構成と、文章のまま貯めて検索する構成を比べた報告（`REF-048`）が、この点を
扱っています。設計思想は「解釈を**読む側から書く側へ移す**」ことで、項目として持つと答えられる
ようになるものの中に、棚卸しに直結する 2 つが挙がっています。

- **更新と削除。** 「これは置き換えられた」「これはもう無い」を、文章の言い回しではなく
  値として表せる。上の表の「前提が偽になった記述が一番危ない」は、裏を返せば
  **偽になったことを書ける場所が無い**という問題です。
- **明示的な不明。** 「確かめていない」を、書かれていないことと区別して残せる。
  前の節の「未確認の推測を確定事項として書き戻さない」を、形の側から支えます。

この報告は査読前で、評価も著者ら自身によるものです。**数値は採りません。** 採るのは、
**棚卸しが続くかどうかは、1 件ごとに種類・根拠・状態を書く欄があるかで変わる**という向きだけです。

実務上は、記憶の仕組みにもともとある項目（名前、呼び出しの手がかりになる説明、種類）を
きちんと埋めることがそのまま備えになります。新しい欄を増やす前に、既にある欄が埋まっているかを
見ます。欄を増やしすぎると埋まらなくなるのは、抽出の側でも測られている失敗です
（[../retrieval-structure-decision/](../retrieval-structure-decision/)）。

## 積むほど良くなる、わけではない

ここまでは「古くなったものを直す」話でした。別の問題があります。**記憶が正しくても、量そのものが害になります。**

継続的に記憶を更新させる設定を対照付きで測った報告（`REF-068`、査読前）が観測しているのは、
**有用性がいったん上がり、その後下がって、記憶を持たない場合の水準を下回りうる**ことです。
同じ報告は、溜まったものを要約してまとめ直す処理が、モデルが依拠していた証拠そのものを
上書きしうるとし、**まとめ直さずに実行の記録をそのまま残すだけの対照が、まとめ直す側より良かった**
場合を挙げています。査読前で、環境も限られているため、採るのは向きだけで数値は移しません。

実務上の規則は 2 つです。

- **まとめ直しを既定の作業にしない。** 量が増えたからという理由だけで要約させない
- **「残すだけ」を常に対照として持つ。** 手を入れた側が、入れない側に勝っているとは限らない

## 書き足す形と、書き直す形は別物

同じ問題を、文脈を育てる側から扱った研究があります（`REF-067`、ICLR 2026）。
蓄積を壊す様式に名前が付いています。

| 様式 | 何が起きるか |
| --- | --- |
| **簡潔さへの偏り** | 短くまとめる最適化を重ねると、その環境でしか分からない詳細から先に落ちる |
| **文脈の崩壊** | 全体を書き直させる形を繰り返すと、積み上げた中身が目減りする |

提案されている形は、**全体を書き直させず、差分の項目として足し、重複だけを定期的に刈る**ことです。
書き直しを避けるのが崩壊への対処、刈る対象を重複に限るのが偏りへの対処、という対応になっています。

報告されている改善幅はここで再現していないので採りません。採るのは
**書き足す形と書き直す形を区別する**という点だけです。[上の表](#残すか移すか)が削除ではなく
移動を既定にしているのも、同じ理由で説明がつきます。

## 効いたかどうかは「記憶なし」と比べる

記憶の仕組みの評価を並べて調べた報告（`REF-069`、査読前）は、比較の作り方に共通の欠陥があると
指摘します。記憶の方式を変えると同時にモデル・埋め込み・検索経路も動いており、
**何を測ったのかが分からない**。そのうえで、**書き込み側の費用を報告してから、利得を構成に
帰属させるべき**だとしています。

棚卸しに引き写すと、こうなります。

1. 比べる相手を**記憶なし**に固定する。前の版の記憶とだけ比べる形では、`REF-068` が示した
   下り坂に入っていても気づけません
2. 一度に変えるのは 1 つ。記憶の中身と、読み込ませ方と、モデルを同時に変えない
3. **書く側の手間も数える。** 棚卸しそのものの費用を勘定に入れないと、効いたように見えます

## 軽くする理由に、費用を使わない

索引を削ると毎回の読み込みが減るので、費用のための作業だと読まれがちです。**その読み方は外れます。**

毎 session 同じものを先頭から読ませる構成は、繰り返しの部分が**割り引かれた単価**で課金されます。
提供元の一次情報では、この割引後の単価は通常の入力の**数分の一から数十分の一**で、
**どれだけ割り引かれるかはモデルによって違います**（`REF-225`、確認日 2026-10-28）。
つまり索引から一定量を削っても、浮くのは素のトークン数から想像する額のごく一部です。
入口の記事（`ART-056`）自身が、1 session の消費の大部分がこの割引後の読み込みだったと測っています。
**記事が挙げている割引の倍率は、その記事が使っているモデルの値です。** 別のモデルに持ち込めません。

さらに、**削った直後は一時的に高くつきます。** 割引は先頭からの一致で効くので、先頭を書き換えると
その回は効きません。小刻みに削る運用は、この書き直しの分を毎回払います。

残る理由は 2 つで、どちらも費用ではありません。

- **載らないものは効かない。** 索引の上限を超えた分は、安いのではなく**存在しません**
- **長いほど拾い落としが増える。** 長い文脈で指示の遵守が落ちることは、査読を経た評価でも
  扱われています（`REF-226`、Findings of EACL 2026）。同じ向きは
  [../instruction-upkeep/](../instruction-upkeep/) の「なぜ減らすのか」にもあります

したがって棚卸しの成果は、削ったトークン数ではなく**上限の内側に収まったか**と**挙動が変わったか**で
測ります。費用で測ると、効いていない作業を効いたと記録します。前後比較を差と呼んでよい条件は
[../cost-change-evaluation/](../cost-change-evaluation/) にあります。

## やりすぎない

- 頻度は設計対象です。目安は月1回程度で、**上げすぎると圧縮のたびに詳細が落ちます**（`ART-012`）。
  この現象には名前と測定が付いています（`REF-067` の「簡潔さへの偏り」）。
- 未確認の推測を確定事項として書き戻さない。確かめていないものは確かめていないと書きます。
- 管理の手間が効果を上回るなら、記憶の仕組みを使わない選択もあります。`ART-012` の筆者自身が最後にその可能性に触れています。棚卸しが続かないまま古い記憶を抱えるより、切ったほうが安全です。
