# 指示ファイルの棚卸し

指示ファイルは、追加するたびの判断が正しくても全体として膨らみます（`ART-015`）。ここでは、何をきっかけに見直し、何を残し、何を測るかを扱います。置き場所そのものの判断は [../agents-md/README.md](../agents-md/README.md) にあります。

## きっかけ

- 起動時に、指示ファイルが推奨の長さを超えたという警告が出たとき（`REF-001`）
- モデルや製品の版が上がったとき。**古い版の弱点を埋めるために書いた指示は、新しい版では足かせになります**（`REF-012`）。版が動くと設定が静かに外れることもあります（下の節）
- 相反する指示に気づいたとき。矛盾した指示があると、どちらが採られるかは決まりません（`REF-001`）
- 定期の点検。頻度そのものが設計対象で、やりすぎると必要な詳細まで失われます（`ART-012`）

## まず組み込みの点検を使う

自分で点検の仕組みを作る前に、製品に用意された点検を試します。Claude Code には、指示ファイル一式を対象に、古い記述・存在しないファイルへの参照・相反する内容を探して**提案だけを出し、承認するまで書き換えない**点検があります。対象には指示ファイルのほか、rules・skills・subagent なども含まれます。長すぎるファイルに対して削る候補を出す点検も別にあります。いずれも最低版があるので、使えない場合は版を確認します（`REF-001`）。

同じことをする仕組みを自作すると、製品側の改善から取り残されます。組み込みの点検で足りない部分だけを補います。

## 何を残し、何をどこへ移すか

| 分類 | 例 | 扱い |
| --- | --- | --- |
| そのリポジトリ固有の落とし穴 | 使えない既定値、壊れやすい前提、既定と違う規約 | **残す。最も価値が高い** |
| ファイルを見れば分かること | ディレクトリ構成、依存一覧、概要 | 外す。読めば分かることを書かない（`REF-001`） |
| 禁止の列挙 | 「必ず〜」「絶対に〜しない」 | **判断の基準に書き換える。** 取り返しのつかない操作の歯止めだけ残す |
| 手順 | 公開手順、リリース手順 | 呼び出し式の層（skill）へ移す |
| 個人の観察・経緯 | 過去の判断の記録、仕様の本文 | 自動の記憶や参照先の文書へ移す（`REF-012`） |

書き換えの型は、提供元自身が行った置き換えがそのまま例になります。「コメントを書くな、最大1行」という禁止を、「周囲のコードに合わせる。コメントの密度・命名・書き癖をそろえる」という判断の基準に替えています（`REF-012`）。禁止を数える代わりに、判断に必要な材料を渡す形です。

## 版が上がったときに静かに外れる設定

点検の対象は指示ファイルだけではありません。**モデルの版が動くと、設定が誤りにならないまま効かなくなる**ことがあります。エラーは出ず、挙動だけが変わります。確認した仕組みは次のとおりです（`REF-013`）。

| 仕組み | 版が動いたときに起きること |
| --- | --- |
| 短い別名で指定している | 別名は推奨の版を指し、**時間とともに指す先が変わる**。固定したいなら完全な名前か、専用の環境変数を使う |
| モデルごとの設定 | **完全なモデル名を鍵にする**。別名の指す先が変わると、古い名前で書いた設定はどれとも一致せず、黙って適用されなくなる |
| 深さ（思考量）の設定 | 「明示の指定 → 設定ファイル → モデルごとの既定」の順で決まる。**既定の値は版ごとに違う**。つまり上の行で設定が外れた瞬間、新しい版の別の既定へ落ちる。二段で静かに変わる |
| 版に依存する環境変数 | 新しい版では効かないものがある |
| 新しい版の利用条件 | 製品側に最低版の要件が付くことがある |

`ART-022` は、組み込みの点検を実際に回してこの種の食い違いを洗い出した記録です。設定の取り違えのほかに、条件に指定したファイルが既に消えていて一度も読み込まれないルールや、文書では削除済みとされている古い鍵が残っている例も見つけています。

**点検では、指示ファイルと並べて「モデル名を鍵にした設定」と「版に依存する指定」も見ます。** 確かめ方は、設定ファイルを読むことではなく、**実際に何が適用されているか**を見ることです。設定は正しく書かれていても、鍵が一致していなければ存在しないのと同じです。

## 測るのは行数ではなく常時読み込みの総量

ファイルを分けても、分けた先が常時読み込みなら総量は変わりません（`ART-003`）。取り込みは整理には役立ちますが、取り込んだ先も起動時に読み込まれるため消費は減りません（`REF-001`）。減らしたいなら、呼び出し式の層へ移します。

数えるのは、少なくとも次の合計です。

- 指示ファイル本体
- 条件を付けていないルール（対象を絞る指定があるものは、一致するファイルを扱うときだけ読み込まれる）
- 使える skill の**名前と説明**。本体は呼ばれるまで読み込まれませんが、説明は常に読まれます（`REF-002`）。まとめて配布する仕組みを有効にしている場合、その中身の名前と説明も毎回載ります（`REF-011`）

行数の目安を超えていなくても、合計で効いてきます。`ART-021` は、この合計を「常時読込の総面積」と呼び、点検の出力に含める構成を示しています。合計を自分の環境で測ってから、どこを削るか決めます。

## やりすぎない

- 既定は削除ではなく**置き場の変更**にします。移す先を先に決めておけば、追記そのものを断らずに本体を短く保てます（`ART-015`）。
- 点検の頻度を上げすぎると、必要だった詳細まで落ちます（`ART-012`）。
- 削った後は、同じ作業をやり直して結果が変わらないことを確かめます。確かめるまで「軽くできた」と扱いません。
