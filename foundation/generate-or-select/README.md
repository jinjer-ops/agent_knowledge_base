# 組み立てさせるとき、部品を生成させるか、用意した部品から選ばせるか

**この構成はこの環境で運用していません。** 根拠は 1 件の実装解説、1 件の公式資料、
1 件の査読済みの測定（ICML 2025）、2 件の査読前の測定、2 件の相反する検証です。
状態は `experiment` です。特定の製品の導入を勧めるものではありません。

起動条件は「**モデルに構造のある成果物（画面、設定、一連の手順、呼び出す道具の並び）を
組み立てさせると決めたとき、部品の中身まで生成させるか、人が先に用意した検証済みの部品から
選ばせるか**」を決める場面です。

隣の手引きとの違いは、決める対象です。

| 迷っていること | 読む場所 |
| --- | --- |
| すでにある 1 つの分岐を、判断専用の仕組みへ差し替えるか | [../typed-decision-gating/](../typed-decision-gating/) |
| 作らせる前に、見た目の正本として何を手元に持つか | [../design-asset-canon/](../design-asset-canon/) |
| 図そのものの正しさを、どう確かめるか | [../diagram-as-text/](../diagram-as-text/) |
| 計画を別のエージェントへ渡す形をどう組むか | [../plan-handoff/](../plan-handoff/) |

ここだけが、**組み立てさせる成果物の部品が、どこから来るか**を扱います。

## 3 つの置き方は、消せる失敗が違う

同じ「構造のあるものを出させる」でも、置き方によって消える失敗と残る失敗が分かれます。
ここが設計の分かれ目で、**何を消したいのかを先に決めないと置き方は選べません。**

| 置き方 | 消える失敗 | 残る失敗 | 払う代償 |
| --- | --- | --- | --- |
| 自由に書かせ、後から解析する | なし | 構文の失敗、中身の失敗 | 解析する側を自分で持ち続ける |
| スキーマ・文法で縛って生成させる | 構文の失敗 | 中身の失敗 | 途中で考える余地が狭まる |
| 用意した部品から選ばせる | 構文の失敗と、部品の中身の失敗 | **どれを選んだか**の失敗 | 候補の外にあるものは表せない |

入口の記事（`ART-055`）が採っているのは 3 番目です。カタログに部品の**型だけ**を置いて
モデルに値を書かせるのではなく、**具体的な値まで入った候補を先に作っておき、モデルには
選択と配置だけを任せる**。この移動で何が変わったのかを、以下で分けます。

## 「スキーマどおり」は「正しい」ではない

ここが最も取り違えやすい点です。入口の記事は利点として「出力の予測可能性が向上する」を
挙げていますが、**上がるのは構造の予測可能性**で、中身の正しさは別に残ります。

これを二軸に分けて測った資料があります（`REF-221`）。小さいモデルを複数系統・複数課題で、
制約あり・なしで比べ、**構造の適合（スキーマに合っているか）と意味の適合（中身が合っているか）を
別々に採点**しています。結果は、制約を入れると構造の適合は上限に張り付く一方、意味の失敗は
残り、しかも**救える失敗と救えない失敗が分かれる**というものでした。型の取り違えのように
形式の問題として現れるものは制約で消えますが、指示の意味に関わる失敗（複数の段を踏む
呼び出しなど）は制約では消えません。著者の結論は、スキーマへの適合は**必要だが十分ではない**、
というものです。

> **構造の適合率と、中身の正答率は、別々に測ります。** 片方だけを見ると、形式が揃った
> 間違いが「予測可能になった」と読めてしまいます。

## 制約が最初に削るのは「該当なし」

候補から選ばせる形を置くときに、これを知らないと設計を誤ります。

道具の呼び出しを選ぶ経路で、**何も呼ばないという答え（棄権）**がどうなるかを測った資料が
あります（`REF-222`）。中心の指摘は、文法の制約が**最も削りやすいのが「どれでもない」であり、
振り分ける側が最も失ってはいけないのもそれだ**ということです。制約によって「修復」された
出力を 1 件ずつ中身まで調べると、その大半は**元々読める答えが無かったもの**で、
**採点規則に弾かれていただけの正しい判断は 1 件も無かった**と報告しています。つまり制約が
したのは読める形にすることであって、判断を良くすることではありません。棄権の正答率自体は、
比較した条件の多くで下がっています。

ここから出る設計規則は 1 つです。

> **候補の集合に「どれでもない」「まだ決められない」を必ず置きます。**
> 選択肢に無いものは選ばれません。置かなければ、モデルは必ずどれかを選びます。

これは、この環境で既に使っている形と同じ向きです。構造化された結果を返させる処理で、
**判断できないことを表す値**（保留・要対応）を型の中に用意しておくと、材料が足りないときに
「それらしい答え」ではなく「決められない」が返ります。用意していなければ、同じ場面で
もっともらしい答えが返ります。

## 縛るほど良くなるわけではない

「制約を強くするほど出力が安定する」は成り立ちません。査読済みの研究（`REF-223`、ICML 2025）が、
**最終的な答えだけを許す厳しい文法に縛ると推論能力が落ちる**ことを理論と実験の両方で示し、
**文法に余地を足す**（途中を書ける規則を加える）ことで、記号推論の課題で制約あり・なしの
どちらにも勝ったと報告しています。

> **縛る対象は、最終的な答えの形だけにします。** 途中で考える場所まで閉じると、
> 閉じた分だけ判断が落ちます。

実装上、これは**項目の並び**として現れます。答えの欄を先に書かせる形にすると、考える前に
答えを決めさせることになります。理由や比較を先に置き、結論を後ろに置くと、同じ型のままで
余地が残ります。

## 反対の根拠：形式の代償は、測り方の問題かもしれない

この領域には、正面から割れている 2 件があります。**両方を残します。**

- 出力を厳密な形式に縛ると推論の質が落ちる、という測定（`REF-085`）。
- その測定に対する反論（`REF-224`）。プロンプトが条件間で揃っていない、スキーマを渡して
  いない、解析にモデルを使っている、JSON モードと構造化生成を混同している、という手続き上の
  指摘を挙げ、条件を揃えて測り直すと**構造化した側がわずかに上回った**と報告しています。
  さらに、元の論文自体が**分類の課題では構造化が勝っている**ことを示していた、と指摘します。

**ただし反論の側は、構造化生成の実装を公開している側が書いたもので、その旨の記載は記事に
ありません。** 記事自身も、対象を「構造に素直に乗る課題」に限ると断っています。

割れたまま使える向きは 1 つだけです。**有限の選択肢から選ぶ種類の課題では、形式を課す代償は
小さいか、無い。段階を踏んで考える種類の課題では代償が出る。** 入口の記事が扱っている仕事
（用意した候補の選択と配置）は前者の側にあり、だからこの構成は形式の代償を受けにくい位置に
あります。これは記事の主張を支持する向きですが、**記事がその理由を示しているからではなく、
別の資料がその条件を測っているから**です。

## 候補を用意する側に、仕事が移る

この構成で消える仕事と、増える仕事があります。

公式資料（`REF-220`、Apache-2.0）は、安全機構として**「AI は自分が定義した部品しか使えない」**を
挙げ、出力が常にスキーマに一致することを利点に置いています。これは正しいのですが、
**止まる範囲は「定義していない部品が出ること」まで**です。

- **止まる**：カタログに無い部品が現れること。構文が壊れた出力。
- **止まらない**：候補そのものの中身が間違っていること。間違った候補が選ばれること。
  候補に無い状況が来たときに、近いだけの候補が選ばれること。

したがって候補の集合が**品質の上限**になります。モデルに書かせていた部分が人の作業へ戻る
ので、候補は書く対象・確かめる対象として残り、場面が増えるほど数が増えます。**どこまでを
候補として持つかは、この増え方で決まります。**

## 確かめる順番

1. **消したい失敗を先に書く。** 構文か、中身か、選択か。3 つは別の対策で消えます。
2. **有限の選択肢に落とせるかを見る。** 落とせないものを無理に落とすと、候補の外の要求が
   近い候補に吸われます。
3. **候補に「どれでもない」を入れる**（上の節）。
4. **縛る対象を、最終的な答えの形だけにする**（上の節）。
5. **構造の適合率と中身の正答率を、別々に測る**（上の節）。平均を 1 つにまとめない。
6. **候補の外に出たい要求が何件来たかを数える。** これが候補集合を見直す唯一の根拠です。
   数えていなければ、候補が足りないことは誰にも分かりません。
7. **費用と速さは組み込んだ後の全体で測る。** 前後比較を差と呼んでよい条件は
   [../cost-change-evaluation/](../cost-change-evaluation/) にあります。

## 限界

- **この環境では動かしていません。** 上の手順も未検証です。
- `REF-221` と `REF-222` は査読前のプレプリントで、いずれも単著、対象は小さいモデルです。
  採ったのは二軸に分ける**枠組み**と、棄権が削られるという**向き**だけで、**割合・ポイント差は
  手引きへ移していません**（読書ガイドのカードに条件付きで残しました）。
- `REF-223` は査読済み（ICML 2025）ですが、対象は記号推論とコード生成です。**画面の組み立てを
  測ったものではありません。** 採ったのは「縛りを強くすることが改善とは限らない」という
  機構と向きだけで、提案手法は採っていません。
- `REF-224` は利害関係のある側の反論です（上の節）。向きの判断にのみ使いました。
- 入口の記事（`ART-055`）が使う判断器との連携は、記事自身が `experimental_` で始まる実験的な
  API だと断っており、**記事が挙げている無料提供の期限は、この手引きを書いた時点で既に
  過ぎています。** 価格・提供条件・API の仕様は、使うときの一次情報を引き直してください。
- `REF-220` の保守状況・版・実運用での評価は確認していません。**導入は勧めていません。**
  採ったのは、カタログが何を止めて何を止めないかという構成上の事実だけです。
- 判断専用モデルそのものの選び方（確信度の扱い、閾値、戻し先、速さの測り方）は、この手引きでは
  扱いません。[../typed-decision-gating/](../typed-decision-gating/) にあります。
