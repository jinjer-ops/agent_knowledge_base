# 学習データに無い言語・出たばかりの版で書かせるとき

**この手引きはこの環境で実行していません。** 根拠は公開された測定と提供元の一次情報で、
ここに書いたのは確かめる順序です。状態は `experiment` です。特定の言語や道具を勧めるものでは
ありません。

起動条件は「**出たばかりの言語・出たばかりの版・あまり使われていない言語で、エージェントに
コードを書かせると決めたとき**」です。

- [../model-tier-selection/](../model-tier-selection/) は、どの段階のモデルで始めるか。
- [../autonomous-loop-delegation/](../autonomous-loop-delegation/) は、機械判定できる検証がある
  範囲まで任せる、という**任せる長さ**の段。
- ここはその手前です。**その言語・その版に、機械判定の土台がそもそも在るか**を扱います。

## 入口になった事実

ある言語が 1.0 に到達した 1 週間後に、コンパイラとツールチェーンが寛容なライセンスで公開されました
（`REF-180`、`REF-181`）。標準ライブラリとカーネルは数年かけて先に公開されており、この発表で
残りが揃った形です。

ここで効くのは「公開された」ことではなく、**1.0 の中身が統合だった**ことです。変数宣言が 1 つの
キーワードに一本化され、クロージャの書き方が統一され、ポインタ型が 1 つにまとめられ、名称が多数
変更されました（`REF-181`）。提供元は 1.x では原則として追加だけにすると書いていますが、同じ文で
「それでも破壊的変更はありうる」と断っています。

つまり、**公開されている大量のコードと解説の多くは、今の版の言語ではありません。** そして
モデルが学習した時期の言語も、今の版ではありません。この構図は特定の言語の話ではなく、
新しい言語・大きな版更新・利用者の少ない言語で共通して起きます。

この入口はもう 1 つ条件を持ち込みます。その言語のネイティブ Windows 対応は「開発中」で、
**時期の表明がありません**（`REF-180`）。この環境は Windows なので、触るとすれば WSL 経由です。
これは好みの問題ではなく、後で出てくる「検証の土台が在るか」に直接効きます。

## 薄い言語は、2 つの別の失敗を同時に連れてくる

| 失敗 | 中身 | 気づき方 |
| --- | --- | --- |
| **存在しないものを書く** | 実在しないパッケージ・関数・型を、実在するかのように書く | レジストリ・コンパイラに引かせる |
| **存在するが版が違う** | 実在するが、指定した版には無い書き方を使う | その版で実行する |

この 2 つは原因も対処も違います。片方だけ塞いでも、もう片方は残ります。

## 1. 存在しないものを書く

査読を通った測定があります（`REF-182`）。16 のコード生成モデルに約 19,000 件の問いを与え、
Python と JavaScript で生成されたパッケージ名を公開レジストリと突き合わせたものです。

- 存在しない名前が出る割合は、商用のモデルで約 5%、公開重みのモデルで約 21%。
- 出てきた**実在しない名前はユニークで 205,474 件**。
- 内訳は、純粋な捏造が 51%、実在する 2 つの名前の混同が 38%、綴り違いが 13%。

ここまでは「ときどき間違える」という話に見えます。**この測定の価値は次の一点にあります。**

> 同じ問いを与え直すと約 45% が同じ名前で再現し、続けて 10 回聞くうちに約 60% が再び現れた。

**つまり「もう一度聞いて確かめる」は検出になりません。** 幻覚は乱数ではなく、その問いに対する
その模型の安定した出力です。言い換えれば、聞き直して同じ答えが返ってきたことは、存在の根拠に
なりません。

2026 年の前線モデル 5 つで同じ手順を繰り返した再評価もあります（`REF-183`、単著・査読の記載なし）。
率は 4.62%〜6.10% まで下がり、**モデル間の差はほぼ消えました**。率だけ見れば改善です。
ただし同じ再評価が、より厄介な性質を測っています。

> **5 つのモデルすべてが同一に発明した名前が 127 件**（PyPI に 109、npm に 18）あり、
> うち 53 件はレジストリ側の既存の防御を通り抜けて取得可能なままだった。

**別のモデルに聞いて一致しても、存在の根拠になりません。** 模型を変えることは独立した確認では
ないからです。ここが、この手引きで最も実務に効く一行です。

学習側で消す試みの結果も記録しておきます。幻覚の無いデータで微調整すると誤りは 8 割以上減りましたが、
**コードの品質そのものが落ちました**（`REF-182`）。この問題は、モデルの側だけでは閉じません。

### 対処

- 新しく出てきた依存名は、**レジストリか言語の公式索引で 1 回引く**。引けない名前は書かせない。
- 既にある依存一覧・ロックファイルに無い依存が増えたときだけ、人が見る（毎回ではなく、増分だけ）。
- 聞き直し・モデルの変更を、確認の手段として数えない。

## 2. 存在するが、版が違う

版の違いを実行で判定するベンチマークがあります（`REF-184`）。328 問の Python の課題それぞれに
ライブラリの版と単体テストが付いており、**どの版向けに書くかを指定した上で**解かせます。

結果は、最前線の構成でも**成功率 48〜51%**でした。版を文字で指定しても、半分は合いません。
これは知識が足りないというより、**指定された版の側へ書き分けられない**ということです。

ここから出る結論は 1 つです。**指示に版を書くことは対処ではありません。** 対処は、その版で
実際に動かして判定する経路を、書かせる前に用意することです。

## 3. 言語そのものの量が少ない場合

低資源の言語を扱う研究が、この問題の輪郭を示しています（`REF-186`、Julia・Lua・OCaml・R・Racket が対象）。
著者らは、潤沢な言語の訓練データを低資源の言語へ翻訳して学習データを作りましたが、その翻訳自体を
**定義からして信用できない**（モデルは低資源の言語が苦手なのだから）と書いています。

採った手段は、モデルの自信でも人の目視でもなく、**単体テストを生成して通らない翻訳を捨てる**こと
でした。この分野で低資源の言語を扱う足場になったのが実行結果だけだった、という事実がここでの
論点です。

## 効く梃子は、指示ではなく機械判定の層

型システムで復号を制約する手法が、**コンパイルエラーを半分以上減らしています**（`REF-185`、
HumanEval と MBPP、30B 超の公開重みモデルを含む複数の規模・系統）。この手法自体を導入する
話ではありません。採るのは**順序**です。

> この種の誤りの大半は、言葉の工夫ではなく、型検査・ビルド・テスト実行という機械の層で落ちる。

だから、薄い言語で書かせると決める前に確かめるのは、指示の書き方でもモデルの段でもなく、
**その言語・その版の検査器とテスト実行を、この環境で回せるか**です。回せないなら、
それはモデル選びの問題ではなく、**検証の土台が無いという問題**です。土台が無い状態は、
[../autonomous-loop-delegation/](../autonomous-loop-delegation/) が任せてよいと言っている
条件（機械判定できる検証がある）を満たしていません。

## この環境で確かめる順序

まだ回していないので、順序の候補だけを置きます。

1. **その言語の検査器とテスト実行が、この機械で動くか**を先に確かめる。動かないなら、
   書かせる前にそこを作るか、書かせない。
2. 動く場所が WSL や別の環境になるなら、**そこへ渡る途中で壊れる経路**を先に閉じる
   （改行・符号化・同期フォルダ: [../windows-file-hazards/](../windows-file-hazards/)）。
   検証の土台が壊れていると、検証結果が嘘になります。
3. **版を 1 つに固定**し、その版の公式資料を手元に引いてから書かせる。指示に版を書くだけでは
   足りないので、2 の経路で実行判定まで通す。
4. 出てきた**依存名を機械で引く**。増えた依存だけを見る。
5. 通らなかったときに、**エラー文をそのまま戻す**。自己修復の効き目は、戻す情報の質で決まる
   （[../review-design/](../review-design/)）。

## 限界

- ここに書いた測定はどれも**この環境で再現していません**。率も成功率も、判断の基準として
  持ち込んでいません。採ったのは向きと、確認の手段として何が成立しないか（聞き直し・モデルの一致）です。
- `REF-182` と `REF-183` が測ったのは **Python と JavaScript のパッケージ名**だけです。
  薄い言語ではもっと悪いだろうという推測は自然ですが、測られていません。ここでは、
  潤沢な言語ですらこの率が出るという事実だけを使っています。
- `REF-183` は単著で査読の記載がありません。確認したのは要旨の範囲です。採ったのは
  「モデル間で一致しても根拠にならない」という性質で、個々のモデルの順位は移していません。
- `REF-184` の緩和策（誤り文の差し戻し・検索・エージェント構成）の効果は、公開ページから
  確認できませんでした。ここでは基準値だけを使っています。
- `REF-185` について、一次情報のページで確認できたのは「コンパイルエラーを半分以上」という
  表現までです。二次的な要約にはベンチマーク別の削減率と、コンパイルエラーの大半が型検査の
  失敗だという数値がありますが、**一次情報で確認できていないので使っていません**。
- `REF-180`・`REF-181` は提供元自身の発表です。採ったのは日付・公開範囲・ライセンス・
  Windows 対応の状態・1.0 の統合内容という事実で、性能やハードウェア対応にまつわる主張は
  採っていません。**この言語の採用を勧めるものではなく、この環境で動かしてもいません。**
- 入口にした記事（`ART-011`）からは、報道としての事実確認以上のものを採っていません。
