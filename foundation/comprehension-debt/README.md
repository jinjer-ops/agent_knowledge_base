# 理解を手放さずに書かせる

**この構成はこの環境で運用していません。** 根拠は提供元の実験、公開された研究、1 人の実践記録で、
ここに書いたのは判断の型です。状態は `experiment` です。

起動条件は「**書かせる量が増えて、自分がその中身を把握できなくなってきたとき**」です。

隣の手引きとの違いは、扱っている対象です。
[../review-design/](../review-design/) は確かめる側の組み方、
[../agent-report-handoff/](../agent-report-handoff/) は結論を受け取る形、
[../autonomous-loop-delegation/](../autonomous-loop-delegation/) は何周任せるか。
ここだけが、**人の側の理解を、減りうる資源として**扱います。

## 減っているのは速度ではなく理解

実践記録（`ART-035`）が「理解負債」と呼ぶのは、技術負債とは別のものです。技術負債は
短期の速さと引き換えに将来の変更費用が上がること。理解負債は、**自分が書いていないコードが
増えるほど、その役割と意図を誰も説明できなくなる**こと。壊れるのはコードではなく、仕様の所在です。

この現象には測定があります。

| 測定 | 条件 | 観測 |
| --- | --- | --- |
| 提供元の実験（`REF-070`） | 開発者 52 名、主に初級、未経験のライブラリ、課題の直後に理解度テスト | AI 支援群の平均 **50%**、手で書いた群 **67%**。差が最大だったのはデバッグの設問 |
| 独立の実験（`REF-071`、査読前） | 学生 54 名、Web サイト作成。エージェントに編集させる群と、自分で当てはめる群 | エージェント群は**初期の完了は速いが、理解と、その後の拡張への備えが損なわれた** |

後者は原因の手がかりも挙げています。**低努力の関わり方**——プロンプトの貼り付け、編集の自動承認——が
低い理解と結びついていました。

どちらも対象は学習者寄りで、熟練者の実務にそのまま移せません。採るのは向きと、
**何が理解を落とすか**の手がかりだけで、割合は持ち込みません。

## 「分かっている」という感覚は、証拠にならない

この領域では、自己評価が符号ごと外れることが測られています（`REF-072`、査読前の無作為化比較試験）。
対象のリポジトリで平均 5 年の経験を持つ開発者 16 名、246 課題。事前の予測は 24% 速くなる、
**事後の自己評価は 20% 速くなった、実測は 19% 遅い**。

測っているのは速度であって理解ではありません。それでも読み替えは成り立ちます。
**自分の作業についての実感は、方向を間違えうる。** したがって「理解できている」も、
感覚ではなく**確かめる手順**の側に置きます。手順が無ければ、理解負債は溜まっていることすら見えません。

### 速度からの読み替えではなく、理解そのもので測られた

**ここは以前、速度の測定からの読み替えに頼っていました。** 同じ分離を、理解そのものに対して
無作為化比較試験で測った資料が出たので置き換えます（`REF-227`、査読前）。2,727 名を 2 群に分け、
片方には専門的な報告書だけを、もう片方には同じ報告書と**モデルが書いた平易な要約**を読ませ、
**自己評価の理解**と、正解が定義された設問による**客観的な理解**の両方を測っています。

| 測ったもの | 要約を足した側 |
| --- | --- |
| 客観的な理解（正解のある設問） | **変わらなかった** |
| 自己評価の理解 | **倍以上に上がった** |
| 満足度 | 大きく上がった |

**感覚と満足度だけが動き、できることは動きませんでした。** 速度からの読み替えが要らなくなった分、
この手引きの前提は強くなっています。対象は医療の報告書で、コードではありません。採ったのは
**felt と actual が分離すること**と、**分離の向き**（感覚の側だけが上がる）です。割合は移していません。

## 効くのは、受け身でない関わり方

`REF-070` は、理解が保たれた使い方も記録しています。

- 生成させた**後に、追加の質問や説明要求**を行う
- 生成と**同時に説明も求める**
- **概念の質問だけに絞り、理解してから自分で実装する**

`REF-071` の観測（低努力の関わりが低い理解と結びつく）は、この裏返しです。

ここで、[../agent-report-handoff/](../agent-report-handoff/) に書いたことと突き合わせます。
あちらでは、**説明を足しても見落としは減らない**という査読済みのレビューを根拠にしています（`REF-066`）。
矛盾ではありません。測っている対象が違い（判断の精度 対 理解の形成）、そのうえで両者は同じ向きを指しています。

- **受け身で差し出される説明**は、受け入れやすさを上げるだけで終わりうる（`REF-066`）
- **自分から問う、自分で書く**という関与は、実際に効いた（`REF-070`）

つまり、図にさせること・説明させること自体を成果にしません。**人が問いを立てて取捨選択する工程が
残っているか**が分かれ目です。

### 読みやすさが、分かった感覚を作る

なぜ受け身の説明が効かないのかには名前が付いています。**処理しやすい情報は、よく理解できたと
誤って判定される**——この誤判定を扱った査読済みのレビューが、2022 年から 2026 年初頭までの
41 件（うち実証研究 28 件）を整理しています（`REF-228`）。結論は、**流暢な生成文は学習者の自信を
上げるが、深い概念理解を一貫して上げるわけではない**。対象は作文・語学、STEM の問題解決、
フィードバックと指導、評価と、分野をまたいでいます。

つまり上の無作為化比較試験（`REF-227`）が 1 分野で見せた分離は、**その分野に限った話ではありません**。
読みやすい説明ほど「分かった」と感じやすい、という方向に機構があります。

### 説明が効く向きと、効かない向き

同じ試験には、見落としやすい観測がもう 1 つあります。要約を足したときの効果が**一様ではなく**、
**原因が書かれている報告では理解が上がり、異常なしの報告ではむしろ下がった**。

コードへ読み替えるなら、こうなります。

| 場面 | 説明の効き方 |
| --- | --- |
| 変更が何をしているかを説明させる | **効きやすい。** 説明する対象が実在する |
| 「ここは問題ない」「見るべき点は無い」を確かめる | **逆に働きうる。** もっともらしい説明が、無いことの確認を難しくする |

ここが [../review-design/](../review-design/) と接するところです。**「指摘なし」という結論ほど、
説明を読んで納得した感覚と、実際に確かめたことの差が開きます。** 採ったのは向きだけで、
対象は医療の報告書なのでコードで再現するかは未確認です。

## 理解する場所を、後ろから前へ

実践記録（`ART-035`）の構成は、人が理解する工程を**実装の前**に置いています。

1. 曖昧な要件を、質問攻めにさせて詰める
2. 実装計画を書かせる（変更するファイル、使う API、テスト方針まで）
3. **長い計画を図解させ、人が読む。** 不明点を個別に聞き、要件の充足とテストの網羅を人が確認する
4. 別系統のモデルに計画の穴を探させ、**過剰防御かどうかは人が取捨選択する**
5. 新しいセッションで実装させる
6. PR を作らせ、複数のモデルでレビューする
7. 人が最終確認して取り込む

著者は 1〜4 に労力の 9 割以上を注ぐと書いています。1 人の実践記録で対照は無く、
**採るのは配分の数字ではなく順序**です。

| 人が見る場所 | 見ているもの | 分かること |
| --- | --- | --- |
| 実装の後だけ | 差分 | 書かれたものが正しそうか |
| 計画の段階 | 変更の意図と範囲 | **そもそも何を作るのか** |

後ろだけに置くと、理解の対象が「他人が書いた差分」になります。これは上の測定で
理解が落ちた側の形そのものです。

計画を**文書として外に出す**ことには、別の効き目もあります。会話として渡した指示は
長いセッションで要約されて消えますが、ファイルは読み直せます（`REF-017`）。
5 の「新しいセッションで実装」が成立するのは、判断が会話ではなく計画側に残っているからです。

## 問いを立てる形が効く範囲には、境目がある

ここまでの結論は「受け身で読まず、自分から問え」でした。**その手当てがどこまで効くかには、
測られた境目があります。**

自分から思い出す・答えを作るという関わり方は、**事実や概念の記憶**に対しては繰り返し効果が確かめられて
います。一方で、**手順的な問題解決の技能**については効かなかった、という査読済みの報告があります
（`REF-229`、`Frontiers in Psychology` 2023）。手本つきの例題から解き方を身につける課題で、
3 つの実験すべて（各 120 名、計およそ 360 名）で効果が見られず、難易度や手当ての与え方を変えても
変わりませんでした。著者らは、宣言的知識では強く出るこの効果が、手順的な問題解決では消えた、と
まとめています。

プログラミングは両方を含みます。したがって**問いを立てる形で何が育つかは、問いの種類で分けます。**

| 問いの種類 | 例 | 期待できるもの |
| --- | --- | --- |
| そのコードについての事実 | この値はどこから来て、誰が渡しているか。この型は何を保証するか | **効きやすい。** 宣言的知識の側 |
| 設計の意図 | なぜこの境界で分けたか。別の案を採らなかった理由は | 効きうる。ただし答え合わせの相手が要る |
| 書けるようになること | 同じ種類の問題を次に自分で解けるか | **これは別物。** 上の報告が効果を見つけられなかった側 |

入口の記事（`ART-057`）は、この分け方を実務の側から独立に言っています。**相談する技能が上がることと、
実装する技能が上がることは別に評価すべき**だ、と。そして著者自身が、作った仕組みの学習効果は
**まだ測っていない**と明記しています。

> **「問う形にしたから学べている」を成果にしません。** 何ができたら理解したことにするかを先に書く、
> というこの手引きの結論（下の節）は、ここでも同じです。3 行目を育てたいなら、
> 問うことではなく**自分で書いて間違える場面**が要ります。

置き場所としては、起動条件と完了条件を持つ反復手順なので skill の層に当たります。ただし
**この環境では運用しておらず、効果も測られていない**ので、ここでは置き場所の判断だけを記録します。

## 移すときに確かめること

- **図にすること自体を成果にしない。** 効いたのは人が問いを立てる関与の方です（`REF-070`、`REF-066`）
- **向かない場面がある。** 実践記録の著者自身が、試行錯誤の段階では「作って、評価して、壊して作り直す」方が
  速いと書いています。この構成が前提にしているのは、テスト・Linter・整形・デッドコード検出が
  揃っていて、設計方針が固まっているリポジトリです（`ART-035`）
- **理解度を測る場所を決める。** 感覚で判定しないという上の結論は、裏返すと
  「何ができたら理解したことにするか」を先に書く必要がある、ということです

## 限界

- `REF-070` は 52 名、主に初級、未経験のライブラリ、課題の直後の測定です。著者自身が、
  **長期のスキル形成を予測するかは不明**で、コーディング以外への一般化も未検証だと断っています。
- `REF-071` は査読前で、対象は学生 54 名と Web サイト作成です。要旨に数値はありません。
  採ったのは向きと、低努力の関わりという手がかりだけです。
- `REF-072` は査読前で、測っているのは**速度であって理解ではありません**。対象は熟練者 16 名、
  成熟したリポジトリ、2025 年前半の道具です。採ったのは「自己評価が外れうる」という一点だけで、
  遅くなるという結果を今の道具に当てはめていません。
- `ART-035` は 1 人の実践記録で、対照も測定もありません。9 割という配分は自己申告です。
  使っている個々の道具や skill は、ここでは採っていません。
- `REF-227` は査読前で、対象は**医療の報告書**であってコードではありません。使った文章も 6 件の
  標準化された報告で、読み手は自分の記録を読んでいません。著者自身が、標準化された文章では
  当事者意識が働かないこと、試したモデルが 1 つであることを断っています。採ったのは
  **felt と actual が分かれること**と、**原因が書かれている場合と異常なしの場合で向きが変わること**の
  2 点だけで、割合は移していません。
- `REF-228` は査読済みですが**レビュー**であり、新しい測定ではありません。採ったのは、
  同じ分離が分野をまたいで繰り返し観測されているという**広さ**だけです。件数（41 件・実証 28 件）は
  規模の説明にのみ使い、個々の研究の結論は持ち込んでいません。
- `REF-229` は査読済みですが、対象は**数学の文章題**で、プログラミングではありません。
  著者らは、習得の期間が短かったこと、手順的知識の複雑さの定義が曖昧なことを限界に挙げています。
  採ったのは「宣言的知識で効く手当てが、手順的な問題解決では効かなかった場合がある」という
  **境目の存在**だけで、プログラミングで同じだと主張していません。
- `ART-057` は 1 人の実践記録かつ道具の紹介で、対照も測定もありません。著者自身が学習効果は
  未測定だと書いています。採ったのは、**相談する技能と実装する技能を分けて評価する**という
  見方と、問いを立てる形を道具として置くという配置だけです。特定の言語・プラグインの採用は
  勧めていません。
- ここに書いた形は、この環境で運用していません。入れるなら、まず**どこで人が問いを立てたか**が
  残る形にし、前後で「後から説明できるか」が変わったかを見ます。
