# 図をテキストから作るとき、どこが壊れるか

**この構成はこの環境で運用していません。** 根拠は査読済みの測定 1 件、未査読のベンチマーク 1 件、
公式資料 3 件、入口の記事 1 件です。状態は `experiment` です。

起動条件は「**エージェントに図（構成図・流れ図）を描かせようとしたとき、または図を文書の中に
持つと決めたとき**」です。

隣の手引きとの違いは、対象です。
[../design-asset-canon/](../design-asset-canon/) は画面の見た目の正本、
[../presentations/](../presentations/) は資料の形式、
[../comprehension-debt/](../comprehension-debt/) は人の側の理解。
ここだけが、**図そのものの正しさと、その確かめ方**を扱います。

## 落ちるのは要素ではなく、関係

図を生成させたときに何が壊れるかには、査読済みの測定があります（`REF-136`）。図を
「文字の要素をノード、つながりを有向辺とするグラフ」として見なし、生成された図と参照の図を
2 つの軸で突き合わせたものです。

| 測った軸 | 何を見るか | 結果 |
| --- | --- | --- |
| 要素の一致 | 参照の図にある文字要素が、生成された図にもあるか | F1 でおおむね 0.33〜0.35 |
| **関係の一致** | **一致した要素の間のつながりが、両方に存在するか** | **F1 でおおむね 0.20〜0.24** |

著者の要約は「参照の図にあるノードと辺の半分以上が、欠けているか判別できない」。さらに、
あるモデルは参照より**多くの要素を置きながら**（平均で 31.67 対 21.42）、関係の側では
より大きく外しています。**箱は増えるのに、線が合わない。**

ここから採る判断は 1 つです。**図の確認は、箱ではなく線を見る。** 生成された図を受け取ったら、
描かれているつながりを 1 本ずつ、元になった対象（コード、設定、実際の経路）と突き合わせます。
要素が揃っていることは、関係が正しいことの証拠になりません。

この結果は対象が論文の図で、構成図そのものではありません。数値はこの環境で再現していないので、
採ったのは**どちらの軸が落ちるかという向き**だけです。

## 「見た目が似ている」は、ほとんど何も言っていない

同じ測定は、確かめ方そのものについても結果を出しています。画像としての類似度を測る従来の指標は、
人の評価との相関が 0.11 前後でした。要素と関係の一致を測る指標は 0.40 前後です。
**画像として似ているかどうかは、人がその図を正しいと判断するかをほとんど予測しません。**

著者は理由も述べていて、画像の類似度は配置・色・体裁に過敏で、中身の正しさと関係ない部分に
左右されるからです。

これはこの領域に限った話ではありません。この foundation には同じ形の結論が既に 2 つあります。
[../design-asset-canon/](../design-asset-canon/) では、画面を目で見てもコントラストの不足は
捕まらない。[../presentations/](../presentations/) では、画像へ書き出して見てもファイルの破損は
捕まらない。**描画された結果を見る検証は、見た目に出ない層の誤りを外します。** 図の場合、
見た目に出ない層とは関係の集合です。

したがって、図に対して最初に行う検査は次の順になります。

1. **構文**：図の記述が描画器を通るか。これは機械が完全に判定でき、人が見る必要がありません。
2. **関係**：辺の一覧を書き出し、元の対象と 1 本ずつ突き合わせる。ここが落ちる場所です。
3. **見た目**：重なり、はみ出し、読める大きさ。最後でよく、ここだけでは 1 と 2 を代替しません。

なお、図の生成を測る別のベンチマーク（`REF-137`、未査読）は、構文の正しさも含めて**モデルに
判定させる**設計です。図は描画器に通せば構文を決定論的に判定できるので、この環境では
手順 1 をモデルに任せません。同じ理由は [../review-design/](../review-design/) に既にあります。

## 記法は、どこで描画されるかで決まる

図をテキストで持つと決めた後の選択は、好みではなく**置き場所**で決まります。

成果物が GitHub の中で読まれる（README、課題、変更要求、wiki）なら、公式に描画される記法は
限られています。公式資料（`REF-135`）が挙げるのは Mermaid、GeoJSON、TopoJSON、ASCII STL の
4 つで、**D2 への言及はありません**。同じ資料は、対応する構文が版によって変わるので使用中の版を
確認するようにとも書いています。

つまり、

- **GitHub の中で直接読ませたい** → そこで描画される記法を選ぶ。別の記法を選ぶと、
  画像を生成して貼る工程が毎回必要になり、テキストを正本にした利点（差分が読める）が
  画像の側で切れます。
- **文書サイトや資料に埋め込む / 画像として出す** → 描画を自分の側で回せるので、
  記法の選択肢は広がります。

## レイアウトエンジンを変える前に

送信元の話題（`ART-045`、一次情報は `REF-133`）は、構成図向けに設計されたレイアウト
アルゴリズムが、同じ言語と同じライセンス（MPL-2.0）で公開され、処理系に同梱されて
指定 1 つで使えるようになった、というものです。既定のエンジンが階層的に一方向へ展開するのに対し、
こちらは直交で、対称性やまとまりを目標に含みます（`REF-134` によれば既定は別のエンジンで、
位置の固定など一部の機能はこのエンジンでしか効きません）。

採用を考えるなら、公表されている制約 3 点を先に見ます（`REF-133`、いずれも作者自身の記述）。

1. **実行ごとに結果が変わりうる**。複数の初期値から最も良いものを選ぶ方式のため、
   ノードを 1 つ足しただけで図全体の配置が変わることがある。
2. **長く流れる図には向かない**。作者自身が、そういう図では既定側のエンジンを好むと書いている。
3. **大きい図で、処理時間が非線形に伸びる**。

1 については、混同しやすい点を 1 つ。**変わるのは配置であって、図の記述そのものではありません。**
正本がテキストである限り、版管理で読める差分は保たれます。影響が出るのは、生成した画像を
成果物として版管理に入れている場合で、そのときは中身が変わっていなくても画像が毎回差分になります。
**画像を版管理に入れるなら、レイアウトが決定的かどうかを先に確かめます。**

## 入れる前に確かめること

1. その図は、**どこで読まれるか**。読まれる場所で描画される記法か。
2. 確認の手順に、**辺の突き合わせ**が入っているか。見た目の確認だけになっていないか。
3. 構文の判定を、描画器に通す形で**機械に任せているか**。
4. 版管理に入れるのはテキストか、生成した画像か。画像なら、レイアウトは実行ごとに同じか。
5. そもそも、その図を**作ること自体が目的に効くか**。
   [../comprehension-debt/](../comprehension-debt/) は、理解が保たれるのは図を出す工程ではなく、
   人が不明点を問う工程だと記録しています。関係の半分が合っていない図は、
   理解の助けではなく、誤った確信の材料になりえます。
