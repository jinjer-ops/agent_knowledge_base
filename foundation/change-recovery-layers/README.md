# エージェントが変えたものを、どの層で取り戻すか

**この手引きは未検証です。** 下の確認手順はこの環境で実行していません。巻き戻しも復元も
一度も試していないので、状態は `experiment` です。特定の製品・構成の導入を勧めるものでは
ありません。実行ファイルは置いていません。

## 起動条件

エージェントにファイルを書き換えさせる構成を、人が 1 行ずつ見ない前提で回すと決めたとき。
扱うのは「間違った変更をどう防ぐか」ではなく、**防げなかったときに、どこから元を取るか**です。

隣の領域との境目を先に書きます。

| 領域 | 扱うもの |
| --- | --- |
| [../windows-file-hazards/](../windows-file-hazards/) | 出力は正しいのに、**ディスクに着くまでに**中身が変わる |
| [../secret-exposure-layers/](../secret-exposure-layers/) | 置いたものが**外へ出る**経路 |
| [../review-design/](../review-design/) | 誤りを**捕まえる**側の組み方 |
| ここ | 着いた後に**消える・戻せない**。捕まえた後に**何から戻すか** |

## 1. 検出と復元は、別の能力である

一番効く区別がこれです。OpenZFS の公式ドキュメントは、冗長性のないプールについてこう書いて
います（`REF-204`）。**破損を検出し、どのファイルが影響を受けたかを正確に報告することはできるが、
修復はできない。** チェックサムは「どこが壊れたか」を教えるだけで、正しい中身を持っていません。
正しい中身は、別のところにある複製からしか来ません。

これは ZFS に固有の性質ではなく、**層の性質**です。同じ形がこの環境にもそのまま出ます。

| 能力 | 何をするか | これだけでは足りない理由 |
| --- | --- | --- |
| 検出 | 変わったこと・壊れたことに気づく | 元の中身を持っていない |
| 冗長 | 同じ中身の別の複製から直す | **同じ操作が全部の複製に届く**（削除・上書きは一緒に伝播する） |
| 履歴 | 以前の状態へ戻す | 期限と射程がある（次の節） |
| 機械の外の複製 | 機械ごと失っても残る | 新しさで必ず遅れる |

[../windows-file-hazards/](../windows-file-hazards/) が勧めている対処（編集の前後で大きさと
ハッシュを比べる）は**検出**です。あの手引きには、検出したあと元の中身をどこから取るかが
書かれていません。この手引きはその続きです。

## 2. この環境の「取り消せる層」は 3 つあり、3 つとも穴がある

### 2-1. セッションの巻き戻し（Claude Code のチェックポイント）

公式の仕様です（`REF-202`、確認日 2026-10-26）。追跡するのは**組み込みのファイル編集ツールが
加えた変更**で、会話を始める入力ごとにその直前の状態を記録します。

**この層に入らないものが 4 つあります。**

1. **シェルが変えたファイル。** 公式の表現は「A file that only Bash commands changed isn't
   tracked and stays as it is」。ここは誤解しやすいので正確に書きます。*一度*編集ツールで
   触ったファイルなら、その後に `rm`・`mv`・`git reset` などが加えた変更も巻き戻ります。
   **編集ツールが一度も触っていないファイル**だけが対象外です。つまり、スクリプトが作った
   ファイル、`mv` で持ってきたファイル、生成物は、この層の外にあります。
2. **背景で動くサブエージェントの編集。** 背景で走るサブエージェント（既定で背景になる
   forked skill や、背景のレビュー実行を含む）が触ったファイルは復元されません。復元されるのは
   「会話の中で既に編集していたファイル」だけです。**下位エージェントに並列で書かせる構成を
   常用しているなら、この穴は閉じていません。**
3. **symlink と hard link。** 巻き戻しのとき、追跡していても**飛ばされ**、
   `Restored the code, but skipped N files` という警告だけが出ます。中身は今のまま残ります。
   公式が例に挙げているのは、dotfile 管理の道具がプロジェクトへ張り込む設定ファイルです。
   入口の指示ファイルをその形で持っているなら、ここに当たります。
4. **セッションの外での変更**と、**並行して動く別のセッション**の編集。

**期限もあります。** セッションあたり直近 100 件まで。既定では、そのセッションが最後に記録してから
約 30 日後の掃除で消えます。消えた後に巻き戻すと `No files were restored` で失敗します。
延ばす設定項目はあります。そして公式自身が **「Not a replacement for version control」** と
書いています。この層はセッションの中の取り消しであって、保存ではありません。

### 2-2. 版管理（git）

2 段目にも時計があり、**こちらが何もしなくても進みます**（`REF-203`）。

| 既定値 | 意味 |
| --- | --- |
| reflog 90 日 | 参照の移動の記録はこの期間で消える |
| 到達不能な reflog 30 日 | どこからも辿れなくなった先の記録はもっと早く消える |
| `prune --expire 2.weeks.ago` | `git gc` が呼ぶ猶予。これを過ぎた到達不能オブジェクトは消える |
| `gc.auto` 6700 | ルーズオブジェクトがこの数を超えると自動で走る |

**自動 gc の起動条件が重要です。** 公式の記述では、オブジェクトを作る一般的な porcelain コマンドが
実行されるたびに、前回から十分に増えたかを確認して `git gc` を自動で走らせます。つまり、
エージェントが普通にコミットを積んでいるだけで掃除は進みます。「あとで reflog から拾えばいい」は、
**期限つきの約束**です。

射程の外も明確です。**コミットしていない作業ツリーの変更と、未追跡のファイルは git の中にありません。**
エージェントが作ってまだコミットしていない成果物は、1 段目（編集ツールが触っていなければ対象外）にも
2 段目（まだコミットされていない）にも入っていない、という状態になりえます。

ひとつ検出の面での長所があります。git のオブジェクトは内容のハッシュで名前付けされているので、
オブジェクトの破損は機械的に判定できます。ただしそれは**オブジェクトの中だけ**で、
作業ツリーのファイルと未追跡ファイルは対象外です。

公式ドキュメントは、`git gc` が別のプロセスと同時に走ったときに、まだ参照の作られていない
オブジェクトを消してしまう危険が残ると書いています。**並行して複数のエージェントに同じ
リポジトリを触らせる構成では、この注意がそのまま当たります。**

### 2-3. 機械の外

上の 2 つは**どちらもこの 1 台の中にあります**。機械を失えば両方消えます。
この環境では、機械の外の層があるかどうかを確かめていません。

## 3. 層ごとに、何が覆われていないかを数える

| 失い方 | 1. 巻き戻し | 2. git | 3. 機械の外 |
| --- | --- | --- | --- |
| 編集ツールが上書きした | ○ | コミット後なら ○ | ○ |
| シェルだけが触ったファイルを壊した | **×** | コミット後なら ○ | ○ |
| 背景のサブエージェントが別のファイルを書き換えた | **×** | コミット後なら ○ | ○ |
| コミット前の未追跡の成果物を消した | 編集ツールが触っていれば ○ | **×** | 複製の時点まで |
| symlink の先を書き換えた | **×**（飛ばされる） | コミット後なら ○ | ○ |
| 30 日以上前のセッションへ戻したい | **×**（掃除済み） | ○ | ○ |
| 2 週間以上前に到達不能になったコミット | × | **×**（prune 済み） | 複製の時点まで |
| 機械が壊れた・暗号化された | × | × | ○ |
| ディスクが黙って中身を変えた | × | オブジェクトなら検出可 | 複製も壊れていれば × |

**この表の読み方は 1 つです。** 行を上から見て、自分の構成で `×` が並ぶ行があるなら、
そこが開いている穴です。穴を見つけてから層を足すので、先に製品を選ばないでください。

## 4. 送信記事（`ART-052`）の構成を、この枠で読む

入口の記事は、古い PC に TrueNAS Community Edition を入れ、HDD 4 台の RAID-Z1 のプールを作って
共有する手順です。この枠に置くと、**冗長の列を 1 つ足す**構成にあたります。
1 台壊れても読めるようになりますが、上の表の「消した」「上書きした」の行は 1 つも埋まりません。
**冗長は、同じ操作が全部の複製へ同時に届くことを防ぎません。**

記事はスナップショットの存在に触れていますが、手順も運用も書いていません。前提の確認が 2 つ要ります。

- **スナップショットは同じプールの中にあります。** プールごと失えば一緒に消えるので、
  これは「機械の外」の層ではありません。外へ出すには別筐体への転送の仕組みが別に要ります。
  この環境では、どちらも確かめていません。
- **古いハードウェアを再利用する構成は、検出の層が要る側です。** 153 万台・41 か月の実測で、
  nearline 級のディスクは企業向けより 1 桁多くチェックサム不一致を出しています（`REF-205`）。
  同じ研究は、不一致が 1 台の中でも複数台の間でも**独立に起きない**（まとまって出る）と
  報告しています。壊れるときは 1 ブロックずつではない、という向きです。
  記事はこの論点に触れていません。

**記事の数値は提供元の現行の記述と食い違う箇所があります。** 起動ディスクについて、記事は
「16GB 以上の SSD」と書いていますが、公式の現行ガイドは 20GB 以上を最小としています（`REF-206`）。
最小メモリは 8GB で一致します。導入する場合は、記事ではなく提供元の現行ページで確かめてください。

**ECC メモリについては、よくある断定が公式の記述と違います。** 公式ガイドの書き方は
「most users _strongly_ recommend ECC RAM as another data integrity defense」で、
**強く勧めているのは利用者であって、提供元が必須としているのではありません。**
同じページが「Many TrueNAS systems operate every day without ECC RAM」とも書いています。
「ECC が無いと使えない」も「ECC があれば安全」も、この一次情報からは出てきません。

## 5. 確認する手順（この環境では未実行）

足す前に、今ある層がどこまで届くかを測ります。順番に意味があります。

1. **一番危ない操作を 1 つ選び、それが 1 段目に入るかを確かめる。**
   エージェントが普段どの道具でファイルを消す・動かすかを見ます。シェル経由なら 1 段目の外です。
2. **背景のサブエージェントを使っているかを数える。** 使っているなら、その編集は巻き戻りません。
   使う構成を続けるなら、2 段目（コミット）を**作業の区切りごとに**置くのが実際の受け皿になります。
3. **未追跡のまま置いている成果物を一覧にする。** `git status` に出てくるもののうち、
   消えて困るものがあれば、それは 2 段目にも入っていません。
4. **入口の指示ファイルが symlink かを確かめる。** symlink なら巻き戻しで飛ばされます。
   張り込みではなく取り込みで持つ判断は [../agents-md/README.md](../agents-md/README.md) にあります。
5. **実際に 1 回戻してみる。** ここが抜けると、上の全部が「持っているつもり」で終わります。
   公式が `No files were restored` という失敗を明記している以上、**巻き戻せることは確かめるまで
   仮定にすぎません**。復元を試していない層は、層として数えません。

## 他の領域との関係

- 着くまでに壊れる側は [../windows-file-hazards/](../windows-file-hazards/) にあります。
  あの手引きの対処の順序は「同期の外へ作業ツリーを出す」から始まりますが、
  **同期の層が版の履歴を兼ねていた場合、外に出すと取り消せる層が 1 つ減ります。**
  出すなら、戻せる層を別に立ててからにします。
- 自律で何周も回させる判断は [../autonomous-loop-delegation/](../autonomous-loop-delegation/)。
  任せる長さを決めるとき、**人が見ていない区間の長さが、1 段目の射程を超えていないか**が
  この領域からの条件になります。
- 止める側（hook・権限・mod）の設計は [../claude-code/README.md](../claude-code/README.md)。
  止める層と戻す層は別物で、片方を厚くしても片方は埋まりません。
- 機械の外へ出す経路を作ると、今度は秘密が外へ出る経路にもなります。
  [../secret-exposure-layers/](../secret-exposure-layers/) を先に読みます。

## 限界

- **この環境では、巻き戻しも git からの復元も一度も試していません。** 上の確認手順は未実行です。
- `REF-202` と `REF-203` の既定値は版に依存します。使う版の公式資料で読み直してください。
  この手引きに残したのは「期限と射程がある」という設計上の事実で、個々の日数を推奨値として
  書いたものではありません。
- `REF-204` は ZFS の実装の説明です。「検出と復元は別」という形だけを一般化して使っており、
  ZFS をこの環境へ導入することは勧めていません。
- `REF-205` は 2008 年の査読付き論文で、対象は当時の企業向けストレージです。
  採ったのは**向き**（再利用・安価側のディスクほど検出の層が要る、破損はまとまって出る）だけで、
  発生率をこの環境へ持ち込んでいません。
- `ART-052` は実務者の手順記事で、対照も実測もありません。構成の入口として扱い、
  ハードウェアの数値は提供元の現行ページ（`REF-206`）で検算した差だけを記録しています。
- スナップショットがプールの外へ出ないことと、別筐体への転送の仕組みについては、
  提供元の該当ページを直接確認していません。構造から述べた範囲に留めています。
