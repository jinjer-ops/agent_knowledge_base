# Evidence-first review

使うのは、データ更新、認可、秘密、金銭、不可逆変更、または複数コンポーネントにまたがる変更をレビューするときです。

## レビューの順序

1. 対象・基準コミット・受け入れ条件・権限境界を短いマニフェストに記録する。
2. 正しさ、環境差、権限と外部入力、運用、引き継ぎの観点から、証拠を伴う仮説だけを調べる。
3. 指摘は別の視点で反証し、再現できるものだけを残す。
4. 指摘がなくても、確認範囲と残余リスクを記録する。

## 判断の置き場所

同じレビュー観点を、すべてLLMや人に再判定させない。判断の性質に応じて次の順で置く。

| 層 | 置く判断 | 扱い |
| --- | --- | --- |
| 決定論的検査 | test、型、schema、明示された依存境界など、機械的に検証できる事実 | 結果をLLMの推測で覆さない |
| ルール検出 | 明示パターンで高い精度に候補を絞れる兆候 | 候補として示し、例外や意味まで単純な規則へ押し込まない |
| 意味的レビュー | planとdiffの整合、要求境界の扱い、複数成果物の矛盾 | 証拠を添えて指摘し、未確認を事実のように扱わない |
| 人間の判断 | 認可、秘密、金銭、不可逆変更、事業上のトレードオフ | agentは根拠を示して停止し、承認・実行・mergeを代行しない |

同じ意味的・人間判断が繰り返し現れ、条件・例外・安全な失敗時の扱いを明文化できるなら、rule、test、checkerへの移行を検討する。移行で安全性、説明可能性、保守性が下がる場合、または責任を伴う場合は、元の層に残す。

## 最小チェック

- 実行環境で実際に動く証拠があるか。開発端末での成功を本番相当の証拠にしない。
- 入力・LLM出力・権限・宛先が許可された範囲に制限されているか。
- read/create/update/delete/admin の操作分類、承認、ロールバック、証跡が定義されているか。
- 失敗時に危険側へ倒れないか。判定不能・絞り込み失敗・未知の入力は停止または人へ返すか。
- 成功応答、設定の保存、テスト通過を、意図どおりの結果の証拠と混同していないか。
- 正本が一つで、手順・設定・実装が矛盾していないか。

実装固有のチェックを追加する場合は、この一般則を複製せず、該当プロジェクトのrulesへ短く追加します。
