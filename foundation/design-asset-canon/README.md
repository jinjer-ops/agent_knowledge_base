# 見た目の正本を、言葉ではなく実物で持つ

**この構成はこの環境で運用していません。** 根拠は 2 件の実践記録、3 件の測定（未査読）、
2 件の査読済みの測定、1 件の提供元による自社測定、4 件の公式資料です。状態は `experiment` です。

起動条件は「**エージェントに見た目のあるもの（画面・サイト・資料）を作らせていて、
毎回『もっと見た目を良くして』と言葉で指示し直しているとき**」、または
「**正本は決めたのに、作らせるたびに少しずつずれるとき**」です。後半は前半の次の段なので、
分けずに同じ文書に置いています。前半は「何を正本として持つか」、後半の
「ずれを捕まえる層と、それぞれの天井」以降が「ずれをどこで止めるか」です。

隣の手引きとの違いは、決める対象です。
[../presentations/](../presentations/) は**どの形式で作るか**、
[../retrieval-structure-decision/](../retrieval-structure-decision/) は**探す経路に何を作るか**、
[../generated-prose-style/](../generated-prose-style/) は**書かせた文章の文体をどう扱うか**。
ここだけが、**作らせる前に、見た目の正本として何を手元に持つか**を扱います。

## 言葉で指示する経路は、測ると裏目に出ている

出発点の実践記録（`ART-010`）の主張は単純です。曖昧な言葉で頼むより、**過去に作って
動作を確かめた実物の HTML を「これを参考に」と渡した方が、方向性が伝わる**。
記事には実測がありません。

その向きを支持する測定が 2 件あり、**うち 1 件は、言葉で足す経路が逆効果だったことまで
測っています**。

| 測定 | 条件 | 観測 |
| --- | --- | --- |
| 未査読のプレプリント（`REF-124`） | 画面の設計から実装コードを作らせる課題。入力を「スクリーンショットのみ」と「構造化メタデータ＋アセット＋スクリーンショット」で比較 | 構造化メタデータを足した方が視覚的な忠実度は上がった。一方で**メタデータを与えた側は固いレイアウトになりやすい**とも報告 |
| 査読済み（`REF-127`、54 名のデザイナー・6 種のツール・21,880 件の評価） | 人が手で作った画面と、同等物を AI に生成させた画面を WCAG の 5 基準で比較 | AI 生成の適合は **29.0%**。最も低いのはコントラスト **26.8%** と色の使用 **19.2%**。**生成時のプロンプトにアクセシビリティ要件を明記すると、適合率は上がらず下がった** |

後者の「明記すると下がる」は、この手引きの土台です。**足りないものを言葉で足す経路は、
効かないどころか、効いていると誤認させる。** 同じ研究は、違反の 39% が「大幅な作り直しが
必要」と判定されたとも報告しています（手作業の画面は 22%）。後から直す前提で進める設計は、
その分の作り直しを買っています。

数値はこの環境で再現していません。採るのは向きだけです。

## ただし「実物を渡す」は、渡し方で結果が変わる

`REF-124` の但し書き——メタデータを与えた側は固いレイアウトになりやすい——は、
`ART-010` の手順の弱点を正確に指しています。**完成した 1 枚の HTML を参考として渡すと、
その寸法・配置・前提ごと複製されうる。** 1 画面では良く見え、画面幅や文字量が変われば崩れます。

したがって、正本の形を 3 段で分けます。下へ行くほど壊れにくく、上へ行くほど作るのが速い。

| 形 | 渡すもの | 複製されるもの |
| --- | --- | --- |
| スニペット | 動作確認した単一 HTML（`ART-010` の形） | 見た目と、**そのときの寸法・前提ごと** |
| 部品 | 名前と用途を持つ再利用単位（`REF-126` のレジストリ項目の形） | 見た目と、使い方の約束 |
| 値 | 色・寸法などを名前と値で持つ（`REF-128` の考え方） | 判断だけ。配置は毎回決まる |

`REF-128`（デザイントークンの交換形式）は 2026-09 時点で**ドラフトであり、仕様自身が
「この版を実装しようとしないこと」と明記**しています。したがってこの形式を採れとは
書きません。採るのは「**見た目の決定は、完成物ではなく名前付きの値としても持てる**」
という考え方だけです。

実務では 3 段を混ぜます。固めたい判断（色・間隔・角丸）は値、繰り返す単位（ボタン・
フォーム・カード）は部品、まだ 1 回しか使っていないものはスニペットで置き、
**使い回した回数が増えたものから下の段へ落とす**。

## その手前に、正本は 1 つではないという分割がある

上の 3 段は「同じ 1 つの正本を、どこまで抽象化して持つか」の話です。実際に組んだ記録
（`ART-050`）は、その手前に別の分割を置いています。**正本は、見た目・値・振る舞いの 3 面に
割れていて、面ごとに置き場が違う**。

| 面 | その記録での置き場 | 一般化すると |
| --- | --- | --- |
| 見た目 | デザインファイル | 画面全体の構図・配置を、人が見て決める場所 |
| 値 | コード側の名前付き変数 | 色・寸法・角丸などの決定を、名前と値で持つ場所 |
| 振る舞い | 部品カタログ | 状態（押せない・読み込み中・エラー）を網羅して見る場所 |

この分割が効くのは、**ずれが面と面の間で起きる**からです。同じ青に別の名前が付く、
デザインファイルの値とコードの値が数 px ずれる、といった症状は、どれか 1 面の中では
正しく見えます。したがって面ごとの確認では捕まらず、**面の間を突き合わせる検査**が要ります。

値の面については、面の間の重複をそもそも作らない道があります。Tailwind CSS v4 の
`@theme` は、宣言した変数から CSS 変数と対応するユーティリティクラスの**両方を生成**します
（`REF-194`）。名前空間ごと既定値を破棄する指定もあるので、「承認した値だけが使える」状態を
値の側で作れます。同じ考え方の、道具に依存しない交換形式が `REF-128` ですが、こちらは
ドラフトのままなので採るのは考え方だけです。

### 入口の指示文書には、観点だけを書く

同じ記録は、入口となる文書に**観点は書き、具体値は書かない**という選択をしています
（`ART-050`）。値を書いた時点で、その文書が 4 つ目の面になり、同期の相手が 1 つ増えるためです。

これは見た目に限った話ではなく、
[../agents-md/](../agents-md/) が指示ファイル一般について述べている
「同じ事実を正本と入口の両方に書かない。入口には正本を指す行だけを残す」と同じ形です。
**見た目の正本を持つと決めたなら、指示ファイル側は正本の場所と、守ってほしい観点だけを持ちます。**

## ずれを捕まえる層と、それぞれの天井

`ART-010` の確認は「ブラウザで開いて、崩れていないか・動くか・不要な部分が残っていないか」
です。これは必要ですが、**落ちている基準をちょうど外しています**。`REF-127` が最も低い
適合率を記録したコントラストと色の使用は、どちらも**人が見て気づきにくく、機械で正確に
判定できる**種類の基準です。

そこで層を分けます。重要なのは順序だけではなく、**層ごとに止められる範囲に天井がある**ことです。
天井を知らずに層を足すと、通ったことを「守られた」と読み違えます。

| 層 | 捕まえるもの | 測られている天井 |
| --- | --- | --- |
| 1. 規則で判定する | コントラスト比、代替テキスト、見出しの入れ子、色だけで情報を伝えていないか、未承認の値・名前 | 自動検出が占めるのは**全体の 6 割弱**（`REF-192`） |
| 2. 面の間を突き合わせる | デザインファイルの値とコードの値の一致、名前の重複 | 面を分けた分だけ必要。1 の検査では出ない（`ART-050`） |
| 3. 描画して比べる | 崩れ、重なり、溢れ、画面幅を変えたときの挙動 | **環境が変われば同じコードでも差が出る**（`REF-193`） |
| 4. 判断モデルに採点させる | 「らしさ」「落ち着き」のような規則にできない観点 | **次元によって人と合う／合わない**（`REF-195`、`REF-196`） |
| 5. 人が読む | その部品が何のためのものか、名前が用途を表しているか | 上の 4 層が残したもの全部 |

### 1 の天井: 自動検出は半分強で止まる

規則判定の道具の提供元が、自社の監査データ（13,000 ページ超・約 30 万件の指摘）から、
自動検出が占める割合を **57.38%** と報告しています（`REF-192`）。残りとして挙げられているのは、
フォーカスの順序、キーボード操作、文字以外のコントラスト、意味のある読み上げ順、
ホバーやフォーカス時の挙動、動画の字幕など、**操作して初めて分かる種類**です。

これは提供元が自社ツールについて出した数字なので、値そのものは採りません。採るのは
**「規則判定を全部通しても、残りの側に同じ桁の量がある」という向き**です。そして残りの中身が
操作に依存する項目に偏るという事実は、後ろの層の設計に効きます（4 の天井がちょうどそこだからです）。

### 3 の天井: 画素の比較は、調整つまみごと渡される

描画して比べる層は、同じコードでも**ホスト OS、版、設定、ハードウェア、電源が電池か否か、
ヘッドレスかどうか**で結果が変わると公式資料が明記しています（`REF-193`）。そのため基準画像を
作った環境と同じ環境で実行することが前提条件になります。記録（`ART-050`）が固定環境を用意して
いるのは、この前提に対する正しい対処です。

同時に、この層には**許容値という正規の調整つまみ**が付いてきます（`REF-193` の `threshold` と
`maxDiffPixels`）。緩めれば失敗は黙りますが、黙るのは環境差だけではありません。
つまみの存在自体が無効化の経路になるという一般の話は
[../review-design/](../review-design/) に書きました。

費用も測られています。この層を入れた PR は、入れていない見た目の変更の PR と比べて
**議論のやり取りが 1 桁多く、解決までの時間も数倍**になり、それでいて**受理される割合は
変わりませんでした**（`REF-197`、103 リポジトリ・307 PR）。読み方は 2 通りあります。
失敗の解釈に人の時間を払っている、とも読めますし、これまで議論されずに通っていた変更が
議論されるようになった、とも読めます。どちらにせよ、**この層は「足せば自動で楽になる」層では
ありません**。

同じ調査は、失敗の内訳を配置・見え方・色・文字・状態・テスト自体・画像に分け、
**約 2 割は見た目が原因ではなかった**と報告しています。未定義の部品状態や、内容がそもそも
消えている類です。つまりこの層は、名前は見た目の検査ですが、実際には**意図しない変更の
副作用を拾う二次的な検出器**として働いています。名前の通りに期待すると、拾っているものを
見落とします。

### 4 の天井: 合う次元と、系統的に甘くなる次元がある

規則にできない観点をモデルに採点させる構成は、記録（`ART-050`）でも使われていますが、
著者自身が結論は出ていないと書いています。外側の測定は 2 件あり、**同じ向きに割れています**。

| 測定 | 条件 | 観測 |
| --- | --- | --- |
| `REF-195`（未査読） | 30 画面を複数のマルチモーダルモデルに採点させ、人の知覚と比較 | 一部の次元では人の選好に近づき、**別の次元では外れる** |
| `REF-196`（査読済み・1,000 画面の専門家注釈データ） | 4 つのモデルに静止画から採点させ、専門家の評価と比較 | 見た目（美しさ・デザインの質）は**ほぼ一致**。使いやすさ・学習しやすさ・効率は**系統的に甘く出る** |

結論は、採点させる観点を**静止画から判定できるものに限る**ことです。見た目の印象を揃える
用途なら使えます。操作して初めて分かる観点を採点させると、**実際より良い点が返ってきます**。
しかもその観点は、1 の天井が落としていた側とちょうど同じ領域です。**自動検出が取りこぼした
範囲を、判断モデルで埋めることはできません。** 両方が同じ場所で弱いからです。

数値はこの環境で再現していません。`REF-196` の差の大きさも採っていません。採るのは
「見た目の次元と操作の次元で結果が割れる」という向きだけです。

### 層を足す前に

この順序が重要なのは、**資産は複製される**からです。1 件の欠陥を入れると、以後その欠陥が
入った画面の数だけ増えます。言い換えると、資産に入れる作業は 1 回ですが、
入れ損ねた確認の費用は後から掛け算で返ってきます。

一方で、上の天井が示すのは**全層を同時に入れる必要はない**ということです。
[../review-design/](../review-design/) の条件がそのまま効きます。足した検査が返す文面が
「何が駄目か・代わりに何を使うか・どこを見ればよいか」を含んでいないなら、
その層は置き場所を変えただけです。入れる順序は、天井が高く費用が低い側（1 と 2）から。

機械判定の具体的な道具とコマンドは、この手引きでは指定しません。
**規則で判定できる部分を決定論的な検査へ移し、残りだけを人と判断モデルに回す**という配置と、
**各層の天井を先に知っておく**ことだけが、ここでの結論です。

## 置き場所と、渡し方

正本をどこに置くかは、**誰が引くか**で決まります。

- **自分だけで使う**: skill に添える参照ファイルにする。Claude Code の skill は本体とは別に
  ファイルを同梱でき、必要になったときにだけ読まれます（`REF-002`）。見た目の正本は
  常時読み込ませる種類の情報ではないので、この形が合います。
- **チームや複数プロジェクトで使う**: 配布の仕組みは既にあります。`REF-126` は自前の
  レジストリを置いて、部品・設定・ルールをエージェントから引ける形で配る方法を示します。
  索引ファイルを 1 つ置けばエージェントが一覧を引けるようになり、推奨は「用途が分かる説明を
  書く」「依存を正確に列挙する」「名前の付け方を揃える」。React 専用ではありません。
- **デザインツール側に正本がある**: `REF-125` は、コンポーネント・変数・レイアウト・
  コードとの対応付けをエージェントへ直接渡す公式の経路です。既にそこに正本があるなら、
  HTML を手で抜き出して二重に持つ理由はありません。

いずれの場合も、**全部をまとめて渡さない**。`REF-126` が索引と項目を分けているのが示すのは、
エージェントに要るのは「何があるか」の一覧と、選んだ 1〜数件の中身だという形です。
部品集を丸ごと貼り付ける運用は、[../heavy-read-delegation/](../heavy-read-delegation/) と
[../token-drain-review/](../token-drain-review/) が扱っている費用の問題に、自分で変わります。

## 入れる前に確かめること

1. 正本は既にどこかにあるか。デザインツール・既存のレジストリ・使っている部品ライブラリに
   あるなら、手で抜き出した複製を増やさない。
2. 正本はいくつの面に分かれているか。面を分けたなら、**面の間を突き合わせる検査を同時に決める**。
   分けただけで突き合わせないと、ずれの発生源を増やしたことになる。
3. 置く段はどれか。スニペットから始めてよいが、**2 回目に使った時点で部品へ、
   色と寸法は値へ**、と落とす先を先に決めておく。
4. 入口の指示文書に、具体値を書いていないか。書いた時点でそこが同期の相手になる。
5. 資産に入れる条件に、**機械で判定する項目が含まれているか**。目視だけなら、
   最も落ちる基準を見ていない。
6. 入れた層の天井を言えるか。特に、**規則判定が落とす側と、判断モデルが甘くなる側は
   同じ領域**（操作して初めて分かる観点）であって、互いに埋め合わない。
7. 描画して比べる層を入れるなら、基準画像を作る環境を固定したか。許容値を緩めて
   黙らせる経路を、誰がどう使ってよいか決めたか。
8. 渡すのは一覧か、中身か。中身を渡すなら何件までか。
9. 出所が自分でないコードを資産に入れていないか（`ART-010` 自身の注意）。
   スクリプトを含む部品は、見た目の参考としてではなく、実行されるコードとして扱う。
