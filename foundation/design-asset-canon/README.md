# 見た目の正本を、言葉ではなく実物で持つ

**この構成はこの環境で運用していません。** 根拠は 1 件の実践記録、1 件の測定（未査読）、
1 件の査読済みの測定、3 件の公式資料です。状態は `experiment` です。

起動条件は「**エージェントに見た目のあるもの（画面・サイト・資料）を作らせていて、
毎回『もっと見た目を良くして』と言葉で指示し直しているとき**」です。

隣の手引きとの違いは、決める対象です。
[../presentations/](../presentations/) は**どの形式で作るか**、
[../retrieval-structure-decision/](../retrieval-structure-decision/) は**探す経路に何を作るか**、
[../generated-prose-style/](../generated-prose-style/) は**書かせた文章の文体をどう扱うか**。
ここだけが、**作らせる前に、見た目の正本として何を手元に持つか**を扱います。

## 言葉で指示する経路は、測ると裏目に出ている

出発点の実践記録（`ART-010`）の主張は単純です。曖昧な言葉で頼むより、**過去に作って
動作を確かめた実物の HTML を「これを参考に」と渡した方が、方向性が伝わる**。
記事には実測がありません。

その向きを支持する測定が 2 件あり、**うち 1 件は、言葉で足す経路が逆効果だったことまで
測っています**。

| 測定 | 条件 | 観測 |
| --- | --- | --- |
| 未査読のプレプリント（`REF-124`） | 画面の設計から実装コードを作らせる課題。入力を「スクリーンショットのみ」と「構造化メタデータ＋アセット＋スクリーンショット」で比較 | 構造化メタデータを足した方が視覚的な忠実度は上がった。一方で**メタデータを与えた側は固いレイアウトになりやすい**とも報告 |
| 査読済み（`REF-127`、54 名のデザイナー・6 種のツール・21,880 件の評価） | 人が手で作った画面と、同等物を AI に生成させた画面を WCAG の 5 基準で比較 | AI 生成の適合は **29.0%**。最も低いのはコントラスト **26.8%** と色の使用 **19.2%**。**生成時のプロンプトにアクセシビリティ要件を明記すると、適合率は上がらず下がった** |

後者の「明記すると下がる」は、この手引きの土台です。**足りないものを言葉で足す経路は、
効かないどころか、効いていると誤認させる。** 同じ研究は、違反の 39% が「大幅な作り直しが
必要」と判定されたとも報告しています（手作業の画面は 22%）。後から直す前提で進める設計は、
その分の作り直しを買っています。

数値はこの環境で再現していません。採るのは向きだけです。

## ただし「実物を渡す」は、渡し方で結果が変わる

`REF-124` の但し書き——メタデータを与えた側は固いレイアウトになりやすい——は、
`ART-010` の手順の弱点を正確に指しています。**完成した 1 枚の HTML を参考として渡すと、
その寸法・配置・前提ごと複製されうる。** 1 画面では良く見え、画面幅や文字量が変われば崩れます。

したがって、正本の形を 3 段で分けます。下へ行くほど壊れにくく、上へ行くほど作るのが速い。

| 形 | 渡すもの | 複製されるもの |
| --- | --- | --- |
| スニペット | 動作確認した単一 HTML（`ART-010` の形） | 見た目と、**そのときの寸法・前提ごと** |
| 部品 | 名前と用途を持つ再利用単位（`REF-126` のレジストリ項目の形） | 見た目と、使い方の約束 |
| 値 | 色・寸法などを名前と値で持つ（`REF-128` の考え方） | 判断だけ。配置は毎回決まる |

`REF-128`（デザイントークンの交換形式）は 2026-09 時点で**ドラフトであり、仕様自身が
「この版を実装しようとしないこと」と明記**しています。したがってこの形式を採れとは
書きません。採るのは「**見た目の決定は、完成物ではなく名前付きの値としても持てる**」
という考え方だけです。

実務では 3 段を混ぜます。固めたい判断（色・間隔・角丸）は値、繰り返す単位（ボタン・
フォーム・カード）は部品、まだ 1 回しか使っていないものはスニペットで置き、
**使い回した回数が増えたものから下の段へ落とす**。

## 資産に入れる前の確認を、目視で終わらせない

`ART-010` の確認は「ブラウザで開いて、崩れていないか・動くか・不要な部分が残っていないか」
です。これは必要ですが、**落ちている基準をちょうど外しています**。`REF-127` が最も低い
適合率を記録したコントラストと色の使用は、どちらも**人が見て気づきにくく、機械で正確に
判定できる**種類の基準です。

資産に入れる条件を、確認の種類で分けます。

1. **規則で判定できるもの**（コントラスト比、代替テキストの有無、見出しの入れ子、
   フォーカスの可視性、色だけで情報を伝えていないか）。ここは機械に判定させ、
   **通らないものは資産に入れない**。
2. **描画して見るもの**（崩れ、重なり、溢れ、画面幅を変えたときの挙動）。
   `REF-124` の「固いレイアウト」はここで見つかります。1 つの幅で見て終わらせない。
3. **人が読むもの**（その部品が何のためのものか、名前が用途を表しているか）。

この順序が重要なのは、**資産は複製される**からです。1 件の欠陥を入れると、以後その欠陥が
入った画面の数だけ増えます。言い換えると、資産に入れる作業は 1 回ですが、
入れ損ねた確認の費用は後から掛け算で返ってきます。

機械判定の具体的な道具とコマンドは、この手引きでは指定しません。
[../review-design/](../review-design/) の原則どおり、**規則で判定できる部分を決定論的な
検査へ移し、残りだけを人と判断モデルに回す**という配置だけが、ここでの結論です。

## 置き場所と、渡し方

正本をどこに置くかは、**誰が引くか**で決まります。

- **自分だけで使う**: skill に添える参照ファイルにする。Claude Code の skill は本体とは別に
  ファイルを同梱でき、必要になったときにだけ読まれます（`REF-002`）。見た目の正本は
  常時読み込ませる種類の情報ではないので、この形が合います。
- **チームや複数プロジェクトで使う**: 配布の仕組みは既にあります。`REF-126` は自前の
  レジストリを置いて、部品・設定・ルールをエージェントから引ける形で配る方法を示します。
  索引ファイルを 1 つ置けばエージェントが一覧を引けるようになり、推奨は「用途が分かる説明を
  書く」「依存を正確に列挙する」「名前の付け方を揃える」。React 専用ではありません。
- **デザインツール側に正本がある**: `REF-125` は、コンポーネント・変数・レイアウト・
  コードとの対応付けをエージェントへ直接渡す公式の経路です。既にそこに正本があるなら、
  HTML を手で抜き出して二重に持つ理由はありません。

いずれの場合も、**全部をまとめて渡さない**。`REF-126` が索引と項目を分けているのが示すのは、
エージェントに要るのは「何があるか」の一覧と、選んだ 1〜数件の中身だという形です。
部品集を丸ごと貼り付ける運用は、[../heavy-read-delegation/](../heavy-read-delegation/) と
[../token-drain-review/](../token-drain-review/) が扱っている費用の問題に、自分で変わります。

## 入れる前に確かめること

1. 正本は既にどこかにあるか。デザインツール・既存のレジストリ・使っている部品ライブラリに
   あるなら、手で抜き出した複製を増やさない。
2. 置く段はどれか。スニペットから始めてよいが、**2 回目に使った時点で部品へ、
   色と寸法は値へ**、と落とす先を先に決めておく。
3. 資産に入れる条件に、**機械で判定する項目が含まれているか**。目視だけなら、
   最も落ちる基準を見ていない。
4. 渡すのは一覧か、中身か。中身を渡すなら何件までか。
5. 出所が自分でないコードを資産に入れていないか（`ART-010` 自身の注意）。
   スクリプトを含む部品は、見た目の参考としてではなく、実行されるコードとして扱う。
