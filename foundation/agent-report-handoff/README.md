# エージェントの結論を人が受け取る形

**この構成はこの環境で運用していません。** 根拠は提供元の公開資料、1 組織の実践報告、公開された研究で、
ここに書いたのは判断の型です。状態は `experiment` です。

起動条件は「**エージェントに調査や一次対応を任せ、その結果を人が読んで次を決める構成を組むとき**」です。
[../autonomous-loop-delegation/](../autonomous-loop-delegation/) は「何周分を人の確認なしで回させてよいか」、
つまり**どこに人を置くか**を扱います。ここはその後の問い、**置いた人が実際に誤りを捕まえられる形になっているか**です。
変更の中身を 1 行ずつ読まない前提で確かめる側を組む話は [../review-design/](../review-design/) にあります。

## 「最後は人が確認する」は、それ自体では安全策にならない

人を置いた時点で安心する設計を、根拠の無い前提として扱います。査読を通ったレビュー（`REF-066`、
PRISMA に沿って 35 件を整理）が報告している向きは次のとおりです。

- 自動化バイアス（自動の推薦に過度に寄りかかること）は、医療・法務・行政のような重い領域でも観測される
- **説明を足しても、判断の精度は上がらず、偏りも減らない**。説明はシステムの受け入れやすさを上げるだけで終わりうる
- 有効性が示された介入は、説明の工夫ではなく**利用者の関与**、すなわち**検証にかかる手間を実際に増やすこと**

読み替えると、報告を読みやすくする、根拠を併記する、理由を説明させる——これらは
**受け入れやすさを上げる側の変更**であって、見落としを減らす側の変更ではありません。
確認の工程を設計するときは「人が読む」ではなく、**その人が何を操作したら確認したことになるか**まで決めます。

この資料は要旨の範囲で確認しており、本文は購読が要ります。採ったのは上の 3 つの向きだけで、
件数や効果量は移していません。

## 自己申告の確度は、閾値に使えない

エージェントに自分の確信度を言わせる構成（「確定 / 有力 / 推定」のようなラベル）は、
読み手の注意を向ける索引としては役に立ちます。**しきい値として使うと壊れます。**

査読を通った研究（`REF-065`）は、モデルが**誤った答えを出すときにも高い確信度を言語化する**ことを示し、
その信号が中盤から後半の層の特定の回路で書き込まれていることまで特定しています。推論時に介入すると
較正は改善しますが、利用する側から見れば、**既定の出力に付いている確信度は較正されていない**という結論になります。

したがって次のように使い分けます。

| 使い方 | 可否 |
| --- | --- |
| 確からしさの違いを**区別させ**、読む順を決める索引にする | 使える |
| 「確定」なら人の確認を飛ばす、という分岐の条件にする | **使わない** |
| 「推定」の件数を品質指標として数える | 使わない。較正されていない値の集計は意味を持たない |

実践報告（`ART-033`）は調査結果に 3 段階のラベルを付けています。採れるのは
**確からしさを一緒くたにさせない**という設計で、ラベルを信じて自動で次へ流す運用ではありません。

## ラベルの代わりに出させるのは、その場で確かめられる一点

提供元は、エージェントの完了報告は作業した当人の自己申告であり検証ではないとし、
主張させるのではなく**証拠を出させる**——実行したコマンドとその返り値、テストの出力、結果の画面——と
書いています（`REF-055`）。確かめ方の信頼度の順序（規則による判定 > 目視 > 別モデルの判定）も
同じ考え方です（`REF-049`）。

これは前の節の `REF-066` が示した「関与を増やす」に対応する、具体的な実装です。報告に添えるのは
説明文ではなく、**受け取った人がその場で開ける・実行できるもの**にします。

- 根拠にした記録そのものへの参照（どの時間帯のどのログか、どの変更か）
- 再実行できる形（そのまま走らせられるクエリやコマンド）
- 結論を否定しうる観測で、確かめていないもの

3 つ目を省かないことが要点です。確認者が自分で否定の筋を思いつく必要がある形は、
自動化バイアスの下では機能しません。

## 報告は、人が既にいる場所へ出す

実践報告（`ART-033`）は、調査結果を**既存の運用導線のスレッド**へ、段階を分けて書き込む形を採っています。
新しい画面を見に行かせる構成にしていません。これは組織の受け入れやすさの話に見えますが、
前の節と同じ理由で効きます。確認のために別の場所へ移動する手間は、**関与を増やさず摩擦だけを増やす**ためです。

同じ報告は、**責任の範囲をエージェントの構成の側に写す**ことにも触れています。誰が受け取り、
誰が直すのかが曖昧なまま共通基盤に載せると、報告は出続けるのに引き取り手がいない状態になります。

## 人へ渡す前に、入力の重複を落とす

同じ原因から大量に発火する入力をそのままエージェントへ渡すと、人の側では**同じ結論を何度も読む**ことになり、
読み飛ばしが起きます。実践報告は、類似の入力を機械的に判定してまとめてから呼ぶ前処理を置いています（`ART-033`）。

この前処理は取りこぼしを生みます。導入するなら、**間引いた事実と理由を残し、後から数えられるようにします**。
記録が無いと、効いているのか見落としているのかを区別できません。報告されている削減率は 1 組織の
自己申告で、環境によって倍近く違うとされているため、期待値として持ち込みません。

## 自動で手を出す範囲は、別に決める

報告（`ART-033`）では、一次調査までを自動で行い、**修正するかどうかの判断は人**が持っています。
自動で変更まで進むのは、精度が高いと判断できた場合に、人が明示の合図を出したときだけです。

ここは [../autonomous-loop-delegation/](../autonomous-loop-delegation/) の「失敗が高くつく作業は 1 周ごとに
人が受け取る」と同じ結論ですが、順序が逆から来ています。**調べる範囲を広げることと、手を出す範囲を広げることは
別の決定**であり、前者がうまくいったことは後者の根拠になりません。

## 限界

- `REF-066` は要旨の範囲でのみ確認しました。本文は購読が要ります。採ったのは向きだけで、件数も効果量も移していません。
- `REF-065` が評価しているのは指示調整済みのモデル 2 つと 3 つのデータセットで、コーディングや運用の
  エージェントそのものではありません。採ったのは「言語化された確信度は誤答時に過大になりうる」という向きだけです。
- `ART-033` は提供元のブログに載った 1 社の事例で、数値はすべて社内測定の自己申告です。記事自身も初期の
  計測は参考値と断っています。採ったのは構成と判断点であって、所要時間・解決率・削減率ではありません。
- ここに書いた形は、この環境で運用していません。導入するなら、まず**確認者が実際に何を操作したか**が
  残る形にし、前後で見落としが減ったかを測ります。報告が読みやすくなったことを成果にしません。
