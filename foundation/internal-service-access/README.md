# 社内限定のツールに、誰を入れるか

**この領域を開くとき**: エージェントに作らせた内製ツールを、自分以外の人や CI にも使わせることにしたとき。
「社内の人だけ」をどう実現するかを決めるとき。

**この環境では運用検証していません。** 根拠は一次情報 3 件、提供元の調査 2 件、設計段階の実践記事 1 件です。
特定の製品の導入を勧めるものではありません。

隣の手引きとの違いは対象です。[../secret-exposure-layers/](../secret-exposure-layers/) は
**秘密が外へ出る経路**、ここは**外から入ってくる人と機械をどう判定するか**を扱います。

## 3 つの問いに分ける

実践記事（`ART-018`）の骨格が有用なのは、**1 つの「ログイン」を 3 つに割っている**ところです。

| 対象 | 入る根拠 | 失効の根拠 |
| --- | --- | --- |
| 人（ブラウザ） | 組織のアカウントであること | アカウントの停止 |
| 人（API を叩く） | 組織のアカウントであること＋在籍していること | 在籍の確認、期限 |
| 機械・CI | 役割に結び付いた資格情報 | 管理者による取り消し |

分ける理由は失効の経路が違うからです。CI の資格情報を発行した人の在籍に紐づけると、その人が辞めた
ときに CI が壊れます。逆に人向けの資格情報を役割だけに紐づけると、辞めた人の経路が残ります。
**「誰が使うか」と「何の役割として入るか」を別に持ちます。**

この記事は設計と疎通確認までの段階だと著者自身が明記しているので、運用で何が起きるかは別に確かめます。

## 自分で検証を書く場合、何を検証するか

ID トークンは表示できるだけでは信頼できません。提供元の仕様（`REF-149`）が検証項目を列挙しています。
署名（提供元の公開鍵で検証）、発行者、宛先（自分のクライアント ID）、有効期限。
組織の所属（`hd` のような claim）を使うなら、**画面側の絞り込みに頼らず、受け取ったトークンの中身を
サーバ側で照合する**と明記されています。利用者の画面での選択は書き換えられるからです。

## 手前の層に任せても、検証は消えない

認証を自分で書かず、手前のプロキシに寄せる構成があります（`REF-150` はその一例の仕様）。
ここで最も重要なのは、**手前の層が付けた「誰々です」というヘッダを、そのまま信じてはいけない**という
記述です。署名の無いヘッダは、手前の層を迂回して到達できる経路があれば偽造できます。
提供元が挙げる守るべき状況は 3 つです。

1. 手前の層が誤って無効化された
2. 経路の設定が間違っていた
3. 内側（同じ環境の中）から直接到達された

したがってアプリ側には、**署名されたトークンを検証する処理が残ります**。これは特定の製品の話ではなく、
「認証を手前へ出す」構成すべてに当たる形です。手前の層に寄せて減るのはログイン画面と交換処理であって、
検証ではありません。

## 何を「同じ人」の鍵にするか

ここがこの領域で最も間違えやすい部分です。

- 提供元の仕様（`REF-149`）は、**メールアドレスを利用者の一意の鍵に使うなと明示**しています。
  アドレスは変わるからで、変わらない識別子（`sub` にあたる claim）を使えとされています。
- 一方、提供元の調査（`REF-151`）は、**ドメインとメールアドレスは組織の所有権が変わると同じ値に戻る**
  ことを示しました。消滅した組織のドメインを買えば、同じ claim を持つアカウントを作り直せます。
  同じ調査は、推奨されている変わらないはずの識別子にも**ごく一部のログインで変化が観測される**と
  報告しています（割合はページ側にあり、ここには持ち込みません）。報告は一度「修正しない」とされ、
  公開直前に再開されました。2026-10 時点で修正を示す一次情報は確認できていません。

**結論は、どれか 1 つの claim を永続の身元として信頼しない**ことです。社内ツールで同じ形が起きるのは、
組織が消える場合よりも、**退職者のアドレスが新しい人へ再割り当てされる**場合です（この読み替えは
この手引き側の判断で、調査が測った対象そのものではありません）。実践記事（`ART-018`）が
在籍の確認を別経路（管理用の API）で行っているのは、この弱さを補う形になっています。
あわせて、確認できないことを「退職した」と扱わない設計も要ります。設定の欠落で全員を締め出す側へ
倒れると、復旧のときに自分も入れません。

## 機械の資格情報は、持たないのが先

提供元の推奨（`REF-153`）は明確で、**長命の鍵は例外として扱い、別の方法を先に選ぶ**ことです。
外部の環境から使う場合は、その環境の資格情報を短期のものへ交換する仕組みがあり、鍵を配らずに済みます。
鍵をリポジトリへ入れない・利用者間で受け渡さない・一時フォルダに残さない、という禁止も同じページにあります。

**ただし、鍵を無くしても権限は縮みません。** 別の調査（`REF-152`）が示したのは、Workspace の
データへ代理でアクセスする委譲が、**サービスアカウントの識別子に付いていて、特定の鍵には紐づかない**
という設計です。そのアカウントに新しい鍵を作れる権限を持つ人は、既にある委譲をそのまま使えます。
影響範囲は 1 人ではなくドメイン全体です。つまり:

- 自分の側から鍵を消しても、**そのアカウントに鍵を作れるのが誰か**を見ていなければ、何も縮んでいない
- 委譲の範囲（どの API をどこまで）が広いままなら、短期の資格情報にした効果はそこで止まる

この 2 つは [../secret-exposure-layers/](../secret-exposure-layers/) の「持たない層」と同じ話の裏表です。

## 確かめる項目

1. 人・機械・CI のそれぞれについて、**入る根拠と失効の根拠を 1 行ずつ書けるか**。書けない経路は、
   止め方が決まっていない経路です。
2. ID トークンを自分で受けるなら、署名・発行者・宛先・有効期限・所属を**サーバ側で**見ているか。
3. 手前の層に任せているなら、その層を迂回して到達できる経路が無いか。あるなら、署名付きの値を
   アプリ側で検証しているか。
4. 人を同定している値は何か。その値は、人が入れ替わったときに別の値になるか。
5. 機械の資格情報に長命の鍵が要るか。要らないなら作らない。要るなら、誰がそれを作れるか。
6. 委譲を使っているなら、**その委譲が何に紐づき、範囲はどこまでか**。
7. 認証基盤の設定が欠けたとき、締め出しと「本当に権限が無い」をログで区別できるか。
