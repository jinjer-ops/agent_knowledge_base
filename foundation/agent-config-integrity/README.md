# エージェントが読む設定は、誰が変えられて、人に何が見えるか

**この領域を開くとき**: エージェントの設定（指示ファイル、skill、hook、接続設定）がリポジトリに入っていて、
そのリポジトリを自分以外も変えられるとき。他人のブランチを手元に取り込んで見るとき。
あるいは、issue や PR のコメントでエージェントを起動する構成にするとき。

**この環境では運用検証していません。** 下の内容は提供元の公開仕様と公開された実証から読み取ったもので、
保護設定も CI 上の実行も、ここで動かして確かめていません。道具の導入も勧めていません。

隣の領域との分かれ目です。[../permission-boundary-layers/](../permission-boundary-layers/) は
**自分の機械で確認を外したとき何が強制として残るか**、[../change-intake-gate/](../change-intake-gate/) は
**本線に入る瞬間の門**、[../secret-exposure-layers/](../secret-exposure-layers/) は**秘密が外へ出る経路**です。
ここはその手前で、**エージェントが従うファイルがリポジトリ側から入ってくる経路**と、
**誰がエージェントを起動できるか**を扱います。問いは 3 つです。

1. 取り込んだだけで、何が走るか
2. 人のレビューに、何が見えないか
3. 誰が変えられて、誰が起動できるか

## 1. 差分を読む前に、もう走っている

**信頼の確認は、capability を与える設定には掛かりますが、hook には掛かりません。**
提供元の一覧（`REF-145`、確認日 2026-10-31）を、効き方で並べ替えるとこうなります。

| リポジトリが持ち込むもの | 親フォルダしか信頼していないとき | `-p` / SDK（そのフォルダを一度も信頼していない） |
| --- | --- | --- |
| **設定ファイルの hook、`env`、helper コマンド、プロジェクト skill の hooks と `allowed-tools`** | **使われる** | **使われる** |
| `allow` ルール・追加ディレクトリ | 使われない（確認の画面が出る） | 使われない（警告だけ） |
| 接続設定（`.mcp.json`）のサーバ | 接続前に確認される | **確認なしで接続される** |
| 下位エージェントの frontmatter にある hook・接続設定 | 使われない | 使われない |

**そして信頼は、git リポジトリの root に紐づきます**（`REF-145`）。一度信頼した自分のリポジトリの中で
ブランチを取り替えれば、その中身は同じ信頼の下に入ります。つまり**「自分のリポジトリだから安全」は
成り立ちません**。危険なのはフォルダの出どころではなく、**そのブランチを誰が書いたか**です。

ここから、順序が 1 つ決まります。

> **他人のブランチを手元のリポジトリへ取り込んでから、そこでエージェントを起動しない。**
> 先に差分を読む。読むときは、エージェントを動かさない経路で読む。

取り込む前に名前だけでも見ておくべき対象は、設定ファイル、hook、skill、接続設定、
そしてワークフローです。`allowed-tools` は skill 側に書けるので、**skill を 1 つ足すことが
権限を先に与えることになります**（`REF-145`）。

この性質は、以前この文書群で `-p` の実行の話として記録していました。**訂正です。**
`-p` はこの表の右の列を強めるだけで、左の列の 1 行目——hook と `env` が走ること——は
対話セッションでも同じです。製品ごとの書き方は [../claude-code/README.md](../claude-code/README.md) にあります。

## 2. レビューに見えないもの

指示ファイルは、**人には見えずモデルには読める**形で書けます。
2025-03 の開示（`REF-239`）は、コーディング支援の規則ファイルにゼロ幅結合子と双方向テキスト記号で
指示を埋め、生成されるコードへ外部のスクリプトを差し込ませる実証を公開しました。報告のうち、
設計に効くのは次の 2 点です。

- 埋め込んだ文字は**プラットフォームの PR 承認画面でも見えなかった**。差分を読む運用は、この層を素通りします。
- 規則ファイルは**フォークを越えて残る**ので、下流へ伝播します。

当初、提供元の回答は「利用者の責任」でした。**ただし、ここには既にもう 1 つ層が足されています。**
プラットフォーム側が 2025-05-01 に、隠れた Unicode テキストを含むファイルへ警告を出すようになり、
変更履歴には**見た目と違う意味に解釈されうること、特に AI がそう読みうること**が理由として
明記されています（`REF-240`）。

> **自前の検査を書く前に、既定で出る警告が何を対象にしているかを見る。**

自前の検査が要るのは、その警告が届かない経路です。手元のエディタ、プラットフォームの外から来る
指示ファイルや skill、配布された plugin。そして検査を足したときの読み方は、この文書群が
秘密の検査について既に書いているものと同じです——**通過は「設定した規則が反応しなかった」以上の
意味を持ちません**（[../secret-exposure-layers/](../secret-exposure-layers/)）。

## 3. 誰が変えられるか

変更できる人を絞る仕組みは広く使われていますが、**静かに失敗する条件が複数あります**（`REF-234`、
確認日 2026-10-31）。

- 判定に使われるのは**取り込み先のブランチにあるファイル**です。PR の側で書き換えても、その PR の
  判定には効きません。これは守る側に有利な性質で、**そのファイル自身にも所有者を定めよ**と
  公式が書いています。
- **必須になるのは、保護設定の側で「所有者のレビューを必須にする」を有効にしたときだけ**です。
  ファイルを置いただけでは、通知が飛ぶだけで門にはなりません。
- **最後に一致したパターンが勝ちます。** 後ろの行で前の行が覆ります。設定を守るつもりの行を
  上の方に書いて、下に広いパターンを足すと、黙って無効になります。
- **構文が無効な行は飛ばされます。** 存在しない利用者や、書き込み権の無い相手を指定した場合も、
  所有者が割り当てられません。いずれもエラーにならずに**効かないだけ**です。

迂回できる人がいるかどうかは、この仕組みとは別に決まります。保護設定は既定では管理者に適用されず、
明示的に迂回を禁じて初めて掛かります。この条件と、1 人運用で自分が管理者である場合の帰結は
[../change-intake-gate/](../change-intake-gate/) に書いてあります。

## 4. 誰が起動できるか

エージェントを CI 側で動かし、issue や PR のコメントで起動する構成にすると、
**起動できる人の集合が、リポジトリを読める人の集合に近づきます。**

提供元の公式統合には、起動の前に 2 つの門があります（`REF-236`、確認日 2026-10-31）。

- **起動した利用者に書き込み権が要る**（例外を設けるには自前のトークンを渡す）
- **bot は既定で拒否される**（ループを防ぐため。定期実行も、その予定を最後に変えた利用者に帰属するので、
  それが bot なら明示が要る）

この 2 つは強制側の門です。一方、**権限の方はまとめて付きます**。この統合が使うのは内容・issue・PR の
3 つですが、アプリを入れると workflow の読み書き、リポジトリの hook の読み書き、Actions の読み書き、
管理情報の読み取りまで含む一式を受け入れることになり、**部分的に承認することはできません**。
最小限にしたい場合は、必要な 3 つだけを持つ自前のアプリを作る、と公式が書いています（`REF-236`）。

ワークフロー側の一般則は、基盤の公式資料がそのまま使えます（`REF-235`）。

| やること | 理由 |
| --- | --- |
| 既定のトークン権限を読み取りだけに落とす | 広い既定のまま走る |
| `pull_request_target` などの特権付きの起動で、未信頼のコードをチェックアウトしない | 秘密と書き込み権を持ったまま他人のコードを走らせることになる |
| 未信頼の入力（題名、本文、コメント）を、スクリプトへ直接展開せず中間の環境変数に入れる | 文字列として展開するとコマンドになる |
| 第三者の処理は完全なコミット識別子で固定する | 同じ名前の指す中身が後から変わる |

**そして、書き込み権を持つ人は、そのリポジトリの秘密を全部読めます**（`REF-235`）。
前段の「起動には書き込み権が要る」という門は、裏から読むと**その集合の全員が秘密に届く**という意味です。
公開リポジトリでは、フォークからの PR の実行に秘密が渡らないという制限が別に掛かります（`REF-236`）。

秘密を片付けるときの順序も、この文書群の既存の結論と同じです。**設定から秘密を消しても、
その資格情報は有効なままです**（`REF-236`）。失効させるのは発行元の側です
（[../secret-exposure-layers/](../secret-exposure-layers/)）。

### この構成が測られている

査読前ですが、ここを正面から測った報告があります（`REF-238`、2026-06）。実在のリポジトリ上で
4 つの提供元の構成に対し 11 種類の攻撃（設定ファイルへの注入、資格情報の窃取、判断の操作、
可用性の妨害）を試し、**どの提供元も既定の構成で少なくとも 1 種類に対して脆弱**でした。
著者の結論は、**最も重大な脆弱性は構造的で、CI/CD が資格情報と設定ファイルをどう扱うかから生じる**、です。

この 2 つは、まさにこの手引きの第 1〜4 節が扱っているものです。**道具の選択ではなく、
設定ファイルと資格情報の扱いの方に効き目がある**、という向きが独立に支持されています。

## 5. 確かめる項目

この環境で未確認のものを含みます。

1. **他人のブランチを、自分のリポジトリへ取り込んでからエージェントを起動していないか。**
   起動しているなら、その順序を逆にします（`REF-145`）。
2. **エージェントが読むファイルの一覧を書き出せるか。** 指示ファイル、skill、hook、接続設定、
   ワークフロー。書き出せないなら、所有者を定めることもできません。
3. **所有者を定めるファイルに、そのファイル自身が入っているか**（`REF-234`）。
4. **その仕組みが「必須」になっているか。** 保護設定側の項目が有効でなければ、通知だけです（`REF-234`）。
5. **隠れた文字について、既定でどの警告が出るかを確かめたか**（`REF-240`）。自前の検査は、
   その外側を対象にします。
6. **CI でエージェントを動かすなら、起動できる人の集合と、秘密を読める人の集合を書き出したか**
   （`REF-235`、`REF-236`）。
7. **アプリに与える権限が、使う機能より広くないか**（`REF-236`）。広いなら、狭い自前のアプリを作るか、
   広いまま受け入れると決めて記録します。

## 6. この入力で採らなかったもの

入口の記事（`ART-059`）は、この領域の脅威を具体的に列挙した点で入口としてよく機能しました。
ただし**代表にはしていません**。検証が 1 アカウント・公開のダミーリポジトリ・対照なしで、
採否を決める 4 点（取り込みで何が走るか、不可視文字に既定の層があるか、所有者の指定が静かに失敗する
条件、CI で誰が起動できてどの権限が付くか）の根拠が、すべて公式と一次の開示の側にあるためです。

2 点、記事と一次情報で食い違いました。

- 記事は秘密の検出を有料の追加機能として扱い、別の道具を勧めていますが、**公開リポジトリでは
  検出と push 時の遮断が既定で使えます**（`REF-143`）。ただし既定の対象は提供元の型が決まった資格情報に
  限られるので（`REF-144`）、別手段が不要という意味にはなりません。
- 不可視文字の検査は、記事では自前のスクリプトとして置かれていますが、
  2025-05 以降はプラットフォーム側に警告があります（`REF-240`）。

記事が挙げる脆弱性の受け取り口（公開の連絡先ファイル）は、エージェント固有の話ではないので
ここでは扱っていません。

## 7. 限界

- **この環境では何も設定していません。** 所有者の指定も、保護設定も、CI 上での実行も未経験です。
- `REF-239` は 2025-03 の開示で、対象は別の 2 製品です。採ったのは**機構**（人に見えずモデルには読める）と
  **フォークを越えて残る**ことだけで、製品ごとの現在の挙動は確かめていません。
  `REF-240` によって、少なくともプラットフォームの表示側は当時と変わっています。
- `REF-238` は査読前で、提供元名も攻撃の内訳も採っていません。採ったのは
  「既定の構成で全提供元が少なくとも 1 種類に脆弱だった」という向きと、著者の構造的という結論だけです。
- 設定項目名・既定値・権限の一覧は版に依存します。使う時点の公式資料で読み直してください。
- 実行ファイル（検査スクリプト）は置いていません。この環境で一度も走らせていないためです。
