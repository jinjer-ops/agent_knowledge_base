# Presentation authoring

資料は、用途に応じて表現形式を選びます。

- ブランド済み資料の更新、共同編集、PowerPointでの受け渡しが必要な場合は、ネイティブなスライドのDOM・オブジェクトモデル・テーマを正本にする。
- 技術発表やブラウザで配布する資料は、HTML/CSSまたはReveal.jsを有力な選択肢にする。
- ドラフトの反復が主目的なら、HTML/CSSを先に編集・表示確認してから、必要な場合だけ最終形式へ変換する。

Markdownは構成案として使えますが、レイアウトの正本ではありません。変換先の形式で最終表示を確認し、テキスト溢れ、重なり、判読性、画像、フォント、編集可能性を確認します。

ただし、この確認はすべて目視です。**目視で気づきにくい側に、実際の欠落は寄っています。** 54 名のデザイナーが作った画面と AI に生成させた同等物を比べた査読済みの測定（`REF-127`）では、適合率が最も低かったのはコントラスト比と「色だけで情報を伝えていないか」という、いずれも規則で正確に判定できる項目でした。判読性を目で見るだけでは、ここは通ります。配色と図の色分けについては、機械で判定できる項目を目視とは別に確認します。

見た目の方向性を毎回言葉で指示し直している場合は、形式の選択ではなく正本の持ち方の問題です。[../design-asset-canon/](../design-asset-canon/) を読みます。

## 正本をテキストにする前に、下流を確かめる

テキスト（Markdown）を正本にすると、版管理できる、コードと数式が書きやすい、GUI で箱を置かなくてよい、という利点があります（`ART-002`）。この判断で決まるのは**作り方ではなく、出した後にできることです。**

出した後に誰かが編集する必要があるなら、テキストを正本にする前にその経路を確かめます。Markdown から PowerPoint へ出す代表的な実装（`REF-130`）では、既定の変換結果は**描画済みの背景画像**であり、受け取った側で文字も図形も編集できません。編集可能な形式で出す選択肢は実験的な位置づけで、ブラウザに加えて別のオフィススイートの導入が要り、複雑なテーマではエラーか不完全な結果になり、再現性は通常の変換より下がり、**発表者ノートは変換されません**。提供元自身が、見た目の維持が重要なら勧めないと書いています。

したがって判断の軸は「PowerPoint が使いにくいか」ではなく、**受け取る人が編集する必要があるか**です。編集が要るならネイティブ形式を正本にし、要らないならテキストを正本にできます。

配布が PDF で足りるなら、ブラウザのスライド実装にも公式の経路があります（`REF-131`）。クエリ文字列を付けてブラウザの印刷ダイアログから書き出す方法で、**動作が確認されているのは Chrome と Chromium だけ**、入りきらないスライドは複数ページへ展開され、その上限は設定値で決まります。コマンドラインから行う場合は別の変換ツールが案内されています。手順と前提が版に依存するため、使う前に一次情報で確かめます。

## 溢れは、どの経路でも静かに起きる

形式を変えても消えない故障が 1 つあります。**入りきらない内容が、警告なく失われること**です。

- ブラウザのスライド実装は、入りきらない内容を黙って切ります。これは推進側の記事（`ART-002`）が自分で挙げている唯一の限界です。
- 同じ系統の上位ツール（`REF-132`）は、溢れに対して「字を小さくする」「その部分をスクロールさせる」という名前付きの手当を用意し、全体にも掛けられるようにしています。手当があるということは、**既定では何もされない**ということです。
- ネイティブ形式を生成させる場合も同じで、提供元の公式手順（`REF-129`）は禁止事項の一つに「テキストを溢れた状態のまま残さない」を挙げています。

したがって溢れの確認は、形式の選択とは独立に必要です。**確認するのは、最終形式で描画した結果**です。ソース側が正しく見えることは、出力側で切れていないことの証拠になりません。

## エージェントに資料を作らせるときの検証

提供元が公開している資料生成の公式手順（`REF-129`）は、作る経路と**検証の段**の両方を定めています。この環境では動かしていませんが、検証の段の構成はそのまま判断の型として使えます。

| 段 | 何を見るか | 目視で代替できるか |
| --- | --- | --- |
| 内容 | 生成物からテキストを抽出し、入れたはずの内容が入っているか | できる（ただし手間が増える） |
| **ファイル** | **成果物が壊れていないか**を検査スクリプトで判定する | **できない** |
| 見た目 | 全スライドを画像へ書き出して、溢れ・重なり・配置を見る | これが目視の段 |

重要なのは**真ん中の段**です。生成されたオフィス形式のファイルは、見た目が正しくてもファイルとして壊れていることがあり、同じ手順は壊す原因になる具体的な操作（影の負のオフセット、グラデーション塗り）を名指しで禁止しています。目視だけの運用は、この段が丸ごと抜けています。**画像へ書き出して確認する運用をしているなら、ファイル検査の段を同じ場所に足すのが最小の改善です。**

経路の選択についても、同じ資料が根拠を 1 つ与えます。この提供元は、新規作成と、テンプレート流用・既存ファイルの編集とで**別の実装**を使い、後者では汎用のスライド操作ライブラリを避けています。理由として挙がっているのは、そのライブラリではスライドの複製ができないといった具体的な制限です。**既存のスライドを編集して作らない**という方針（このページの冒頭の判断）は、この点から見ても妥当です。

なお、この公式手順は公開されていますが、提供元自身が**ソースは見られるがオープンソースではない**と明記しています。採用する場合は利用条件を先に確かめます。
