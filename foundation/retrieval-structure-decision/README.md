# 事前に構造を作るか、その場で探すか

**この手引きは未検証です。** 下の測り方はこの環境で一度も実行していません。状態は `experiment` で、
特定の構成の導入を勧めるものではありません。

## 何の問題を扱うか

起動条件は、**探索の費用か答えの正確さに不満があって、索引・ナレッジグラフ・オントロジー・
生成した文書を作ろうと考えたとき**です。この種の提案は「トークンが 10 分の 1 になる」といった
倍率とともに流通します。倍率を評価する前に、作るかどうかを決める材料を置きます。

作る対象は 1 種類ではありません。**関係を辿る構造**（索引・グラフ・オントロジー）、
**読ませる散文**（生成した wiki・リポジトリ文書）、**決めた項目への抽出**（スキーマに沿った値と
その出典位置）では、効く問いも失敗の仕方も違います。順に、下の 3 節、「生成した文書を置く場合」、
「項目として取り出す場合」で扱います。共通するのは、**作った物を誰がいつ更新するか**を先に
決めないと、どれも誤答の源になることです。

ほかの手引きとは層が違います。[instruction-upkeep/](../instruction-upkeep/) は**常時載るもの**、
[heavy-read-delegation/](../heavy-read-delegation/) は**1 回ごとの大きい読み取り**、
[token-drain-review/](../token-drain-review/) は**自分の入力以外で減る分**です。ここで扱うのは
**取りに行く経路そのものを作り替えるか**です。

## この環境の既定は、都度の探索である

提供元の説明では、取得のやり方は 2 つに分かれます（`REF-018`）。すべてを事前に処理して埋め込み
検索に備える方式と、**軽い識別子（ファイルパス、クエリ、リンク）だけを持ち、実行時に道具で
読み込む**方式です。この製品は後者を軸にした**ハイブリッド**で、指示ファイルは先に文脈へ載せ、
`glob` と `grep` で環境を動き回ります。提供元は「速さのために一部を先に取り、残りは自律的に
探索するハイブリッドが最も効く」と書き、同時に**実行時の探索は事前計算より遅い**こと、
事前計算側には索引の陳腐化が付くことを挙げています。

大規模なコードベース向けの公式の手引き（`REF-008`）も、**独自のグラフを作れとは書いていません**。
挙がっているのは次の順です。

| やりたいこと | 公式が挙げる手段 |
| --- | --- |
| 定義や呼び出し元を、木を舐めずに引く | language server に繋ぐ code intelligence プラグイン |
| 生成物・ベンダ取り込みを読ませない | `permissions.deny` の `Read` 規則 |
| 関係ない指示を載せない | 階層化した指示ファイル、`claudeMdExcludes` |
| 作業に要る範囲だけ展開する | worktree の sparse な取得 |
| 領域固有の手順を必要なときだけ載せる | 領域ごとの skill |
| 既に社内に検索・RAG の索引がある | **MCP の道具として見せて引かせる** |

最後の行が要点です。公式が想定しているのは**既にある索引を使う**ことであって、エージェントの
ために新しく作ることではありません。ここから最初の分岐が出ます。

> **関係や定義を辿りたいだけなら、グラフを作る前に language server がある。**

## まず試すのは公式の code intelligence プラグイン

この経路は公式のプラグインとして用意されています（`REF-038`）。提供元が維持するものが 12 言語分
（C/C++、C#、Go、Java、Kotlin、Lua、PHP、Python、Ruby、Rust、Swift、TypeScript と JavaScript）あり、
ほかに Shopify が維持する Liquid が公式の一覧に載っています。入れると、**記号で定義と参照を引く
読み取り専用の道具**が増え、編集のたびに型の誤りや取り込み漏れが診断として返ります。
テキスト検索で記号を探す代わりになります。

導入の前提と制限も公式に書かれています。入れる前にこの 4 点を確認します。

- **言語サーバーのバイナリは別に入れる。** プラグインは起動の仕方と拡張子を伝えるだけです。
  入れたあと、`claude` を起動するシェルの `PATH` に載っているかを確かめます（PowerShell なら
  `Get-Command <バイナリ名>`）。
- **クラウドのセッションでは起動しません。** そこでは診断も記号での探索も得られません。
- **モノレポでは、解決できている取り込みを未解決と報告する誤検出が起こりうる**と troubleshooting に
  挙がっています。
- **索引中はメモリが増えます。** 索引は言語サーバーが持つもので、こちら側で保守する成果物は増えません。
  これが、自前のグラフとの最大の違いです。

一覧に無い言語でも、`.lsp.json` を書けば自前のプラグインとして繋げられます。

ここまでで足りるなら、**作る話はここで終わります。**

## 構造が効く問いと、効かない問い

統一した条件での独立比較（`REF-036`）は、どちらかが一貫して勝つわけではないと報告しています。

| 問いの種類 | 通常の RAG | グラフ側 |
| --- | --- | --- |
| 単一ホップ（NQ） | **64.78%** | 63.01%（グラフ側の最良） |
| 多段（MultiHop-RAG） | 67.02% | **70.27%** |
| 時間・推論を要する問い | 25.73% | **49.06%** |

論文の言葉では「RAG and GraphRAG exhibit complementary behaviors rather than a consistent winner」
であり、結論は両者を排他的な選択として扱うなというものです。

**単一事実の問いでは構造は効かず、わずかに落ちます。** 同じ向きの観察が送信記事側にもあります
（`ART-016`）。単一事実の問いに 16 ノードの部分グラフを渡すと周辺のノイズが混ざり、精度が落ちた
と報告されています。

## 作ること自体が、損失と費用を持つ

同じ独立比較から（`REF-036`）。

- **抽出で落ちる。** HotpotQA では、構築した知識グラフに**正解実体の約 65.8% しか現れません**。
  グラフは、抽出時に拾えなかったものを後から返せません。
- **構築が高い。** 構築時間は通常の RAG の 135 秒に対し 5,560〜7,702 秒。知識グラフ方式は検索も
  14,434 秒かかっています。
- **併用は効くが安くない。** 問いの種類で振り分ける方式が +1.1%、両方引いて連結する方式が +6.4%。
  後者は計算量が倍になります。

## グラフにすると、トークンが増えることもある

ここが、この話でいちばん見落とされる点です。コードをグラフのデータベースにしてエージェントに照会
させる構成を評価した一次情報（`REF-039`）は、**トークンが減るどころか増えた**と報告しています。
原文では「larger and more flexible action spaces」の利点と引き換えに「it also incurs increased
token costs」とされ、理由は 2 つ挙がっています。

- **照会の結果の長さを制御できない**（the length of the query outcomes is not controllable）。
- **実行できる照会を書けずに堂々巡りに入ることがある**（sometimes encounters loops where it fails
  to generate executable graph queries）。

倍率は**何と比べるか**で変わります。同じ表の平均トークン（GPT-4o）から読み取れるのは次のとおりです。

| 比較対象 | CrossCodeEval Lite | SWE-bench Lite | EvoCodeBench |
| --- | --- | --- | --- |
| 単純な検索（BM25） | 1.47k | 14.76k | — |
| 別のエージェント方式 | 10.74k | 76.01k | 21.41k |
| グラフのデータベース照会 | **22.16k** | **102.25k** | **24.49k** |

単純な検索と比べれば約 7〜15 倍、別のエージェント方式と比べても約 1.1〜2.1 倍です。**どの比べ方でも
減っていません。** 精度の方は、補完課題で 27.90%（別方式 21.20%）と上回る一方、SWE-bench Lite の
解決率は同等でした。つまりこの構成で買えたのは**一部の課題の精度**であって、費用ではありません。

> **「グラフにすればトークンが減る」は、一般には成り立ちません。** 減る構成と増える構成があり、
> 分かれ目は照会の結果の長さを押さえられるかどうかです。

**範囲の取り違えにも注意します。** よく引かれる GraphRAG の一次情報（`REF-037`）が対象にしているのは
**クエリ指向の要約**、すなわち「この資料群の主題は何か」という全体への問いで、報告されているのは
約 100 万トークン規模の資料に対する包括性と多様性の改善です。多段の質問応答やコードベースの探索の
根拠としてそのまま引くのは、論文の対象範囲を超えています。

## 公開された倍率は、何と何の比か

この種の記事は大きな倍率を見出しに置きます。倍率を見たら、**分母と分子が何か**を先に読みます。

ある導入記録（`ART-019`）は「2000 分の 1」を掲げていますが、その中身は**1 回の取得で文脈に載る量の比**
です。レビューのために全文を読ませると変更内容しだいで 9,272〜142,188 トークン、グラフ経由だと
約 70 トークン。大きい方を小さい方で割った値が見出しの倍率です。**タスク全体の消費を測った値では
ありません。**

もう 1 つ、同じ記録に目を引く観察があります。グラフ経由の約 70 トークンは、**6 コミット連続で
同じ値**でした。著者はその安定を肯定的に書いています。ただし、変更の大小に関係なく出力の大きさが
変わらないということは、その出力が**変更固有の詳細を運んでいない**ということでもあります。
固定の長さに切り詰めた応答がタスク全体では高くついた、という提供元の実測もあります
（[../cost-change-evaluation/](../cost-change-evaluation/)）。

同じ記録では、意図的に仕込んだ 3 種の脆弱性（SQL インジェクション、秘密鍵の直書き、`eval`）が
**全件すり抜けています**。著者はその原因を、組み込まれた静的解析のルール本数（その言語向けが 8 本で、
設定で広げる手段が無い）に帰しており、約 70 トークンの文脈のせいだとは書いていません。
**そこまでが記事の述べている範囲です。** ここから言えるのは次の一点に尽きます。

> **この記録は、縮めた文脈でも全文読みと同じ結論に達するかを測っていない。** 倍率と品質が、
> 同じ実験の中で結び付けられていない。

だからこそ、下の測り方では**被覆**を独立に判定します。

### 費用と品質を同じ実験で出した数字

数少ない例として、グラフ照会と素のファイル探索を 31 の実リポジトリで比べ、**3 つを同時に報告した**
ものがあります（`REF-040`）。トークンは約 10 分の 1、道具の呼び出し回数は約 2.1 分の 1、そして
**回答品質は 83%、素の探索は 92%**。言語別では、31 言語のうち 19 言語でグラフ照会が同等以上でした。

品質の差は約 9 ポイントです。これを「安い」と見るか「落ちた」と見るかは用途によりますが、
**少なくとも両方の数字が並んで初めて判断できます。** 片方しか出していない比較は、良し悪しを
決められません。

なお、この数字は提案手法の作者ら自身による評価です。方向（費用と品質は同時に動く）は採れますが、
値そのものは自分の環境のものではありません。それでも、見出しの倍率だけを出す記事より扱いやすい
形になっています。入口になった記事（`ART-008`）が参考になるのは、まさにこの両面を並べて紹介して
いる点です。

## 生成した文書を置く場合

構造を作るもう一つのやり方は、**取り込み時に一度ソースを読み、その結果を Markdown の文書として
残しておく**ことです（`ART-007`）。質問のたびに素材から組み立て直す代わりに、費用を質問時ではなく
取り込み時に寄せる、という考え方です。グラフと違って成果物が人にも読める散文になるため、
更新の担当を人が持てます。

### 効く範囲は測られている

この方式には、下流の課題で測った一次情報があります（`REF-041`）。SWE-bench 由来の 12 リポジトリ
（Python）に対し、人手の文書・対話で書かせた文書・リポジトリ単位の自動生成 4 手法を比べ、
生成した文書を渡したときの解決率を測っています。

| 測ったこと | 文書なし | 最良の生成文書 |
| --- | --- | --- |
| SWE-Agent の課題解決率（57 件） | 43.86% | **52.63%** |

見出しに出る「20.00% 改善」は**相対値**です。絶対差は 8.77 ポイント、57 件中およそ 5 件で、
**n が小さい**ことを見積もりに入れます。向き（効く）は採れますが、幅は自分の環境のものではありません。

同じ論文が、**文書だけでは足りない**ことも同時に出しています。

| 問いの種類 | 文書だけ | 文書 + ソースコード |
| --- | --- | --- |
| その機能が書かれているか | 63.75% | **72.66%** |
| 関係するファイルを特定できるか | 70.19% | **78.22%** |
| 実装の詳細を埋められるか | 26.87% | **28.41%** |

論文の言葉では「source code offers complementary value to software documentation」であり、
限界として「limited navigation ability and struggles to provide comprehensive details」を挙げています。

> **生成した文書が効くのは「どこを見ればよいか」で、「何がどう書いてあるか」ではありません。**
> 実装の詳細を問う欄は、文書を足しても 3 割に届いていません。

これは `REF-036` の「排他的な選択として扱うな」と同じ向きです。**文書はソースの代わりではなく、
ソースへの入口**として置きます。置いたうえで全文読みを禁止すると、この表の右列を捨てることになります。

### いちばん大きい失敗様式は、文書が間違っていること

生成した散文には事実誤りが混ざります。コードから説明文を生成させて実行で検証した研究（`REF-043`）は、
評価した中で**最良のモデルでも約 5 分の 1 の説明に、実証できる不正確さが含まれていた**と報告します。
誤りの型は、目的の取り違え、**実在しない要素への言及**、呼び出し元の文脈の欠落、実装の読み違いでした。

この研究は 2024 年のモデルと Java のメソッド単位の評価なので、**採るのは向きだけで、値は移せません**。
それでも設計に効く点が一つあります。**間違った文書は、文書が無い状態より悪くなりうる**ことです。
索引が古いときは取りこぼし（取得が落ちる）ですが、文書が間違っているときはエージェントが
「分かった」と判断して探索をやめます。前節の charter で言えば、**被覆は通るのに正答が落ちる**形で
現れ、構造を足しても直りません。

### 半年運用した記録では、使われたのは本文ではなく構造だった

作る前の比較ではなく、**作って半年使った後**の記録があります（`ART-030`）。対象は個人の記録
（購読・切り抜き・日誌）で、コードベースではありません。約 15 万件のうち能動的に関わった約 6,000 件を
処理し、実際に出典になったのは約 1,700 件、全体の約 1% でした。タグ 9,000 種のうち 20 件以上の記録が
付いたものをページにして 170 ページという規模です。

著者の結論は、**生成した本文を 1 文字も使っていなかった**、というものです。本文は
「どこかの技術記事のまとめを読んでいるようで、驚くほど読み返す気にならない」状態で、原因として
**要約をさらに要約させる処理**を挙げています。個別の記録 10 件の共通部分だけが残り、
「タグの固有性がほとんど残っていません」。

代わりに使われていたのは、本文ではなく**本文から派生した 2 つの表示**でした。

| 使われた表示 | 何を出すか | なぜ効いたか |
| --- | --- | --- |
| 時系列の一覧 | 増えているもの／**しばらく触れていないもの** | 何から離れたかは自覚できない。盲点を機械的に出せる |
| 関連図 | 1 ページを中心に、記録を共有するページを周囲に置き、触れると中心が移る | 関心の空間を辿れる |

決め手は著者自身の指摘です。**本文の生成を止めても、この 2 つの表示は同じものが出ます。**
つまり価値を生んでいたのは文章ではなく、**分類と構造化**の側でした。実際に効いた LLM の使い方は、
保存時のタグ付けと、表記ゆれの統合（埋め込みで近い候補を出し、統合するかを LLM に判断させる）です。

失敗として記録されている 2 つが、そのまま設計の指針になります。

- **本文の中にリンクを書かせる案は全滅した。** 生成させたところ全ページでリンクがゼロになり、
  リンク用のテーブルも抽出処理も捨てて、**記録の共有関係だけで関連を判定する方式**に変えています。
  関連は生成物から取り出すのではなく、**実際に共有しているものから導く**ほうが成立しました。
- **選定の閾値を順位で決めると止まる。** 「上位 10 件」という相対の基準では 19 日間ページが
  増えませんでした。「20 件以上」という絶対値に変えて動き出しています。

これは著者 1 人の記録で、対照実験ではありません。対象も個人の記録でコードベースではないため、
値は移せません。それでも、`REF-041` が下流の成績で示した向き（上がるのは「どこを見ればよいか」で、
実装の詳細ではない）と**独立に一致します**。両者を並べると次のようになります。

> **生成した文書の価値は、文章そのものよりも、文章を作る過程で付いた構造の側にある。**
> 文章を置くこと自体を目的にすると、読み返されない成果物が増えます。

### なぜ束ねると固有性が落ちるのか

上の「要約をさらに要約させると固有性が消える」という観察には、査読を経た裏付けがあります
（`REF-044`）。複数の資料をまとめさせた出力の誤りを 5 つのモデルで分類・計測した研究で、
誤りの型は 4 つです。

| 型 | 原文の定義 |
| --- | --- |
| Pedantic | 正しいが、新しい情報を足さない |
| Instruction Inconsistency | 主題と無関係、重複、または共有されていない |
| Context Inconsistency | 単純化や誇張によって、細部が微妙に歪む |
| Fabrication | 提示された情報と矛盾する、または支持されない |

**1 行目が、運用記録の「読み返す気にならない」と同じ現象です。** 事実として誤ってはいないのに
価値が無い、という失敗は、正しさだけを見る検査では捕まりません。幻覚の割合は領域によって差が大きく、
会話では最大 75%、ニュースでは最大 45% と報告されています。

もう一つ、直感に反する結果があります。**まとめる文書を増やしても誤り率はほとんど変わりません
（±5%）。変わるのは再現率で、こちらは下がる傾向にあります。** つまり束ねることで起きるのは
「間違いが増える」ことではなく、**「落ちるものが増える」**ことです。だから、生成した文書を
信用できるかどうかを誤りの有無だけで判定すると、本当の損失を見逃します。

評価は 2024 年世代の 5 モデルで、対象はニュースと会話です。値は移せませんが、型の分類と
「誤り率は一定のまま再現率が落ちる」という向きは、文書を生成するどの構成にも当てはまります。

### 陳腐化させないための最小の仕組み

文書を置くと決めたなら、更新の設計が本体です。公開されている実装の一つ（`REF-042`）は、
この問題に次の形で答えています。道具の採用を勧めるものではなく、**自前で用意する場合にも要る項目**
として読みます。

| 項目 | その実装がしていること |
| --- | --- |
| 根拠の紐付け | 記述を、版付きのソース位置（`repo://<path>#L40-L82` 形式）に結び付ける |
| 差分での更新 | 変更と既存の根拠を突き合わせ、影響の無い更新ではモデルを動かさない |
| 自動実行 | CI で文書だけの変更要求を作る |
| 検証の記録 | 根拠の再確認を通ったページにだけ、確認済みの印と版を残す |
| 読む範囲の制限 | 除外ファイルで読ませない場所を指定する |

**最小構成は上の 1 行目と 2 行目です。** 記述が「どのファイルのどの行に由来するか」を持っていれば、
その行が変わったときに見直す対象を機械的に出せます。由来を持たない文書は、全体を作り直すか、
古いまま置くかの二択になります。

同じ資料は、避けられない限界も明記しています。**除外の指定は読む境界であって、許可された証拠から
話題が推論されないことは保証しません。** 外に出せない内容があるリポジトリでは、除外設定を
秘匿の手段として当てにしません。送信される計測情報が既定で有効になっている点も、
入れる前に確認する項目です。

### 費用の目安

入口になった記事（`ART-007`）が出している唯一の実測は、**初期化だけで約 1.5 ドル**（当時の上位モデル）
という1件です。小さいリポジトリでの1回の値なので規模の目安にしかなりませんが、**取り込み時に
費用を寄せる方式では、その費用がゼロではなく前払いで発生する**ことは確かめられます。見積もりには
初回の生成に加えて、変更のたびに走る差分更新の分を入れます。

## 項目として取り出す場合

前節までの 2 つは、どちらも「読ませるもの」を作る話でした。3 つ目は、**決めた項目に値を入れる**
形で取り出し、各値が元のどこから来たかを持たせるやり方です。散文を書かせないので、
前節の「要約の要約で固有性が落ちる」経路に入りません。

### 保証されるのは正しさではなく、照合できること

この種の道具の代表例（`REF-046`、入口は `ART-001`）は、抽出した値ごとに**元テキストの文字位置**を
持たせます。紹介記事ではこれが「抽出データが元テキストと一致することを保証する」と書かれますが、
**一次情報を読むと保証ではありません。**

提供元自身が、モデルが入力ではなく**手本の例文から抜いてしまう**ことがあると注意しており、
その場合は位置が `None` になります。対処として示されているのは、位置を持たない抽出を
**捨てる**ことです。つまりこの仕組みが与えるのは、

> **誤りを防ぐことではなく、根拠を持たない抽出を機械的により分けられること。**

です。これは小さい違いに見えて、設計上は大きい差です。散文を生成させる方式では「どこにも無い話」が
文章に溶けて見分けが付きませんが、項目として取り出す方式では**位置が付かなかったという事実が
そのまま検出になります**。前節で挙げた「間違った文書は無い状態より悪い」という問題に、
初めて機械的な歯止めが入ります。

長文は分割・並列・複数回の走査で扱う作りになっており、試行の範囲では十数万文字の資料から
数百件の抽出が報告されています。Gemini 系のほか、別の提供元のモデルや手元で動かすモデルにも
繋げられます。ライセンスは Apache 2.0 です。

**ただし、公開元の表記は「公式に支援される製品ではない」です。** 見出しの「どこそこがリリース」から
受ける印象と、支援の水準は別に確かめます。推論された情報の正確さは、選んだモデル・課題の複雑さ・
指示の明確さに依存するとも明記されています。入口になった紹介記事は 1 年以上前のもので、
推奨モデルの世代も当時のものです。**現況は一次情報で読み直します。**

### 項目を増やすと壊れる

この方式の限界は測られています（`REF-047`）。実文書から決めた形式へ取り出す課題を、
35 文書・12,867 の評価可能フィールドで評価したベンチマークです。結果は、

> **スキーマの幅が広がるほど性能は急激に落ち、369 項目の様式では、試したすべての最新モデルが
> 有効な出力 0% だった。**

というものです。つまり「項目にすれば安全」ではなく、**安全なのは項目が少ないうちだけ**です。
ここから実務上の指針が 1 つ出ます。

> **スキーマは、答えたい問いから必要な項目だけに絞る。広いスキーマを 1 回で埋めさせない。**

同じ資料が挙げている採点の作法も、そのまま使えます。識別子は完全一致、数量は許容幅つき、
名前は意味として同じかどうか、配列は並びを合わせて比べる、そして
**取りこぼしと作り話を別々に数える**。最後の 1 つは、前節の `REF-044`（誤り率は変わらず
再現率が落ちる）と同じ指摘です。**片方にまとめて「誤り率」として数えると、この方式の
本当の弱点が見えなくなります。**

### 書く側で解釈する、という方向

抽出した項目を記憶として使う構成を、非構造化のまま貯めて検索する方式と比べた報告があります
（`REF-048`）。設計思想は「解釈を**読む側から書く側へ移す**」ことで、記憶のベンチマークで
F1 97.10%（比較対象は 80.16〜87.24%）と報告されています。項目として持つことで答えられる
ようになるものとして挙がっているのは、正確な事実、現在の状態、**更新と削除**、集約、関係、
否定の問い、**明示的な不明**です。

**査読前で、提案手法の評価は著者ら自身によるものです。値は移せません。** 採れるのは向き、
すなわち「取り込み時に寄せる」のは正しいが、寄せる先を散文にするか項目にするかで、
後からできることが変わる、という点です。

### 3 つを並べると

このテーマで集めた資料は、次の形に収束します。

| 寄せる先 | 効くこと | 壊れ方 |
| --- | --- | --- |
| 関係を辿る構造 | 定義・参照をたどる、多段の問い | 照会の長さを押さえられないと費用が増える（`REF-039`） |
| 読ませる散文 | どこを見ればよいか（`REF-041`） | 重ねるほど固有性が落ち、読み返されない（`ART-030`、`REF-044`） |
| 決めた項目への抽出 | 検算、更新と削除、明示的な不明（`REF-046`、`REF-048`） | 項目を増やすと成立しなくなる（`REF-047`） |

> **取り込み時に寄せるという方向は支持されています。寄せる先を散文にしないこと、
> 項目にするなら狭く保つこと、どちらの場合も出典の位置を残すことが、分かれ目です。**

## 作る前に測る（charter）

送信記事（`ART-016`）から採るのは数値ではなく**測り方**です。**取得できていないのか、取得できたのに
答えられていないのか**を分けます。前者は LLM を通さずに判定できます。

- **用途**: 索引・グラフ・オントロジーを作るかどうかを、公開された削減率ではなく自分の問いで決める。
- **入力**: 実際に繰り返し聞いている質問 5 件程度と、その**正解集合**（ファイル名・シンボル・項目の
  列挙）を手で書き出したもの。各問いに種類（単一事実／多段／型の網羅／型と関係の結合）を付ける。
  コードも自動化も要りません。
- **安全境界**: 判定は手元で行い、業務データ・本文・パスを外へ出さない。測定のあいだ既存の設定は
  変えない。
- **検証方法**:
  1. いまの経路（検索・読み込み、language server があればそれも）で各問いに答えさせ、**文脈に
     載った集合**を記録する。
  2. **被覆**: 正解集合が文脈に載ったか（はい／いいえ）。ここは決定的に判定できる。
  3. **正答**: 答えが正解集合と一致したか。
  4. **2 が通って 3 が落ちるなら、問題は取得ではない。** 構造を作っても直りません。指示・手順・
     モデルの側を見ます。
  5. 2 が落ちた問いだけを数え、その**種類**を見ます。
- **終了条件**: 被覆が落ちる問いの種類が特定できたら終わり。**どの種類も落ちなければ、何も作らない
  のが結論**です。

## 件数の上限は、モデルを上げても外れない

被覆が落ちる原因のうち、構造とは無関係なものが 1 つあります。`ART-016` では、正解が 5 件ある網羅の
問いに対して上位 4 件しか取らない検索は、**再現率が 0.80 で頭打ち**になりました。より強いモデルに
替えても外れません。取得件数が正解の件数より少なければ、残りは文脈に存在しないからです。

手元でも同じ形が起こります。検索結果の件数上限、読み取りの行数の上限、要約で落ちた列。

> **「全部挙げて」型の問いで取りこぼすときは、まず上限を疑う。** これは索引を作らなくても直せる
> 種類の失敗です。

これは [../instruction-upkeep/](../instruction-upkeep/) や [../heavy-read-delegation/](../heavy-read-delegation/)
が勧める「広く読まず絞って取る」という方向と、**衝突しうる唯一の場面**でもあります。網羅を問われて
いるときは、絞ることが失敗の原因になります。絞る既定は保ったまま、問いの種類が網羅なら上限を先に
確認する、という順序にします。

### 逆に、増やせば良くなるわけでもない

前の項は「少なすぎると天井ができる」でした。反対側は単純ではありません。査読済みの測定
（`REF-101`）は、同じ問いについて 2 つのことを報告しています。**取得の順位が高いのに答えを
含まない文書は、性能を下げる。** そして **問いと無関係な無作為の文書を足すと、かえって精度が
上がる場合がある**（報告された上げ幅は最大 35%）。「関連する順に、入るだけ入れる」という
素朴な既定が最善ではない、という向きです。

ただしこの効果は、**そのまま持ち込めません。** 同じ実験を再現した報告（`REF-102`、再現を目的と
した発表）は、元の設定では現象を再現できたものの、使うモデル・指示文の書き方・出力の長さの
制限を変えると**現れたり、弱まったり、消えたりする**ことを示し、「無関係な文書を入れると得をする」
という一般的な利益としては確認できない、と結論しています。

ここから、取り出し方の可変パラメータ（件数、並べ方、何を入れるか）について 2 つ。

- **公表された調整値を既定として持ち込まない。** 同じ数値が自分の設定で同じ向きに効く保証は、
  この分野では実際に崩れています。自分の文書と自分の設定で測るほかありません。
- **測る前に、切り詰めの経路を塞ぐ。** 再現側の誤り分析では、**切り詰めと壊れた生成**が結果の
  ばらつきに大きく効いていました。入力が文脈長を超えて黙って落ちる構成では、パラメータの差を
  測っているつもりで切り詰めの差を測ることになります。手元で動かす場合の確かめ方は
  [../local-model-boundary/](../local-model-boundary/) にあります。

何回測れば差と言えるかは [../cost-change-evaluation/](../cost-change-evaluation/) にまとめてあります。

## 作ると決めたときの順番

1. **既にあるものから使う。** language server のプラグイン、社内に既にある検索索引を MCP 経由で
   （`REF-008`）。
2. **落ちた種類だけを対象にした最小の構造にする。** 全体をグラフにしない。問いの種類で経路を
   振り分ける方式が、費用あたりでは穏当でした（`REF-036`）。
3. **「どこを見るか」で落ちているなら、グラフより先に生成した文書を考える。** 場所の特定と
   機能の有無は文書で上がりますが、実装の詳細は上がりません（`REF-041`）。逆に、定義と参照を
   記号で辿りたいだけなら 1 に戻ります。
4. **照会の結果の長さを押さえられるか先に確かめる。** 押さえられない構成は、費用が増える側に倒れます
   （`REF-039`）。件数や深さの上限、返す項目の指定、照会に失敗したときの打ち切りを、入れる前に決めます。
5. **陳腐化の担当を先に決める。** 更新の経路が無いなら作らない。事前計算方式の弱点として提供元が
   挙げている点です（`REF-018`）。生成した文書の場合は、記述を版付きのソース位置に結び付けて
   差分で見直せる形にするのが最小の答えです（`REF-042`）。
6. **代わりに読ませるのではなく、入口として置く。** 文書を置いた後もソースを読める経路を残します。
   文書だけに絞ると、場所の特定で得た分を実装の詳細で失います（`REF-041`）。
7. **要約を束ねて、さらに要約させる段を作らない。** 重ねるほど固有性が落ちます（`ART-030`、`REF-044`）。
   まとめが要るなら、まとめの元を直接指せる形にします。
8. **関連は生成物から取り出さず、実際に共有しているものから導く。** 生成した本文にリンクを書かせる
   方式は成立しませんでした（`ART-030`）。この環境で言えば、出典 ID の相互参照のように、
   機械で検算できる関係を関連の根拠にします。
9. **選定の閾値は順位ではなく絶対値にする。** 相対の基準は、母数が動かない限り何も増えません
   （`ART-030`）。
10. **入れた後の判定はタスク単位で、費用と品質を同時に行う。** 1 回の応答が短くなったことは安くなった
    証拠になりません。手順は [../cost-change-evaluation/](../cost-change-evaluation/) にあります。
11. **「作られたか」ではなく「読み返されたか」で価値を測る。** 生成が成功したことは、使われたことの
    証拠になりません（`ART-030`）。
12. **項目として取り出すなら、スキーマを狭く保ち、出典の位置が付かなかったものは捨てる。**
    広いスキーマは 1 回で埋まりません（`REF-047`）。位置の無い抽出をより分けられることが、
    この方式の主な利点です（`REF-046`）。
13. **採点では、取りこぼしと作り話を別々に数える。** まとめて「誤り率」にすると弱点が見えなくなります
    （`REF-047`、`REF-044`）。

## 作ったあとに毎回かかるもの

比較に出てくるのは構築の費用までで、**そのあと毎回かかる分**は表に載りません。実際に一式を組んだ
記録（`ART-019`）から、見積もりに入れる項目を挙げます。

- **更新の担当。** グラフは定期的に作り直さないと、古い構造のまま誤った答えを返します。誰がいつ
  回すかを決めていないなら、作らない理由になります。
- **実行環境の固定。** 依存する処理系の版が固定で、1 つ上の版では依存パッケージの構築に失敗したと
  報告されています。開発機の更新と衝突します。
- **文字コード。** 日本語の Windows 環境で、文字コードに起因する失敗が起きたと報告されています。
  公開されている手順は作者の環境で通ったものなので、別の環境では通らないことがあります。
- **接続の読み込まれ方。** 編集環境によっては、接続した道具がそのセッションで読み込まれない事象が
  報告されています。入れたつもりで効いていない状態は、黙って起こります。

これらはどれも、**公式のプラグインで済ませる場合には発生しない**種類の費用です。自前の構造を選ぶ
理由は、この分を払ってでも取りたい問いの種類が、測定で特定できているときに限ります。

## 限界

- `REF-036` は文章の質問応答ベンチマークであり、コードベースの探索を直接測ったものではありません。
  問いの種類ごとの**傾向**は移せますが、**数値は移せません**。コード領域の費用については `REF-039`、
  費用と品質を並べた数字については `REF-040` が直接の一次情報です。
- `REF-039` の評価は Python 1 言語に限られると著者自身が書いています。`REF-040` は提案手法の作者ら
  自身による評価です。どちらも、採るのは向き（増える側に倒れうる、費用と品質は同時に動く）であって、
  自分の環境の値ではありません。
- `ART-008` は商用の会社の記事で、末尾に自社サービスの案内があります。引用されている数値は一次情報で
  確かめましたが、記事が勧めている道具の削減率は提供元の自己申告で、この手引きはその採用を勧めていません。
- `ART-016` は 5 問・16 ノードの合成例で、著者自身が、記事の例示表（macro 0.681）が実測
  （0.150〜0.548）より楽観的だったと訂正しています。採るのは測り方だけです。
- `REF-008`、`REF-018`、`REF-038` は提供元自身の資料で、独立した比較ではありません。ただしこの環境の
  既定の挙動と、公式プラグインの前提・制限については正本です。
- `ART-019` は著者 1 人が自分の課題プロジェクトで組んだ記録で、独立した再現はありません。採るのは
  倍率の読み方と、運用で何が起きたかの項目だけです。使われている道具の保守状況は確認していないので、
  この手引きは特定の道具の導入を勧めていません。
- `REF-041` は査読前で、対象は Python の 12 リポジトリです。下流の解決率は 57 件での比較なので、
  差は数件分にあたります。採るのは向きであって幅ではありません。
- `REF-042` は提供元自身のリポジトリで、独立した評価ではありません。採ったのは**陳腐化対策として
  何を用意する必要があるか**という設計項目だけで、効果の主張も導入も採っていません。この環境では
  動かしていません。
- `REF-043` は 2024 年のモデルを Java のメソッド単位で評価したもので、値は現在の世代に移せません。
  採るのは、生成した散文には無視できない割合で事実誤りが混ざるという向きだけです。
- 文書を置く方式について、費用と品質を同じ実験で並べた独立の数字はまだ見つけていません。
  `REF-041` は品質側、`ART-007` は費用側の 1 点で、両者は別の実験です。
- `REF-101` と `REF-102` は互いに反対の向きを示しています。この手引きが採ったのは、どちらの数値でも
  なく「取り出し方の調整値は自分の設定で測るほかない」という結論だけです。両者とも対象は公開の
  質問応答データセットで、コードベースや社内の文書ではありません。
