# 事前に構造を作るか、その場で探すか

**この手引きは未検証です。** 下の測り方はこの環境で一度も実行していません。状態は `experiment` で、
特定の構成の導入を勧めるものではありません。

## 何の問題を扱うか

起動条件は、**探索の費用か答えの正確さに不満があって、索引・ナレッジグラフ・オントロジーを
作ろうと考えたとき**です。この種の提案は「トークンが 10 分の 1 になる」といった倍率とともに
流通します。倍率を評価する前に、作るかどうかを決める材料を置きます。

ほかの手引きとは層が違います。[instruction-upkeep/](../instruction-upkeep/) は**常時載るもの**、
[heavy-read-delegation/](../heavy-read-delegation/) は**1 回ごとの大きい読み取り**、
[token-drain-review/](../token-drain-review/) は**自分の入力以外で減る分**です。ここで扱うのは
**取りに行く経路そのものを作り替えるか**です。

## この環境の既定は、都度の探索である

提供元の説明では、取得のやり方は 2 つに分かれます（`REF-018`）。すべてを事前に処理して埋め込み
検索に備える方式と、**軽い識別子（ファイルパス、クエリ、リンク）だけを持ち、実行時に道具で
読み込む**方式です。この製品は後者を軸にした**ハイブリッド**で、指示ファイルは先に文脈へ載せ、
`glob` と `grep` で環境を動き回ります。提供元は「速さのために一部を先に取り、残りは自律的に
探索するハイブリッドが最も効く」と書き、同時に**実行時の探索は事前計算より遅い**こと、
事前計算側には索引の陳腐化が付くことを挙げています。

大規模なコードベース向けの公式の手引き（`REF-008`）も、**独自のグラフを作れとは書いていません**。
挙がっているのは次の順です。

| やりたいこと | 公式が挙げる手段 |
| --- | --- |
| 定義や呼び出し元を、木を舐めずに引く | language server に繋ぐ code intelligence プラグイン |
| 生成物・ベンダ取り込みを読ませない | `permissions.deny` の `Read` 規則 |
| 関係ない指示を載せない | 階層化した指示ファイル、`claudeMdExcludes` |
| 作業に要る範囲だけ展開する | worktree の sparse な取得 |
| 領域固有の手順を必要なときだけ載せる | 領域ごとの skill |
| 既に社内に検索・RAG の索引がある | **MCP の道具として見せて引かせる** |

最後の行が要点です。公式が想定しているのは**既にある索引を使う**ことであって、エージェントの
ために新しく作ることではありません。ここから最初の分岐が出ます。

> **関係や定義を辿りたいだけなら、グラフを作る前に language server がある。**

## 構造が効く問いと、効かない問い

統一した条件での独立比較（`REF-036`）は、どちらかが一貫して勝つわけではないと報告しています。

| 問いの種類 | 通常の RAG | グラフ側 |
| --- | --- | --- |
| 単一ホップ（NQ） | **64.78%** | 63.01%（グラフ側の最良） |
| 多段（MultiHop-RAG） | 67.02% | **70.27%** |
| 時間・推論を要する問い | 25.73% | **49.06%** |

論文の言葉では「RAG and GraphRAG exhibit complementary behaviors rather than a consistent winner」
であり、結論は両者を排他的な選択として扱うなというものです。

**単一事実の問いでは構造は効かず、わずかに落ちます。** 同じ向きの観察が送信記事側にもあります
（`ART-016`）。単一事実の問いに 16 ノードの部分グラフを渡すと周辺のノイズが混ざり、精度が落ちた
と報告されています。

## 作ること自体が、損失と費用を持つ

同じ独立比較から（`REF-036`）。

- **抽出で落ちる。** HotpotQA では、構築した知識グラフに**正解実体の約 65.8% しか現れません**。
  グラフは、抽出時に拾えなかったものを後から返せません。
- **構築が高い。** 構築時間は通常の RAG の 135 秒に対し 5,560〜7,702 秒。知識グラフ方式は検索も
  14,434 秒かかっています。
- **併用は効くが安くない。** 問いの種類で振り分ける方式が +1.1%、両方引いて連結する方式が +6.4%。
  後者は計算量が倍になります。

**範囲の取り違えにも注意します。** よく引かれる GraphRAG の一次情報（`REF-037`）が対象にしているのは
**クエリ指向の要約**、すなわち「この資料群の主題は何か」という全体への問いで、報告されているのは
約 100 万トークン規模の資料に対する包括性と多様性の改善です。多段の質問応答やコードベースの探索の
根拠としてそのまま引くのは、論文の対象範囲を超えています。

## 作る前に測る（charter）

送信記事（`ART-016`）から採るのは数値ではなく**測り方**です。**取得できていないのか、取得できたのに
答えられていないのか**を分けます。前者は LLM を通さずに判定できます。

- **用途**: 索引・グラフ・オントロジーを作るかどうかを、公開された削減率ではなく自分の問いで決める。
- **入力**: 実際に繰り返し聞いている質問 5 件程度と、その**正解集合**（ファイル名・シンボル・項目の
  列挙）を手で書き出したもの。各問いに種類（単一事実／多段／型の網羅／型と関係の結合）を付ける。
  コードも自動化も要りません。
- **安全境界**: 判定は手元で行い、業務データ・本文・パスを外へ出さない。測定のあいだ既存の設定は
  変えない。
- **検証方法**:
  1. いまの経路（検索・読み込み、language server があればそれも）で各問いに答えさせ、**文脈に
     載った集合**を記録する。
  2. **被覆**: 正解集合が文脈に載ったか（はい／いいえ）。ここは決定的に判定できる。
  3. **正答**: 答えが正解集合と一致したか。
  4. **2 が通って 3 が落ちるなら、問題は取得ではない。** 構造を作っても直りません。指示・手順・
     モデルの側を見ます。
  5. 2 が落ちた問いだけを数え、その**種類**を見ます。
- **終了条件**: 被覆が落ちる問いの種類が特定できたら終わり。**どの種類も落ちなければ、何も作らない
  のが結論**です。

## 件数の上限は、モデルを上げても外れない

被覆が落ちる原因のうち、構造とは無関係なものが 1 つあります。`ART-016` では、正解が 5 件ある網羅の
問いに対して上位 4 件しか取らない検索は、**再現率が 0.80 で頭打ち**になりました。より強いモデルに
替えても外れません。取得件数が正解の件数より少なければ、残りは文脈に存在しないからです。

手元でも同じ形が起こります。検索結果の件数上限、読み取りの行数の上限、要約で落ちた列。

> **「全部挙げて」型の問いで取りこぼすときは、まず上限を疑う。** これは索引を作らなくても直せる
> 種類の失敗です。

これは [../instruction-upkeep/](../instruction-upkeep/) や [../heavy-read-delegation/](../heavy-read-delegation/)
が勧める「広く読まず絞って取る」という方向と、**衝突しうる唯一の場面**でもあります。網羅を問われて
いるときは、絞ることが失敗の原因になります。絞る既定は保ったまま、問いの種類が網羅なら上限を先に
確認する、という順序にします。

## 作ると決めたときの順番

1. **既にあるものから使う。** language server のプラグイン、社内に既にある検索索引を MCP 経由で
   （`REF-008`）。
2. **落ちた種類だけを対象にした最小の構造にする。** 全体をグラフにしない。問いの種類で経路を
   振り分ける方式が、費用あたりでは穏当でした（`REF-036`）。
3. **陳腐化の担当を先に決める。** 更新の経路が無いなら作らない。事前計算方式の弱点として提供元が
   挙げている点です（`REF-018`）。
4. **入れた後の判定はタスク単位で行う。** 1 回の応答が短くなったことは安くなった証拠になりません。
   手順は [../cost-change-evaluation/](../cost-change-evaluation/) にあります。

## 限界

- `REF-036` は文章の質問応答ベンチマークであり、コードベースの探索を直接測ったものではありません。
  問いの種類ごとの**傾向**は移せますが、**数値は移せません**。
- `ART-016` は 5 問・16 ノードの合成例で、著者自身が、記事の例示表（macro 0.681）が実測
  （0.150〜0.548）より楽観的だったと訂正しています。採るのは測り方だけです。
- `REF-008` と `REF-018` は提供元自身の資料で、独立した比較ではありません。ただしこの環境の既定の
  挙動については正本です。
- この手引きは、ここで示した測り方をこの環境で一度も実行していません。
