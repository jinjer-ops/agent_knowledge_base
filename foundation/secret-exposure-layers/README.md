# 秘密が外へ出る経路を、どの層で止めるか

**この領域を開くとき**: エージェントにコードや設定を書かせ、それをコミット・push・共有する経路が
できたとき。あるいは「秘密が混ざっていないか」を一度の検査で確かめているとき。

**この環境では運用検証していません。** 下の層はすべて公開されている仕様と測定から読み取った内容で、
どれもここで動かして確かめていません。道具の導入も勧めていません。

## 一度の検査では決まらない

この領域の出発点は、検査の通過が「秘密が無い」ことの証明にならない、という測定です。
基準データ付きで複数の検出器を比べた研究（`REF-146`）は、**精度と再現率を両立する道具が無い**と
報告しています。精度の高い検出器は見逃しが多く、見逃しの少ない検出器は誤検出が多い。片方を選んだ
時点でもう片方の失敗様式を引き受けます。

だから問いは「どの道具を入れるか」ではなく、**どの層で何が止まり、何がすり抜けるか**になります。
層を並べる理由は、どの層も単独では閉じないからです。

## 層ごとに、止まるものと止まらないもの

| 層 | 止まるもの | すり抜けるもの |
| --- | --- | --- |
| エージェントに読ませない | 指定したパスを、組み込みのファイル操作と、ツールが解釈できる形のシェル読み取りから外す（`REF-145`） | パスを名指ししない読み取り、自前のスクリプトが開くファイル。OS の水準で止めるならサンドボックス側（`REF-145`） |
| 手元の検査（コミット前） | 変更された範囲だけを、再現率の高い検出器で見る | その作業コピーで有効にした人にしか効かない。誤検出の扱いを決めていないと、作業が止まるか、無効化される |
| push の時点で止める | 提供元が決まった型の資格情報。public への push は利用者の既定で有効（`REF-143`） | **汎用の秘密（秘密鍵・接続文字列）と、AI で検出されるパスワード類は既定の対象外**（`REF-144`） |
| 公開後の検出 | 履歴全体と、issue・PR・Discussions・Wiki・secret gist まで（`REF-003`） | 既に外から読める。提携提供元へ直接通知される型は自分のアラート一覧に出ない（`REF-003`） |
| 是正 | 資格情報を無効にする | ファイルを消すことは是正ではない |

**ここが判断の分かれ目です。** 止める層（push の時点）が守るのは、形の決まった提供元のトークンだけです。
自分たちで作ったトークン、データベースの接続文字列、秘密鍵、人が決めたパスワードは、既定の設定では
止まらず、無料の public リポジトリでは検出側の既定にも入りません（`REF-144`）。
**自分の環境で最も漏れやすい種類ほど、既定の仕組みの外にあります。**

## 是正は、失効が本体

漏れた後の順序を取り違えないために、2 つの独立した根拠があります。

- 査読済みの実地調査（`REF-147`）は、漏えいした秘密の**大半がそのまま残り**、取り除いた側も履歴までは
  書き換えていないと報告しています。削除は是正として機能していません。
- 提供元自身の資料（`REF-003`）も、まず資格情報を入れ替えるよう書き、**失効させたなら履歴から取り除く
  作業は多くの場合不要**だとしています。

したがって順序は、**失効・入れ替え → 影響範囲の確認 → 必要なら履歴**です。履歴の書き換えを先頭に
置くと、時間のかかる作業をしている間、有効な資格情報が外に残り続けます。

この順序は、公開前の確認手順（[../../skills/repository-publish/SKILL.md](../../skills/repository-publish/SKILL.md)）にも
同じ形で書いてあります。

## エージェントを入れると、どこが増えるか

秘密検出を事業にしている会社の年次報告（`REF-148`、提供元の自己申告）は、エージェントが共著として
記録されたコミットの漏えい率が全体の基準より高いこと、そして**エージェント用の設定ファイル**から
多数の資格情報が見つかっていることを報告しています。測り方は共著の記録に頼った代理指標で、報告自身も
モデルの版が進むにつれて差が縮まったと書いているので、**倍率は環境の判断材料にしません**。
採るのは経路の指摘です。

- エージェントが書いたコードは、人が書いたものと同じ経路で漏れる。レビューの密度が下がれば、
  その経路だけが太くなる。
- **接続設定そのものが新しい経路**になる。資格情報を設定ファイルへ直接書く形が広まると、
  コードを一度も通らずに秘密が版管理へ入る。
- 秘密は、コミット以外にも出る。ログ、プロンプト、出力、画面の記録。止める層をコミットの前後にだけ
  置くと、ここは素通りする。

## 確かめる項目

この環境で未確認のものを含みます。順に見ます。

1. **エージェントが読める範囲**。資格情報を置いたファイルが読み取りの対象外になっているか。
   製品ごとの書き方は [claude-code/README.md](../claude-code/README.md) にあります。
   設定しただけでは、名指ししない読み取りと自前のスクリプトは防げません（`REF-145`）。
2. **接続設定に値が埋まっていないか**。参照ではなく値が書かれていれば、それは版管理へ入る候補です。
3. **止める層が、自分の種類の秘密を対象にしているか**（`REF-144`）。対象外なら、手元の検査が
   その分を担うことになります。
4. **検査の通過を何の証拠にするか**を決めてあるか。`REF-146` の測定どおり、通過は「設定した規則が
   反応しなかった」という意味しかありません。
5. **失効の手順が、誰に対して誰が実行できるか**。漏れてから調べ始めると、`REF-147` が記録した
   「結局そのまま」に合流します。
