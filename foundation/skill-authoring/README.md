# skill の書き方

置き場所の判断は [../claude-code/README.md](../claude-code/README.md)、指示ファイルの正本の置き方は [../agents-md/README.md](../agents-md/README.md) にあります。ここは「skill にすると決めた後、どう書き、どう確かめるか」だけを扱います。

## skill にするか、別の層にするか

| 状況 | 置き場所 |
| --- | --- |
| 同じ手順・判断基準を繰り返し渡している。入口ファイルの一節が「事実」ではなく「手順」に育った | skill |
| ほぼ全作業で必要な短い事実 | `AGENTS.md` |
| 対象ファイルや用途が限られる方針 | 条件付き読み込みのルール層 |
| **必ず実行させたい処理** | skill ではなく hook |

最後の行が要点です。skill の起動は `description` との照合による選択なので、起きる保証がありません。確実に止めたい・必ず通したい処理は仕組み側に置きます（`REF-001`）。

記事や思い付き1件につき skill を1つ作らないでください。skill を増やすこと自体に常時の費用があります。全 skill の名前と説明は起動時に毎回読まれます。自動起動を抑止した skill だけは一覧にも入らず、名前で呼ぶまで何も占有しません（`REF-017`）。手で呼ぶと決めている手順は、そう宣言しておくと常時の費用が消えます。

## 手順は、思い出して書くのではなく、記録から掘り出す

何を書くかを頭から考えると、起きていない問題のための手順ができます。出どころは**実際に起きたこと**にします。

1. 過去の作業記録を読み、**複数回繰り返された作業**と、今後も確実に再実施される手順を洗い出す。
2. 候補のうち再利用の頻度が高いものだけを残す。全部は要りません。
3. 記録に残った**失敗を、禁止事項の理由として書き写す**。なぜ駄目かが実例として残ります。

`ART-004` はこの流れを実際に回し、100 本以上の作業記録から 40 の候補を出し、13 本まで絞っています。手順の中身だけでなく「なぜその制約があるか」まで記録から供給される点が要点です。公式の指針が勧める評価の作り方（skill 無しで走らせて失敗を記録する。`REF-014`）とも同じ向きで、どちらも**出発点を実測に置く**ことを言っています。

掘り出す作業自体はモデルに任せられますが、**採用の判断は人が行います**。モデルに手順書を作らせたものは、独立した評価では平均して成果を下げています（`REF-016`）。候補として出させ、絞るのは人、という分け方にします。

## 手順だけでなく、名前と実体の対応表を渡す

手順を丁寧に書いても、エージェントは**その環境でしか決まらない対応関係**を推測で埋めます。
どのログがどのサービスのものか、ある呼び名が実際にはどのディレクトリを指すのか、監視画面の
どの項目がどの構成要素に対応するのか——このあたりです。推測が外れると、手順は正しく実行されたのに
結論だけが的外れになります。

ある実践報告（`ART-033`）は、この対応表を**モジュールマップ**として skill に書き込み、
**エージェント自体の能力よりも、この対応関係をどれだけ具体的に渡せるかが結果を左右する**と述べています。
1 組織の自己申告で対照はありませんが、向きは別の公式仕様でも裏が取れます。別の製品の skill の公式例は、
本体に手順を置き、**判断に使う具体的な数値の表を `references/` 側のファイルに置く**形になっています（`REF-064`）。

書くときの切り分けはこうなります。

| 内容 | 置き場所 |
| --- | --- |
| 何をどの順で確かめるか（手順・分岐） | `SKILL.md` 本体 |
| 名前と実体の対応表、閾値表、命名規則 | `references/` 側のファイル |
| その対応表を参照しろという 1 行 | 本体から**一段だけ**の参照として置く |

**常時読み込みの側へ対応表を置きません。** 製品によっては常時の指示に明示の上限があり、
ある製品は 25KB を上限、120 行程度を推奨とし、「指示が長いほど、実際の問題に使える余地が減る」と
書いています（`REF-063`）。常時側に置くのは「記憶で書かず、対応表を読んでから答える」という
短い行だけにし、表そのものは呼び出し式の側へ出します。

対応表は環境が変われば古くなります。**いつ時点のものかを表の先頭に書き**、構成を変えたときに
一緒に直す対象として扱います。古い対応表は、無いよりも危険です。

## 制約は、強さを使い分ける

手順の中の制約を全部同じ強さで書くと、どれが本当に守るべき行なのか分からなくなります。段階を付けます（`REF-021`、`REF-022`）。

| 強さ | 使う場面 |
| --- | --- |
| **しなければならない / してはならない** | 守らないと**害が出る**こと。取り返しのつかない操作、安全や公開の境界 |
| **すべき / すべきでない** | 既定の方針。理由を比べたうえで外れてよい |
| **してもよい** | 本当に任意 |

**強い語を使う範囲は、意図的に狭く保ちます。** この語法を定義した標準自身が、命令形は慎重かつ控えめに使うべきで、相互運用に実際に必要な場合か、害を及ぼしうる挙動を制限する場合に限って使うよう求めています（`REF-022`）。

この制限は、禁止を並べるより判断の材料を渡すほうが効く、という方針（`REF-012`）と同じ結論になります。両立させる書き方はこうです。

- 害を止める行だけを強い語で書く。
- **禁止には必ず理由を併記する**（`ART-004`）。理由が付いていれば、想定していなかった場面でも読み手が判断できます。理由を書けない禁止は、たいてい禁止ではなく好みです。
- 残りは「こういう場合はこうする」という判断の基準として書く。

## 形式は、移植できる範囲で書く

共通仕様（`REF-015`）が決めているのは、これだけです。

- ディレクトリ名と一致する `name`。1〜64文字、小文字英数字とハイフンのみ、先頭と末尾のハイフンと連続したハイフンは不可
- `description`。1〜1024文字、空でないこと
- 任意: license、環境の要件（最大500文字）、自由な付加情報、事前に許可する道具（実験的）
- 補助ファイルは `scripts/`（実行する）、`references/`（読む）、`assets/`（素材）

製品側（`REF-002` は Claude Code）には、この外側に多くの項目があります。自動起動の抑止、利用者からの呼び出しの抑止、対象ファイルの限定、別の文脈での実行、モデルや思考の深さの上書き、hook の同梱、引数の受け取りなどです。**どの項目まで使うかが、そのまま移植できる範囲になります。** 複数のエージェントで共有する skill は必須2項目と本文だけで書き、製品固有の挙動に頼る部分は分けます。

## description は索引であって説明文ではない

`description` は、使うかどうかを決めるためだけに読まれます。

- **三人称で書く**。システム側の指示に差し込まれるため、一人称・二人称が混ざると発見に失敗します（`REF-014`）
- 「何をするか」と「どの語が出てきたら使うか」を両方入れる。実際の依頼に現れる語を入れる
- `helper`、`utils`、`tools` のような曖昧な名前を付けない
- 要点を先頭に置く。製品によっては一覧に載せる段階で長さを切り詰めます（`REF-002`）

別の製品の公式仕様も同じことを、より強い言い方で書いています。**曖昧な description や欠けた description は、
本体がよく書けていても skill ごと読み飛ばされる原因になる**ため、起動させたい具体的な場面・対象・症状を
description の中に並べるよう求めています（`REF-064`）。「○○用の skill」という名詞だけの説明を、
「〜のときに使う」という形へ書き換えます。

## 本体は、残り続ける前提で書く

Claude Code では、読み込まれた本文は一つのメッセージとして会話に入り、**以後の turn も残り、読み直されません**（`REF-002`）。したがって、

- 途中の一度きりの手順としてではなく、作業の間ずっと効く指示として書く
- 1行ごとに、以後ずっと払う費用に見合うかを問う。モデルが既に知っていることは書かない（`REF-014`）
- 自由度を作業の壊れやすさに合わせる。判断が要る作業は方針だけ、決まった型がある作業は雛形付き、壊れやすく順序が決まっている作業は実行する命令そのもの
- 本体は500行未満に保ち、詳細は別ファイルへ出す。**参照は本体から一段だけ**にする（入れ子にすると部分読みで情報が欠けます）
- **大事な指示を先頭に置く。** 長いセッションで会話が要約されると、呼んだ skill の本体は読み直されますが、1本あたりと合計に上限があり、超えた分は切り捨てられます。切り捨ては先頭を残すので、後ろに置いた指示から先に失われます。古く呼んだものから丸ごと落ちることもあります（`REF-017`）
- 100行を超える参照ファイルは、冒頭に目次を置く
- 「いつまでは旧方式」のような時限の記述を本文に置かない。旧方式は別節へ畳む
- 用語を一つに固定し、パスは常にスラッシュ区切りで書く
- 選択肢を並べず、既定を1つ示して例外だけ添える

## 確かめてから運用に入れる

1. **評価を先に作る。** skill 無しで代表的な作業を走らせ、実際に失敗した点を記録する。そこから3つの場面を決め、基準値を測り、それを通す最小限だけ書く（`REF-014`）
2. 使う予定のモデル全部で試す。小さいモデルで足りるか、大きいモデルで説明過多になっていないかを見る
3. 新しいセッションで、起動すべき場面で起動するか、参照ファイルまでたどれるかを見る。読み込まれた形跡を確認するまで運用中と扱わない
4. 入れた後と入れる前を比べる。改善が見えないものは外す

## 実行時の合否判定を、本文に任せない

前の節は運用に入れる前の評価の話です。別の問題として、**skill が動いている最中に「できたか」を
判定させる**書き方があります。「変換後、本文を読み直して不自然な箇所が無いことを確認する」のような行です。

この判定は甘く出ます。評価役としてのモデルは**自分の出力に高い点を付け**、人の評価者が同等と判断した
場合でも差が付きます（`REF-094`、査読済み）。自分が書いたものを自分で見る構成は、この条件そのものです。

対処は、判定を本文の外の**決定論的な検査**へ出すことです。共通仕様が `scripts/`（実行する）と
`references/`（読む）を分けているのは、この使い分けができる形になっています（`REF-015`）。

実例があります。日本語の文章を書き直す公開の skill は、本文に原則を並べたうえで、
**同梱した検査スクリプトの実行を必須**にしています。作者が挙げている理由は「モデルは自己チェックで
甘く評価する傾向がある」で、上の測定と一致します（`ART-039`、`REF-092`）。
同じ道具は差分を出すスクリプトも持っており、**何が変わったかを人が見る**経路を残しています。

書くときの切り分けはこうなります。

| 役割 | 置き場所 |
| --- | --- |
| どう直すか（判断・手順） | `SKILL.md` 本文 |
| 直ったかの機械的な判定 | `scripts/` 側の検査 |
| **必ず通したい**検査 | skill ではなく hook（この章の冒頭の表と同じ理由） |

ただし、検査が通ったことは**設定した規則に触れなかった**ことしか意味しません。同じ道具の README が
自分でそう書いています（`REF-092`）。合格の表示を品質の保証として本文に書かないでください。

## 増やす前に知っておくこと

独立した評価（`REF-016`、査読前・単一のベンチマーク）では、方向として次が観測されています。数値は目安であり、自分の環境の期待値として持ち込みません。

- 人が用意した skill は平均で成果を上げた一方、**モデルに自分で作らせた手順書は平均で下げた**。生成したものをそのまま採用せず、範囲を絞って人が確かめてから入れる
- 入れれば効くわけではない。2割弱の課題では skill を入れた方が悪くなった。だから前後の比較が要る
- 1つの作業に効くのは2〜3個まで。それ以上では伸びが落ちる
- 「網羅的」に書いたものは skill 無しより悪く、「詳しいが絞った」ものと「簡潔な」ものが最も効いた

最後の点は、公式の指針（`REF-014`）が勧める「簡潔に、絞って書く」と同じ方向です。一方、同じ指針が勧める「skill 作りをモデルに任せる」進め方については、この実測が人の確認を挟む理由になります。
