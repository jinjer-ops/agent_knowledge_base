# 他の人とそのエージェントが使う道具を作って配るとき

MCP サーバーやセットアップの配布物のように、他の人のエージェントが読んで実行する道具を作ったときの教訓です。自作の MCP を独立した 2 つの AI にレビューさせたところ、2 つが別々に同じ点数と同じ重大な指摘を出しました。偶然ではなく、作り方の構造的な盲点として扱っています。出どころは 2026-07〜08 の運用の記録です。

## 中心にある癖

**守るべき境界と、確かめられる受入条件を先に決めず、便利な実装を完成させてから、指摘のたびに局所的に直す。** 後付けの直し（パスの制限、書き込みの旗、文字コードの対応表）は、どれもこの型から出ていた。

## 作る前に表にすること

1. **道具ごとの脅威の表**: 呼べる主体、LLM が読む信頼できない入力、送信先、秘密、変更する対象、最悪の副作用、戻し方。埋まらないなら作らない。
2. **既定で拒否する能力の表**: 対象・操作・役割・確認・戻し方・監査を並べる。任意のパスや任意のメソッドを呼べる口は本番に置かない。削除は常に別の能力にする。
3. **異常系を正常系より先に受入条件へ入れる**: 認証切れ、401・403・429・5xx、切断、二重クリック、途中の失敗、再実行、競合、古い配布物、悪意のあるメタデータ。

## 具体的な落とし穴

- **パスを相対に限っても、トークンの漏れは防げない。** リダイレクトを追うと、`Authorization` ヘッダーがリダイレクト先へ送られる。リダイレクトを追わない設定にする。
- **パスの先頭の `/` を確かめるだけでは、管理用の API が通る。** 対象のリソースを許可の一覧（正規表現）で限る。
- **GET などの読み取りのメソッドで状態を変えない。** 読み取りの URL でパスワードを再設定していたため、ページに画像として埋め込むだけで、閲覧した他人のパスワードが変わる状態だった。秘密や権限を変える操作には、再認証・CSRF 対策・二重実行の防止・期限・監査を付ける。
- **外から来た値を、生成するシェルの文に素で埋め込まない。** `$()` や `"` で任意のコードが動く。
- **「X は持たせない」と書いても経路が残ることがある。** 文書の境界の宣言とコードを突き合わせる。
- **自己完結の配布（Base64 の埋め込みなど）は、完全性も署名も与えず、読みにくくするだけである。** 署名付きの一覧（ハッシュ・期限・版）で配る。依存は版を固定し、ハッシュで確かめる。
- **ソースを直しても、利用者は守られていない。** 正本を 1 つにし、実際に配る物を作って、対象の OS・言語設定・版で動かして確かめるまでを完了にする。
- **「0 件」と「やっていない」を同じ表し方にしない。** 件数 0・空の一覧・未実行・失敗は、読む側から区別できる別の値にする。

## 配るコードと文書は、相手の LLM が読む

- 配布物は、実行する前に利用者とその LLM が読む。慎重な LLM ほど、個人名・内部の前提・古いコメントに引っかかって実行を止める（作者向けのコメントを読み、埋め込まれた値を他人の秘密と誤解して止まった例がある）。配るコードと文書には、個人名、実在の利用者名、個人に紐付いた秘密の名前、内部の符号、作った時の会話を知らないと読めない言い回しを書かない。開発のメモは配らない別のファイルに置く。
- 任意のメソッドとパスで API を呼べる汎用の口は、説明欄などに仕込まれた指示に誘導されて、認証付きの要求を外へ送る経路になる。相対パスだけに限り、書き込みは既定で禁止にし、利用者が明示したときだけ許す。
- 個人データを含む運用のファイルは、配布するパッケージの外に置く。

## 確かめ方

- 自分の失敗を隠さず列挙した資料を独立した AI に渡すと、自己診断より深い根本原因と、まだ見つかっていない欠陥が出た。
- 配布物は「作って検査する」。配る本文を実際の配布の処理で作り、構文を実行せずに検査し、検査が効いていることを対照（壊した版が落ちること）で確かめる。Windows PowerShell 5.1 で通るかは、PowerShell 7 では確かめられない。
